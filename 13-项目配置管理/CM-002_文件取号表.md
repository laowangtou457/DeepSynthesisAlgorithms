## 0 一句话

本表是**全工程文件编号的唯一登记处**：任何一份配置项文件的新增、改名、停用，都先在这里取号、登记，再落盘。
**编号一经分配，永不复用**——即使文件被删除或归档，号段也不回收。

> **为什么要有这张表**：评审请求 / 评审意见 / 复查记录此前散落两处且无统一编号，「哪个需求评到哪一步」只能靠文件名里的中文描述去认，跨文件引用时极易张冠李戴。本次统一为 `<编号>_<原文件名>` 命名，并给**评审类三件套**单独分配 `REV-<对象标号>-<序号>`。

## 1 编号规则

### 1.1 编号格式

```
<类别码>-<三位流水号>                 # 通用类别
REV-<对象标号>-<两位序号>              # 评审类专用（对象标号 = SW-004 / SW-005 / … / D-017）
```

### 1.2 文件命名格式

```
<编号>_<原文件名>                      # 下划线连接；原文件名一字不改地保留
```

| 例 | 说明 |
| --- | --- |
| `TPL-013_synopsis_v1.yaml` | 模板类第 13 号 |
| `REV-SW-007-02_shot_prompt_v1-分镜提示词生成模板-导演视角评审意见-独立会话.md` | SW-007 的第 2 份评审文件（意见） |

### 1.3 三条硬规则

1. **永不复用**：编号一经分配即锁定，文件删除 / 归档后号段不回收，避免历史引用指向新文件。
2. **流水号按类别独立**：各类别从 `001` 起独立编号，引用时**必带类别码**。
3. **改名即登记**：文件名一经变更，同步更新本表与全工程引用（引用同步是改名动作的一部分，不是后续补做项）。

### 1.4 评审类（`REV-`）的编号约定

评审类**不按时间顺序排号，而按「对象」分组**，因为这张表的首要用途就是回答「**某个需求的评审做到哪一步了**」：

| 序号位 | 含义 |
| --- | --- |
| `-01` | **评审请求书**（我方 → 评审方） |
| `-02` `-03` … | **评审意见**（评审方 → 我方）；**预评审（路径 A）在前、独立会话（路径 B）在后** |
| `-0N`（末位） | **复查 / 处置记录**（我方，逐条闭环） |

> 因此看文件名即可知「对象 + 阶段」：`REV-SW-006-03_…复查记录.md` = SW-006 的处置结果。
> 对象的标号取**该对象所承载的需求编号**（`synopsis_v1` → `SW-004`）；非软件需求条目的对象取**其交付物编号**（《分镜提示词交付规范》→ `D-017`、`硬件级需求文档` → `D-014`）。
> **2026-10-14 扩展（第三种情形）**：当评审对象是**一组文档**而非单一交付物时（三层需求 ＝ `D-004` 主登记 ＋ `D-012` / `D-013` / `D-014` 三份展开件），取该组的**主登记编号 `REQ-006`** 作对象标号——理由：主登记是该组的**共同上位与总索引**，其分层索引、项目级条目与交付物登记**均在评审范围内**，而用任一层标号都会指向偏窄（且 `D-014` 的 `-01` 位已被占用，见下条）。
> ⚠️ **一处既有编号错位（只登记、不改名）**：`REV-D-014-01` 的 `-01` 位是**评审意见**而非请求书——系统一取号时由旧文件名机械映射而来，与上表「`-01` ＝请求书」规则不符。因**改名属 C 类变更**（牵动 6 处引用）且该件为**历史留痕**，故**保留原状**；**引用时须注明「该 `-01` 为意见」**。

## 6 取号流程（新增配置项时怎么做）

1. **定类别**：查 §2 类别表，确定该文件属于哪一类（拿不准时看「覆盖内容」列）。
2. **取号**：取该类别的**下一起始号**（§2 表右列）；评审类先按 §1.4 确定对象标号，再从该对象的 `-01` 起。
3. **改名**：文件命名为 `<编号>_<原文件名>`。
4. **落盘**：把文件放到归属目录。
5. **登记**：在本表 §4 追加一行；若属评审类，同时更新 §5 专表。
6. **同步引用**：在**同一动作内**更新全工程引用（`grep -rI` 旧名 → 逐一替换），并在留痕（`11-过程文档/开发历史/DEV-*.md`）中记录。
