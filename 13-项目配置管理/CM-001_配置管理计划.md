## 0 摘要（一段话）

本工程是**生成合成类算法备案**项目，核心资产是**提示词模板 + 交付规范 + 合规资料 + 评审留痕**，
其价值几乎全部落在「**文件的状态与版本是否可追溯**」上——备案审查看的正是「你改过什么、谁看过、改完结果如何」。

因此本计划确立三条主原则：

| # | 原则 | 落地方式 |
| --- | --- | --- |
| 1 | **一切需追溯的东西都有编号** | `CM-002_文件取号表.md` 为全工程文件编号的**唯一登记处**；文件名即 `<编号>_<原名>` |
| 2 | **一切变更都有留痕** | `11-过程文档/开发历史/DEV-<YYYYMMDD>-<NNN>-<简述>.md`，**一动作一份、编号永不复用** |
| 3 | **一切对外交付都过机器门禁** | `validate_templates.py` / `validate_output.py` / `delivery/validate_pack.py` 三道脚本闸门，**人眼看不算数** |

## 1 引言

### 1.1 目的

对工程内**全部需要管理的配置项**建立统一标识、基线、变更控制、状态记录与审计机制（**四类分列见 §1.2**；原「现有 **326** 份文件」这一聚合数**已无法复现**，依「量化陈述必须标注测量口径」纪律改为指向 §1.2 分列，见 §13 V1.8），
使任意一份产物在任意时刻都能回答四个问题：

1. 它**当前是哪一版**？（标识与版本）
2. 它**改动过什么、为什么改**？（变更控制与留痕）
3. 它**被谁看过、意见处置到哪一步**？（评审状态）
4. 它**能不能交付**？（审计与门禁）

## 2 配置管理组织与职责

本工程为**小团队（算法作者 + 算法负责人 + 项目方）**结构，不设专职 CM 工程师，**角色兼任但职责分离**：

| 角色 | 人 | 配置管理职责 |
| --- | --- | --- |
| **配置管理员（CM）** | 算法作者 | 取号与登记（`CM-002`）、留痕（`DEV-*`）、版本控制操作（提交 / 推送）、审计执行 |
| **配置控制委员会（CCB，简化）** | 算法负责人 + 项目方 | 批准**基线变更**与**对外交付**；批准编号体系变更 |
| **配置项责任方** | 各文档归属人 | 对本配置项内容负责；接收评审意见并处置、出具复查记录 |
| **评审方（外部）** | AI 视频提示词导演 等 | 出意见、不改正文；按 `PROC-RELAY-001` 路径 B 委托 |
| **巡检机制（自动）** | 自动化任务 | 每 2 小时扫描留痕窗口，**只读**、不修改正文；无新增动作则不出产物 |

> ⚠️ **单人兼任的补偿机制**：因为「自己改自己审」风险高，本工程用**三道机器闸门**（§8）与**外部独立评审**（§6.4）替代人工复核。

## 4 配置标识与命名规则

### 4.1 标识规则

完整规则见 `CM-002` §1，摘要：

```
<类别码>-<三位流水号>            通用类别，例 TPL-013
REV-<对象标号>-<两位序号>        评审类，例 REV-SW-007-02
```

  非软件需求条目的对象取**其交付物编号**（《分镜提示词交付规范》→ `D-017`、`硬件级需求文档` → `D-014`）。

### 4.2 版本标识

| 配置项 | 版本字段位置 | 升版规则 |
| --- | --- | --- |
| 提示词模板 | `prompts/CFG-008_manifest.yaml` 的 `version` | **主版本** = 结构变更（含 `output` 字段增删）／**次版本** = 约束·示例／**修订号** = 文案 |
| 交付规范 | 文档头部「版本」 | 技术内容变更升次版本；仅编号/口径澄清亦须升版并写明技术影响 |
| 需求文档 | 文档头部「版本」 | 需求增删改即升版，并在 §10 变更记录留行 |
| 其余文档 | 文档头部「版本」 | 内容实质变更即升版 |
| **文件编号** | `CM-002` §4 | **与内容版本正交**：编号固定不变，版本随内容演进 |

> ⚠️ **「连带升版」不是惯例动作，而由契约规律决定**：**上游 `output` 即下游 `input` 契约**——
> 上游改了字段，下游才连带升版；上游未改字段则不连带升。该规律已由四次实证确认。

## 6 配置变更控制

### 6.1 变更分类

| 类别 | 定义 | 审批 | 例 |
| --- | --- | --- | --- |
| **A 类 · 基线变更** | 改动已基线化配置项的内容 | **CCB（算法负责人 + 项目方）** | 改模板 `output` 字段、改交付规范条款 |
| **B 类 · 一般变更** | 新增 / 修改未基线化配置项 | 配置项责任方 | 新增用例、补文档章节 |
| **C 类 · 标识变更** | 仅改名 / 改编号，内容不变 | **CM（算法作者）** | 本次全工程统一取号 |
| **D 类 · 纠错变更** | 修正事实性错误（笔误、失效引用、失实表述） | 配置项责任方 | 订正陈旧版本引用、修脚本误报 |

### 6.2 变更流程（七步，全部留痕）

```
① 提出 ──→ ② 影响分析 ──→ ③ 批准 ──→ ④ 实施 ──→ ⑤ 验证 ──→ ⑥ 留痕 ──→ ⑦ 登记
```

| 步 | 动作 | 落地要求 |
| --- | --- | --- |
| ① **提出** | 在 `PM-001_任务清单.md` 登记 `T-###`；缺陷类登记 `ISSUE-###` | 编号三位、永不复用；**不得无编号改动** |
| ② **影响分析** | 判定**上游 / 下游契约连带**（上游 `output` 即下游 `input`）；判定是否触及基线 | 触及基线 → 转 A 类报 CCB |
| ③ **批准** | A 类由 CCB；B/C/D 类由责任方 | 批准记录写入留痕 |
| ④ **实施** | 改动文件；**改名须同动作内同步全工程引用** | 引用同步是改名动作的一部分，不得跨动作补做 |
| ⑤ **验证** | 跑三道机器闸门（§8）；**新增校验判据必须构造越界样本**（负向验证纪律） | 「只跑通过样本」不算验证 |
| ⑥ **留痕** | 落 `11-过程文档/开发历史/DEV-<YYYYMMDD>-<NNN>-<简述>.md` | 一动作一份；**无证据不得标已完成** |
| ⑦ **登记** | 同步 `CM-002` §4 / `CFG-008_manifest.yaml` / `PM-001` §9 变更记录 / `PM-002` §五 | 台账**追加行**，不覆盖 |

### 6.3 冻结窗口

| 窗口 | 规则 |
| --- | --- |
| **对外交付前** | 该配置项及其上游进入**冻结**，只接受 D 类纠错变更 |
| **备案提交后** | 提交所用版本组**打标签冻结**；后续改动不得覆盖，只能新增版本 |

### 6.4 外部评审（配置项的独立验证）

按 `PROC-RELAY-001` 路径 B 执行，要点：

1. 我方起草**评审请求书**（`REV-<对象>-01`）；
2. **项目方本人**在另一独立会话中转发给专家（**中转由项目方承担**）；
3. 专家落盘意见（`REV-<对象>-02` 起）；
4. 我方逐条处置并出具**复查记录**（`REV-<对象>-0N`）；
5. **会话隔离为硬条款**（§4.2）：评审方须**新起会话**——否则该意见**降级使用**（如实留痕、不作独立背书、举证不引用）。
