# 需求管理规范

> 本目录是项目所有需求的**唯一登记处**。系统级、软件级、硬件级需求分层存放，主文档做总索引。

## 一、目录结构

```
00-需求\
├── README.md              本文件：需求管理规范与文档模板
├── REQ-006_需求文档.md            主需求登记（总索引，跨层汇总 + 待明确事项 + 变更记录）

├── 软件级需求\            软件级需求文档（SW-xxx）
```

**两级关系**：

| 文件 | 作用 | 粒度 |
| --- | --- | --- |
| `REQ-006_需求文档.md` | 总索引与项目级约定：背景、范围、结论、待明确事项、交付物、里程碑、变更记录 | 项目级，概览 |

> 新增需求时先在 `REQ-006_需求文档.md` 的汇总表中登记编号，再在对应分层目录下展开详细文档。

### 文档层级冲突裁决规则（2026-10-15 增设）

本目录四类文档对同一事项的表述若不一致，按下列优先级裁决，**不得各写各的**：

| 序 | 规则 | 说明 |
| --- | --- | --- |
| ① | **分层展开件 > 主登记** | `REQ-004` / `REQ-005` / `REQ-001` 是开发与测试的**唯一依据来源**；主登记 `REQ-006` 的项目级条目（`F-xxx` / `N-xxx`）是**概览与索引**。两者冲突时**一律以分层件为准**，主登记须**同批订正** |
| ② | **口径唯一定义处 > 引用处** | 测量口径只在**唯一定义处**定义（当前为 `REQ-005` §5），引用方**只引用、不重定义**，且引用**必须带版本号 + 条目号** |
| ③ | **同一要求多层承载时，指定唯一入口层** | 见 [§二 跨层承载三规则](#跨层承载三规则2026-10-15-增设rs--rw-待议-b)；责任始终落在入口层，不因重复登记而分散 |
| ④ | **判据底座只管体例、不裁内容** | 本文件（`README.md`）规定**字段、状态与判据形式**，不裁决**技术内容对错**——技术内容之争议由分层件自身修订解决 |

> **本规则的直接来源**：2026-10-15 三份独立评审意见（`REV-REQ-004-02` / `REV-REQ-005-02` / `REV-REQ-006-02`）共同暴露的缺陷族——主登记与分层件表述漂移（如导出格式 5 种、`D-013` 版本两处不一致）、跨文档引用不带版本、口径被多处旁引。

## 二、三层需求的划分

### 判断标准

| 层级 | 编号前缀 | 回答的问题 | 典型内容 |
| --- | --- | --- | --- |
| **系统级** | `SYS-` | 「系统要做什么、对谁做、受什么约束」 | 业务目标、用户角色、业务流程、系统边界、外部接口、合规约束、性能容量总体指标 |
| **软件级** | `SW-` | 「软件怎么实现这些能力」 | 功能模块、接口契约、数据模型、算法逻辑、异常处理、安全机制、非功能指标 |
| **硬件级** | `HW-` | 「跑起来需要什么物理资源」 | GPU/CPU/内存/存储/网络、机房与供电、终端设备、外设、部署形态 |

### 归属判断表（避免放错层）

| 需求描述 | 应归层 | 理由 |
| --- | --- | --- |
| 系统需支持四类文本合成任务 | 系统级 | 描述系统能力边界 |
| 单次同步合成响应时间 < 3s（P95） | 软件级 | 软件性能指标 |
| 需 1×24G 显存 GPU 支撑 7B 模型推理 | 硬件级 | 物理资源要求 |
| 需符合《深度合成管理规定》并完成算法备案 | 系统级 | 外部合规约束 |
| 生成内容需带显式与隐式标识 | 软件级 | 功能实现要求 |
| 硬盘需预留 300–500GB SSD | 硬件级 | 物理资源要求 |
| 租户之间数据必须隔离 | 软件级 | 软件安全机制 |
| 系统需支撑 3 个业务部门日常使用 | 系统级 | 用户与业务范围 |
| 需支持断电后 4 小时不断电运行 | 硬件级 | 物理保障要求 |

**判断口诀**：说「要什么能力/受什么约束」→ 系统级；说「怎么实现」→ 软件级；说「需要什么设备」→ 硬件级。

### 跨层承载三规则（2026-10-15 增设）

> **增设动因**：归属判断表只回答「一句话归哪一层」，**未回答「同一要求可否多层承载、哪一层是入口、责任归谁」**。本工程实际已采用「义务归系统层 / 机制归软件层 / 判据只在承载层定义」模式（如 `SYS-015` ↔ `SW-101`），但该模式**此前无判据可依**，导致跨层整段重复、追溯链单向、责任无处安放。

同一要求在多层都出现时**不视为重复登记**，但**必须同时满足三条**：

| 规则 | 要求 | 反例（禁止） |
| --- | --- | --- |
| **① 侧面分工** | 上层写**义务与指标**（做什么、达到什么）；下层写**机制与判据**（怎么实现、怎么测）。两层措辞**不得整段复制** | `SYS-015` 与 `SW-101` 复制同一段口径文字 |
| **② 判据唯一** | **测量口径只在唯一定义处定义**；另一层**只能引用**，且引用须带**版本 + 条目号** | `SYS-015` 同时引用 `REQ-005` §5 与 `HW-001` 验收③，形成两个口径源 |
| **③ 双向互指** | 上层条目的「关联」列须写出**下层承接编号**（或明示「无下层承接 + 原因」）；下层条目的「来源」列须写出**上位条目编号**。任一方向缺失即为**追溯断链** | `SYS-001` / `SYS-012` / `SYS-013` 未写承接编号；`SW-111` 来源错挂 `SYS-006` |

**责任分派**（三层的入口层）：

| 入口层 | 承担什么 | 判据落在哪一层 |
| --- | --- | --- |
| **系统级** | **义务与合规责任**（做什么、受什么约束、对谁负责） | 只登记指标，**引用**下层口径 |
| **软件级** | **实现机制与测量判据**（怎么实现、怎么测、达标值） | **测量口径唯一定义处** |
| **硬件级** | **物理资源与保障**（需要什么设备、什么环境） | 登记容量/算力测算与其限定条件 |

**孤儿要求自检**（每轮评审与每次新增需求必过）：

| 孤儿形态 | 判定 | 处置 |
| --- | --- | --- |
| ① 项目级 `F-xxx` / `N-xxx` 在三层无承接 | 需求在主登记存在、分层件无任何条目承载 | **补承接** 或 **显式排除**（写入 §2.2 不纳入本期，并注明理由） |
| ② 分层条目无上位来源 | 条目「来源」列写「架构约束」或空缺，且无理由说明 | **补挂上位条目** 或 **注明「无上位条目」及其理由**——**如实暴露、不强行挂靠** |
| ③ 上层条目无下层承接且未说明 | 「关联」列为空或只列同层 / 交付物 | **补承接编号** 或 **明示「无下层承接 + 原因」** |

## 三、编号规则

```
SYS-001   系统级需求，三位序号
SW-001    软件级需求，三位序号
HW-001    硬件级需求，三位序号
```

扩展规则：

| 场景 | 写法 | 示例 |
| --- | --- | --- |
| 同一需求下的子项 | 父编号 + `.n` | `SW-012.3` |
| 需求变更（不覆盖原条目） | 版本后缀 | `SW-012-v2` |
| 需求废弃 | 状态置 `已废弃`，保留原条目 | — |

**原则**：编号一经分配永不复用；需求废弃不删除，仅改状态。

## 四、需求条目必备字段

每条需求至少包含以下八项：

| 字段 | 说明 |
| --- | --- |
| 编号 | 唯一标识 |
| 需求名称 | 一句话概括 |
| 描述 | 具体、可验证的表述 |
| 来源 | 谁提出 / 依据什么（法规、业务、技术） |
| 优先级 | 高 / 中 / 低 |
| 验收标准 | 如何判定已满足（可量化优先） |
| 状态 | 待确认 / **内部确认** / 已确认 / 开发中 / 已完成 / 已废弃 |
| 关联 | 关联需求编号、交付物编号（D-xxx） |
| **测量方法** | **用什么方法测**（脚本化比对 / 压测采样 / 人工抽检 / 代码评审 / 监控统计 / 部署核查 / 安全检查 / 审计核查 / 配置切换 / 模板热更 / 备份演练） |
| **责任人** | **谁测**——一律写**角色**（算法作者 / 算法负责人 / 安全负责人 / 运维 / 测试），不写人名 |
| **验证时点** | **何时测**——须挂到里程碑或交付物（`D-xxx`）或任务（`T-xxx`） |

**「八项必备字段」与「验收三要素」的关系**：八项是**最小集**（条目成立的条件）；**测量方法 / 责任人 / 验证时点**是**验收标准的必备三要素**——一条验收标准若三者缺一，即为**不可判定的能力断言**（「能做什么」而非「做到什么程度算过、谁在什么时点用什么东西测」），须改写。

> ⚠️ **「口径只引用、不重定义」**：验收标准中引用测量口径时，**只写条目号 + 版本**（如「口径见 `REQ-005` V2.7 §5 `SW-101`」），**不得在本文档重新定义并发数值**——重定义即产生第二个口径源（本次评审 `RS-13` 的直接成因）。

**状态取值域说明（2026-10-14 增设，`RQ4-02` / `RQ5-03`）**：

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| 待确认 | 条目已成文，尚未经业务方过审 | — |
| **内部确认** | **业务方已过审、我方内部确认**——条目内容与验收标准已定，但**尚未经独立评审背书** | 业务方确认（本项目为 `SYS-Qn` 决策闭环） |
| 已确认 | **已经独立评审通过**，可作为正式基线 | ⚠️ **须独立评审通过**（外部独立会话出具意见并完成处置），**不得以「内部确认」直接改判** |
| 开发中 | 已开工实现 | 立项开工 |
| 已完成 | 实现完成且验收通过 | 验收通过 |
| 已废弃 | 编号保留、不再适用 | 决策废弃 |

> ⚠️ **「内部确认」与「已确认」是两个不同取值**，不可混用：仅当**独立评审闭环**后方可由「内部确认」改判「已确认」。此前条目直接写「已确认」属**越界取值**，已按本表订正（`REQ-004` V1.8、`REQ-005` V2.0；另 `REQ-004`/`REQ-005` 后续 V1.9/V2.1 为 `ISSUE-016`／`ISSUE-017` 决策落盘，状态口径不变）。
> ⚠️ **另有三条取值纪律**：① 状态须落在**本表取值域内**——「待开发」等业务侧口语**不在域内**（`REQ-005` V2.0 已把越界的「待开发」订正为「内部确认」/「开发中」）；② **「模板/资产建成」不等于「需求完成」**——功能需求的验收须以**服务化跑测**为准，仅资产已建者只能记「开发中」，**不得记「已完成」**；③ **状态取值不得加修饰后缀**（2026-10-15 增设）——须写取值域内的**裸取值**，如「内部确认」**不得**写成「内部确认（暂定值）」；确需附带限定时，把限定写进**描述或验收标准**，并在该条目内注明转正机制（触发条件 / 时点 / 批准角色 / 未达标处置）。本次评审 `RS-03` 即为该缺陷的实例。

**前置条件与「未达成」的登记位（2026-10-15 增设）**：

条目因**前置条件尚未满足**而当前不可达成时，**必须显式标注**，不得留白或以「已完成」掩盖。三种合法写法：

| 写法 | 用在哪 | 示例 |
| --- | --- | --- |
| **在验收标准内加注** | 能力条目本身标注 | `SW-001`「⚠️『状态可恢复』当前未达成：会话存储为内存实现，进程重启即丢失；待持久化接入后闭环」 |
| **设「实现现状 / 前置条件」列** | 功能需求表（见 §五.2 模板） | 「模板资产已建 / 服务化未开始」 |
| **登记进待明确台账** | 影响范围跨条目、需责任人与时点者 | 主登记 §7「未闭环台账」逐项登记状态、责任人角色、阻塞对象、是否有外部审核周期 |

> 三条纪律的共同点：**诚实标注的成本远低于事后被发现「文档声称与事实不符」的成本**。本工程已多次出现「模板建成被当作需求完成」的记录，故此处立为硬纪律。

## 五、文档模板

### 5.0 主登记文档模板（2026-10-15 增设）

> **增设动因**：`RQ-03` / `RQ-04` 的**根因**——判据底座此前只定义了系统级 / 软件级 / 硬件级三类模板，**主登记的项目级条目（`F-xxx` / `N-xxx`）无判据可依**。后果是该层 **31 条条目全无「来源」与「关联」**、§4 非功能条目**连状态列都没有**、§3 状态取值越界（「待开发」不在 §四 取值域内）。本节补齐后，**新增项目级条目一律按下列列结构**，不得再出现无判据格式。

#### 5.0.1 功能性项目级条目（`F-xxx`，主登记 §3）

| 列 | 必备 | 填法 |
| --- | --- | --- |
| 编号 | 是 | `F-xxx`，三位序号；**一经分配永不复用** |
| 需求 | 是 | 一句话**可验证**表述（不得写不可判定的能力断言） |
| 优先级 | 是 | 高 / 中 / 低 |
| 状态 | 是 | **§四 取值域内的裸取值**，不得加修饰后缀；原「待开发」等口语须回判为「内部确认」/「开发中」 |
| 验收标准 | 是 | 可判定；带数值者须写明**达标值**；**方法 / 责任人 / 时点三要素若本层不定义，须回指分层件的检查方式**（口径只引用、不重定义） |
| 来源 | 是 | **四类写死**：① 法规条号 / 国标号 ② 系统级 `SYS-xxx` 或决策记录 `SYS-Qn` ③ 本文档 §5 技术选型 / 架构约束 ④ 本文档其他章节号 |
| 关联 | 是 | 层级条目编号 / 交付物 `D-xxx` / 同层条目 / 依据 |
| **落地于（层级条目）** | 是 | **最小映射**（见 5.0.3）——本条在三层展开件中的承接条目；无承接须填「**无下层承接**」并注明理由 |

#### 5.0.2 非功能性项目级条目（`N-xxx`，主登记 §4）

| 编号 | 类别 | 需求 | 目标值 | 口径引用 | 状态 | 优先级 | 来源 | 关联 | 落地于（层级条目） |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

- **「口径引用」列**：性能 / 可用性 / 容量类目标的**测量口径唯一定义处为 `REQ-005` §5**；本列**只写条目号 + 版本**（如「`REQ-005` V2.7 §5 `SW-101`」），**不得在本层重定义并发数值**。
- **「目标值」列**：可写项目级目标（如「≥99%」），但**须在同一行注明其为暂定值或实测校准值**，并给出转正机制（触发条件 / 时点 / 批准角色 / 未达标处置）。
- 其余列填法同 5.0.1。

#### 5.0.3 最小映射（待议 A 的落地形态）

**只给 `F-xxx` / `N-xxx` 增加「落地于」一列**，指向其在三层展开件中的承接条目；**不建全量对照表**。三类处置口径：

| 情形 | 「落地于」填法 |
| --- | --- |
| 有明确承接 | 填层级条目编号（可多个） |
| 本期不做 | 填「**本期不做**」并同步写入主登记 §2.2「暂不纳入」 |
| 应做但暂缺承接 | 填「**待补承接**」并登记进待明确台账，**不得留空** |

> **为什么用最小映射而非全量对照**：全量对照需覆盖 `F-`/`N-` 与三层共 67 条的双向映射，维护成本高、易陈旧；最小映射只解决「主登记条目落到哪一层」这一个真问题，**而反向追溯（层级条目回指上位）由各分层件的「来源」列承担**。

## 六、维护流程

```
① 需求提出
   → 在 REQ-006_需求文档.md 登记编号与摘要
        ↓
② 分层展开

        ↓

   → 优先级与验收标准确认后，状态改为「内部确认」
   → 经【独立评审】通过并完成意见处置后，方可改为「已确认」
        ↓
④ 变更管理
   → 变更提升版本号，记录到 REQ-006_需求文档.md 的「变更记录」表
   → 同步更新「修订记录」表
```

**约定**：

1. 需求变更只追加、不删除历史记录；
2. 每层文档变更需同步更新 `REQ-006_需求文档.md` 的汇总表；
3. 涉及备案材料的需求变更，需同步检查 `02-备案申报` 下的文档是否受影响。
4. **孤儿要求自检**（2026-10-15 增设）：每次新增需求、或每轮评审收口前，须逐条过 §二 的**孤儿要求自检三形态**——① 项目级条目在三层无承接；② 分层条目无上位来源；③ 上层条目无下层承接且未说明。命中即**补承接或显式排除**，不得留待下一轮。
5. **验收三要素齐备**（2026-10-15 增设）：任一条目的验收标准若缺**测量方法 / 责任人 / 验证时点**，即为**不可判定的能力断言**，不得进入「已确认」态。「已确认」的前置条件 = **八项必备字段齐 ＋ 验收三要素齐 ＋ 独立评审通过且意见已处置**。
6. **口径单源**（2026-10-15 增设）：同一指标只允许**一个口径定义处**；其他文档引用时**必须带版本 + 条目号**。发现第二处定义即按 [§一 冲突裁决规则 ②](#文档层级冲突裁决规则2026-10-15-增设) 处理。
