# 提示词模板 · 样例与评测

> 本目录存放每个模板的「输入 → 输出 → 评测结论」用例，是备案材料中**二次开发痕迹**的直接证据。
> 建立 2026-10-13。

---

## 一、本目录解决什么问题

模板本体（`../templates/*.yaml`）只能证明「写了什么」，**证明不了「验证过」**。

备案审查关注的是：这套提示词是否经过**自主设计—实测—迭代**，而不是从开源库复制。本目录的三段式记录（输入／输出／评测）就是这条证据链。

| 记录项 | 证明什么 |
| --- | --- |
| 输入 | 面对什么业务场景 |
| 输出 | 模板实际产出（或目标产出） |
| 评测结论 | 逐条对照该需求的验收标准，结论可核查 |

---

## 二、命名与文件约定

| 项 | 约定 |
| --- | --- |
| 文件名 | `<模板id去版本>-case<两位序号>.md`，如 `synopsis-case01.md` |
| 一份文件 | 只记一个用例，不合并 |
| 用例来源 | 优先用**真实业务场景**（脱敏后）；无真实场景时用构造用例，但须在文件内注明 |
| 采样参数 | 必须记录（temperature / max_tokens），否则结果不可复现 |

## 三、必备结构

每个样例文件必须含以下五节，缺一不可：

1. **用例信息** —— 用例编号、对应需求编号（SW-xxx）、模板 id 与 version、用例来源
2. **输入** —— 变量的实际取值，按模板 `variables` 逐项列出
3. **输出** —— 模型实际输出；尚无实测时放**目标输出样例**并标「待回填」
4. **评测结论** —— 逐条对照该需求的「验收标准」字段，给通过／不通过与理由
5. **验证状态** —— `已实测` / `未验证` / `已实测待复核`

> **纪律**：未跑过模型的，验证状态一律写 **未验证**。项目规范明确「无验证证据不得标已完成」——把「人工构造的期望输出」冒充成「实测输出」是留痕造假。

## 四、评测的执行方式

| 层 | 手段 | 可自动化的部分 |
| --- | --- | --- |
| 结构合规 | JSON Schema 校验（`delivery/validate_pack.py` 同源思路） | ✅ 全自动 |
| 覆盖完整性 | `covered_points` 与输入要点逐条比对 | ✅ 可脚本化 |
| 无编造 | 抽取输出中所有专名 → 回溯输入，找不到来源即失败 | ✅ 可脚本化 |
| 内容质量 | 人工阅读（叙事是否成立、文风是否合适） | ❌ 须人工 |

三层里的前两层必须**脚本产出结论**，不得只写「人工看过没问题」——这是本项目在镜头语言质量门上已经确立的口径（「靠人记着做的事，等于没人做」）。
