# 提示词模板 · 样例与评测

> 本目录存放每个模板的「输入 → 输出 → 评测结论」用例，是备案材料中**二次开发痕迹**的直接证据。
> 建立 2026-10-13。

---

## 一、本目录解决什么问题

模板本体（`../templates/*.yaml`）只能证明「写了什么」，**证明不了「验证过」**。

备案审查关注的是：这套提示词是否经过**自主设计—实测—迭代**，而不是从开源库复制。本目录的三段式记录（输入／输出／评测）就是这条证据链。

| 记录项 | 证明什么 |
| --- | --- |
| 输入 | 面对什么业务场景 |
| 输出 | 模板实际产出（或目标产出） |
| 评测结论 | 逐条对照该需求的验收标准，结论可核查 |

---

## 二、命名与文件约定

| 项 | 约定 |
| --- | --- |
| 文件名 | `<模板id去版本>-case<两位序号>.md`，如 `CASE-004_synopsis-case01.md` |
| 一份文件 | 只记一个用例，不合并 |
| 用例来源 | 优先用**真实业务场景**（脱敏后）；无真实场景时用构造用例，但须在文件内注明 |
| 采样参数 | 必须记录（temperature / max_tokens），否则结果不可复现 |

## 三、必备结构

每个样例文件必须含以下五节，缺一不可：

1. **用例信息** —— 用例编号、对应需求编号（SW-xxx）、模板 id 与 version、用例来源
2. **输入** —— 变量的实际取值，按模板 `variables` 逐项列出
3. **输出** —— 模型实际输出；尚无实测时放**目标输出样例**并标「待回填」
4. **评测结论** —— 逐条对照该需求的「验收标准」字段，给通过／不通过与理由
5. **验证状态** —— `已实测` / `未验证` / `已实测待复核`

> **纪律**：未跑过模型的，验证状态一律写 **未验证**。项目规范明确「无验证证据不得标已完成」——把「人工构造的期望输出」冒充成「实测输出」是留痕造假。

> **一个用例可以有多个 JSON 块**（2026-10-14 随 SW-008 补充）：`validate_output.py` 按**形态**而非「第几块」分派规则，故同一文件里可以放「上游摘录 + 本层产物」（如 `CASE-001`），也可以放「**两个并列的产物**」。
> 后者的首例是 **`CASE-005_revise-case01.md`（SW-008 `revise_v1`）**——本层产出**两件独立产物**：
> ① **交付包**（形态 `pack`，走 R26~R36）；② **缺口台账**（形态 `ledger`，走 R37）。⚠️ 台账**不在交付包内**，
> 规范 §3.1 顶层八段无台账段；它不是「用例的附件」，而是与交付包**同批落盘的交付物** `<pack_id>.unspecified.json`。
> 因此本目录的用例**不是**「一个文件＝一个 JSON 块」，判定口径是**形态齐备**而非块数。
> **第二个例子是 `CASE-006_modify-case01.md`（SW-002）**——同一文件放**变更说明 `modify`（管「改了什么」）与漂移报告 `drift_report`（管「有没有漂移」）**两件产物；二者**形态与判据各不相同**（R38／R39），故「按形态分派」这一口径在此再次被验证。
> **其姊妹用例 `CASE-007_modify-pack-case01.md`（2026-10-14 依 `REV-SW-002-02` §4-C ③ 补）** 是 `target_stage=pack` 的**正极样本**——`SW-002` 的两个 `pack` 专属问题（**溯源追加可落地**、**字段→正文牵连**）此前被 `CASE-006` 的 `storyboard` 选型**掩盖**，无样本可撞。

## 四、评测的执行方式

| 层 | 手段 | 可自动化的部分 |
| --- | --- | --- |
| 结构合规 | JSON Schema 校验（`delivery/validate_pack.py` 同源思路） | ✅ 全自动 |
| 覆盖完整性 | `covered_points` 与输入要点逐条比对 | ✅ 可脚本化 |
| 无编造 | 抽取输出中所有专名 → 回溯输入，找不到来源即失败 | ✅ 可脚本化 |
| **缺口交接**（2026-10-13 新增） | 核查「下游必填字段的缺失是否被标记」：凡字段值为「未指定」者，须在 `unspecified` 中有对应条目；**视觉锚点类**（角色外观／年龄段、场景空间与时相、风格线索、道具外观）的缺失须单列且 `fill_stage=script`；**剧本层起，「待客户确认」类缺口的 `owner` 必须为『客户』且 `fill_stage` 回归本层 `script`**（下游无人能补，见 R21） | ✅ 可脚本化 |
| **外观锚不重述**（2026-10-13 新增，SW-006 起） | 逐镜语义字段（`action.*` / `shot_language.composition\|axis\|result` / `camera.from\|to` / `notes`）**不得出现上游 `appearance_lock_zh` 的外观特征词**（颜色／材质／饰件／磨损／款式）——承接 `action` 里的**动作对象**可以，写外观**特征词**不可以。**刻意不含** `dialogue` / `sfx` / `lighting`（台词与光声描述可合法提到景物） | ✅ 全自动（`validate_output.py` **R23**，需 `--script`） |
| **道具覆盖**（同上） | 某场 `props_present` 非空 → 该场**至少一镜**须把它标进 `prop_refs`；整场漏标即「**剧本说它在场、分镜一镜都没拍到**」 | ✅ 全自动（**R24**，需 `--script`） |
| **独立台账形态与责任阶段**（2026-10-14 新增，SW-008 起） | `revise` 层无上游，台账必须**另行产出**——查：① 顶层是否**只有** `unspecified`（多键＝混装）？② 每条是否**恰好** 7 字段？③ `blocking` 是否为**布尔**（字符串 `"false"` 是真值）？④ `fill_stage` 是否**一律** `revise`（写成别值＝把责任推给本路径上没跑过的层）？ | ✅ 全自动（`validate_output.py` **R37**） |
| **对话式修改两形态与内在自洽**（2026-10-14 新增，SW-002 起） | 查：① **变更说明**顶层是否**恰好** 6 键、每条变更是否**恰好** 8 字段？② `op_id` 是否形如 `MOD-01` 且**唯一不跳号**、`target_path` 能否在 `artifact` 上**解析成功**（`insert` 除外）？③ `blocking` 是否为**布尔**（字符串 `"false"` 是**真值**）？④ 「需要澄清」与「有变更」是否**互斥**（`needed=true` 时 `change_log` 必须为空、`questions` 1~3 条）？⑤ **漂移报告**顶层是否**恰好** 5 键（**含 `focus` 缩范围声明**）、**是否含 `category=anchor` 条目**（⚠️ `focus` ≠ `全篇` 时该条目的 `action` **必须写明「本次未扫锚」**——写全查式声明即失败）、`summary` 三数是否与 `findings` **复算一致**、`location_b` 是否形如 `a.b[0].c`（**禁 `[*]`／`/`／空串／自然语言**，锚类条目不在此列）？ | ✅ 全自动（`validate_output.py` **R38**／**R39**） |
| **承继守恒**（2026-10-13 新增，SW-007 起） | 交付包**不得改动任何导演决策**：`shot_id`／镜序／镜数／逐镜 `duration_ms` 与上游分镜**逐项相同**。SW-007 是编译表达层，改一个秒数就改了一个导演决策 | ✅ 全自动（**R31**，需 `--storyboard`） |
| **提示词正文不复述外观**（同上） | `prompt_zh`／`prompt_en` 正文不得复述 `characters[].appearance_lock_*`——正文写的是「这一镜在发生什么」，不是「这个人长什么样」 | ✅ 全自动（**R28**） |
| **提示词正文卫生**（同上） | ① 无模型参数指令（`--ar`／`--v` 等，参数走结构化字段）；② 无负向残留（负向意图走 `negative_global`／`negative_prompt` 或转写为正向约束句）；③ **风格锚点封闭**（正文不得出现 `style_anchors` 之外的风格词） | ✅ 全自动（**R29**） |
| **八维双落地**（2026-10-13 新增，SW-007 起） | 八维（景别/运镜/角度/光学/构图/轴线/光线/画面结果）每个维度须**同时** ① 有字段承载 ② 写进 `prompt_*` 正文——模型读到的是文本，不是字段。⚠️ 与规范 §3.7.6 的 40–120 字长度建议**存在张力**（长镜实测 150–200 字），已列入评审待议项 | ⚠️ 逐维人工核对（有核对表） |
| **镜头语言质量门**（2026-10-13 新增，SW-006 起） | 11 项量化阈值（运镜/景别覆盖 100%、静止镜 ≤40%、运镜类型数 ≥`min(5,max(2,⌈镜数/4⌉))`、单一运镜 ≤35%、角度 ≥40%、光学 ≥30%、构图 ≥50%、轴线 ≥30%、光线 ≥40%、画面结果 ≥60%）；**整片与逐生成单元各判一次**。阈值与容差算法直接引用 `audit_shots.py` 的 `GATE` | ✅ 全自动（`validate_output.py` R19） |
| 内容质量 | 人工阅读（叙事是否成立、文风是否合适） | ❌ 须人工 |

> ⚠️ **质量门的两个层次不要混**：`validate_output.py` 判的是**结构化字段是否有值**（SW-006 的产物）；
> `audit_shots.py` 判的是**适配投喂文本**（SW-007 的产物）。两者对象不同——上游判定通过**不等于**下游文本判定通过，
> SW-007 完成后必须对文本再跑一次（规范 §4.8）。

三层里的前两层必须**脚本产出结论**，不得只写「人工看过没问题」——这是本项目在镜头语言质量门上已经确立的口径（「靠人记着做的事，等于没人做」）。
