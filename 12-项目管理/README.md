# 项目管理

> 本目录存放本项目**跨模块的任务编排与排期**：所有可预见、可规划的任务在此登记，形成**唯一事实来源**（Single Source of Truth），并随工程推进滚动维护。
>
> 建立 2026-10-13

---

## 一、定位与分工

本工程此前已有三处「进度类」信息，三者职责不同，**互不替代**：

| 位置 | 回答的问题 | 更新时机 | 性质 |
| --- | --- | --- | --- |
| `00-需求/REQ-006_需求文档.md` §8 §9 | **交付物是否完成**、**里程碑处在哪一阶段** | 交付物状态变化时 | 结果台账 |
| `11-过程文档/开发历史/` | **过去发生了什么**（每 2 小时巡检留痕） | 动作发生后 | 事实留痕（只读回溯） |
| **本目录** | **接下来做什么、谁做、何时做**（`PM-001` 账本 / `PM-002` 周视图 / `PM-003` 日视图） | **每周**滚动复审（`PM-002`）＋ **每个工作日**收尾日报（`PM-003`） | 计划（前瞻）＋ 当日对账 |

一句话：**开发历史向后看，任务清单向前看，需求文档是两者共同的锚。**

## 三、状态图例

### 任务状态

| 状态 | 含义 |
| --- | --- |
| ⬜ 待开始 | 已登记，尚未启动，前置依赖已满足或即将满足 |
| 🟦 进行中 | 已启动，本周在推进 |
| 🟨 受阻 | 因前置依赖、外部输入或待决策事项而暂停 |
| 🟩 已完成 | 已产出并经**验证**（有证据：文件路径 / 提交哈希 / 命令输出） |
| ⬛ 已取消 | 不再执行（保留编号不复用，注明原因） |

### 优先级

| 级别 | 含义 |
| --- | --- |
| **P0** | 关键路径：不做则备案无法提交 |
| **P1** | 重要：影响质量或合规完整性，但不阻断提交 |
| **P2** | 增强项：可在备案后迭代 |
| **P3** | 扩展项（如 LoRA 微调、文生视频）：本期可不做 |

## 四、维护规范

1. **编号规则**：任务编号 `T-<三位流水>`（如 `T-001`），**一经分配永不复用**；任务取消时保留编号、状态改 ⬛ 并注明原因。新任务取当前最大编号 +1，按分区插入。
2. **一次一源**：任务只在 `PM-001_任务清单.md` 登记；`PM-002_日程表.md` **只引用编号**，不重复描述任务内容，避免两处描述不一致。
3. **滚动复审节奏**：每周一上午复审一次 ——
   ① 把上周完成项按证据改 🟩；
   ② 把新识别的任务补登记；
   ③ 重排未来两周的日程；
   ④ 在 `PM-001_任务清单.md` §7 变更记录追加一行。
   日常有变化可随时改，不必等周一。
4. **状态与证据绑定**（沿用开发历史的硬规则）：**没有验证证据不得标 🟩 已完成**，只能标 🟦 进行中或 🟨 受阻。证据 = 文件路径 / 提交哈希 / 命令输出摘要。
5. **不预测未拍板的事**：需要人工输入才能确定的任务（GPU 型号、责任人名单等）放进 §5「待决策与待输入」，**不排入日程表**；决策后转正。
6. **与交付物清单锚定**：每项任务必须写「归属交付物」（`D-xxx` 或 `SYS/SW/HW-xxx`），治理类任务标注「—」。反之，`REQ-006_需求文档.md` §8 中状态为 ⏳/🟡 的交付物，**在任务清单里必须有对应任务**。这条是双向校验。
7. **可调整**：所有预估工时与周次均为**当前口径的估算**，随实测校准；排期改变时更新 `PM-002_日程表.md` 并记变更。
8. **日报节奏**：`PM-003_工作日报与次日计划.md` 于**每个工作日收尾**追加一节（倒序，最新在上）；其 §3「ISSUE 遗留总览」随日报滚动更新 —— ⚠️ **新增或闭环 ISSUE，一律先改 `PM-001` §8，再回填 `PM-003`**，**顺序不可颠倒**（`PM-003` 不是事实来源）。

## 五、脱敏纪律

本目录随仓库提交（`main` = 对外脱敏版），文档中：

- **不得出现真实企业名与人名**，一律使用占位符 `{{PROVIDER_NAME}}`（备案主体）、`{{ALGO_OWNER}}`（算法负责人）、`{{ALGO_AUTHOR}}`（算法作者）；人员一律写**角色**（算法负责人 / 算法作者 / 安全负责人 / 运维）。
- **受控类**（涉政、涉民族）任务只记「受控资产计数变化」，不落内容明文。
