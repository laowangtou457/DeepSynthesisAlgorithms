## 一、为什么必须是「人工」台账

工程里有两类「看起来像证据」的东西，**都不能**当人工核对记录：

1. **模型自述**——让模型在产物里写「已人工核对通过」，本质是「让被审对象自己出具无犯罪证明」，属假合规。代码层已硬性禁止：`_load_human_review()` 只读人工录入的台账文件，**不读任何模型产物字段**。
2. **自检项的 `pass`**——自检第 18 项是**回读台账**得出，台账为空时它必须 `fail`。若把它改成硬编码 `pass`，就是把「没检」显示成「检过了」。

因此台账缺失时的行为是**如实阻断**：自检第 18 项 `fail` ＋ 清单判据 `human_review.missing` **BLOCK**，正式包拒付（HTTP 422）。

## 二、台账形态与字段

```json
{
  "records": [
    {
      "pack_id": "FR-PK-20261111-A1B2C3D4",
      "no": 18,
      "item": "角色一致性 / 跨镜连续性人工核对",
      "result": "pass",
      "checked_at": "2026-11-11T15:20:00+08:00",
      "operator": "{{核对人}}",
      "detail": "15 镜逐镜对比上游剧本；主角发型/服装/场景光位一致；未发现跨镜断裂"
    }
  ]
}
```

| 字段 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- |
| `pack_id` | ✅ | 与交付包编号**逐字符一致** | 台账按它过滤；写错等于没填 |
| `no` | ✅ | 固定 `18` | §8.3 第 18 项编号 |
| `item` | ✅ | 非空 | 核对项名称，照抄上文即可 |
| `result` | ✅ | `pass`／`warn`／`fail` 三值 | `fail` ⇒ 该包不得交付；`warn` ⇒ 可交付但进自检 `warn` |
| `checked_at` | ✅ | ISO 8601 带时区 | 核对**完成**时刻，不是计划时刻 |
| `operator` | ✅ | 非空 | 核对人；**真名只落私密区台账**，入库文件写 `{{核对人}}` |
| `detail` | 建议 | 一句话 | 写了核对了什么、依据是什么；审核问询时这是最有说服力的部分 |

> 一个包可以有多条记录（如「角色一致性」「跨镜连续性」分别核对）。多条时**任一条 `fail` ⇒ 该包判 fail**。

## 三、怎么填（三步）

1. **复制模板到私密区**：`SEC-022_人工核对台账-模板.json` → `_私密实值/human_review_ledger.json`（只需做一次，之后一直用它累加）。
2. **加一条记录**：拿交付包目录名（即 `pack_id`）＋ 核对结论，按上表补 7 个字段。**不要**照抄模板里 `_example` 的 `pack_id`——那个是示例，照抄会造成「假命中」。
3. **自查**：跑 `python 03-工程代码/tools/check_human_review.py`，全部 `OK` 才算填对；再用 `--pack-id <编号>` 确认目标包已齐备。

配置：`03-工程代码/.env` 里 `APP_HUMAN_REVIEW_LEDGER` 指向该台账文件绝对路径（已配好，指向 `_私密实值/human_review_ledger.json`）。留空或路径不存在 ⇒ 视为「未做人工核对」，门禁如实阻断。

## 四、谁能填（独立性）

- 应由**内容/交付审核责任人**填写，不建议由生成本身的人自签（`SEC-007`「操作人≠复核人」同理）。
- 本项目八类制度责任人**由同一人兼任**（小团队实际，法规不禁止）。但审核问询常问「如何保证审核独立性」，**人工核对台账是仅有的、可留下异人痕迹的环节**：若条件允许，让另一名员工做核对并在 `operator` 署名，风险显著下降。
- 台账**不设删除**：写错时追加一条更正记录（`detail` 写「更正上条，原因…」），保留轨迹。

## 五、与截图举证的关系

官方第 8 项要求「交付四件套」可举证。台账是**数据证据**，截图是**形态证据**，两者互补：

- 台账 → 证明「有人核对过、结论是什么」
- 截图 → 证明「交付包里真的有标识、清单里真的有实值」

截图要截哪三张、怎么跑出交付包，见 `12-项目管理/PM-005_真机留证操作指引.md`。
