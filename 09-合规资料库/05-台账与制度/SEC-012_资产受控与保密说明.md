## 三、受控区存储要求

| 要求 | 说明 |
| --- | --- |
| **物理/逻辑隔离** | 受控资产存于独立目录或独立存储，**不纳入工程代码仓库版本控制**（版本控制方案见 **§三之二**） |
| **访问控制** | 仅授权人员可访问；建议加密存储 |
| **访问留痕** | 每次读取/修改记录时间、人员、用途 |

| **禁止外发** | 不得通过聊天工具、邮件、云盘随意传递 |
| **销毁管理** | 过期或作废的受控资产须登记后销毁，不得直接删除 |

> 建议目录命名（与 `../06-构建工具/init_controlled.py` 的默认输出一致）：`<受控区>/lexicon_controlled/`、`<受控区>/bank_controlled/`、`<受控区>/refuse_controlled/`

> `init_controlled.py --init` 会按上述命名生成骨架与 `README.md`（含存放要求与格式示例）。
> **受控区默认落在工程根目录的 `_受控区/`**——实施时须确认该目录**未纳入版本控制**（工作区 `.gitignore` 应包含该项），或改为指向独立存储路径。

## 三之二、受控区的版本控制方案（Git / SVN 怎么选）

> **本节回答一个具体问题**：受控区要不要用 SVN 建版本库？

### 3.1 先看现状（2026-10-12 实测）

| 项 | 实测结果 |
| --- | --- |
| 工程根 `E:\深度合成算法工程材料\.git` | **不存在** |
| 工程根 `.svn` | **不存在** |
| 工程根 `.gitignore` | 原本**不存在**（本次已建立） |
| 结论 | **整个工程目前没有任何版本控制** |

> ⚠️ **这本身就是一个隐患**：工程根**没有 `.gitignore`**。
> 一旦有人执行 `git init && git add -A && git commit`，`_受控区/` 会被**整体入库**，
> 且 **Git 无法保证历史被彻底擦除**。
>
> **本次已在工程根建立 `.gitignore`**（详见工程根 `.gitignore` 文件），其中
> `_受控区/` 与 `**/_受控区/` 已列为忽略项。这是**优先级最高的一道兜底**，请勿删除。
>
> **若将来初始化版本库，顺序必须是**：
> `git init` → **先提交 `.gitignore`** → 再 add 其它内容。
> 顺序反了，第一次 `git add -A` 就会把受控区扫进去。

### 3.2 结论（先给答案）

| 问题 | 结论 |
| --- | --- |
| 受控区**要不要**版本控制？ | **不强制**。GB/T 45654 要求的是「资产**真实存在**且**可核查**」，**未要求**受控内容进版本库 |
| 若不做版本控制，怎么做？ | **方案 A（推荐）**：受控区 + 定期加密归档（带哈希清单）+ 台账登记 |
| 若组织制度强制版本化，用 SVN 还是 Git？ | **用 SVN 独立仓库**（方案 B）。理由见下表 |
| 能不能放进工程文档的同一个库？ | **绝对不能**。无论 SVN 还是 Git，一律独立库、独立账号、独立权限 |

### 3.3 Git 与 SVN 对受控资产的适用性对比

| 维度 | Git | SVN | 对受控资产谁更合适 |
| --- | --- | --- | --- |
| 架构 | 分布式 | 集中式 | **SVN**——内容只在服务端，客户端拿到什么由服务端决定 |
| **泄漏面** | `clone` = **全量历史落到本地**；任何有读权限的人一次 clone 即获得全部内容 | 支持**稀疏检出**，可只 checkout 需要的子目录 | **SVN** |
| **权限粒度** | 原生**无路径级读权限**（读权限是仓库整体；细粒度需 Gitolite/Gitea 等额外组件） | 原生 **`authz` 支持路径级读写权限** | **SVN** |
| 防并发误改 | 靠分支/PR 流程 | **`svn:needs-lock`** 文件锁，适合"同一文件不许两人同时改" | **SVN** |
| 历史擦除 | 历史几乎**无法真正删除**（需 `filter-repo` 重写并强推，且已有克隆副本仍可能残留） | 服务端可删，但客户端工作副本仍有残留 | 都不彻底——**所以最好从未入库** |
| 审计能力 | 提交人、时间、diff 完整 | 提交人、时间、diff 完整 | 持平 |
| 部署成本 | 轻，`git init` 即得 | 需自建服务端（VisualSVN Server / `svnserve`） | Git 更轻，但这不是受控场景的决策因素 |

> **一句话**：受控资产的核心诉求是「**最小可见范围**」与「**防误改**」。
> 这两点上 **SVN 的路径级 ACL + 稀疏检出 + needs-lock 明确优于 Git 的分布式模型**。
> Git 的"轻"在这里不是优点——**它的 clone 即全量导出，恰恰是受控场景最想避免的**。

### 3.4 三种方案（按推荐度排序）

#### 方案 A｜不纳入版本控制（★ 推荐）

| 项 | 做法 |
| --- | --- |
| 内容管理 | 受控区目录 + **定期加密归档**：`_受控区-YYYYMMDD.7z`（AES 加密），存**独立介质**（离线硬盘 / 加密盘） |
| 完整性 | 归档时生成 **SHA-256 清单**（`sha256sum > _受控区-YYYYMMDD.sha256`） |
| 留痕 | `SEC-009_受控资产台账.md` §四 登记：归档日期、文件名、哈希、保管人 |
| 复查 | 每季度随机抽 1 类文件核对哈希，结果记入台账 |
| 优点 | 无泄漏面、无历史遗留、无服务端依赖；**完全满足国标「可核查」要求** |
| 代价 | 无逐行历史（但受控资产的"过程可核查"靠台账而非 diff 达成） |

#### 方案 B｜SVN 独立仓库（组织强制版本化时）

| 项 | 做法 |
| --- | --- |
| 服务端 | **自建**（VisualSVN Server 或 `svnserve`），**不接公网**，仅内网受控网段可达 |
| 库位置 | **独立仓库**，与工程文档**不同库、不同账号** |
| 权限 | `authz` 路径级：仅安全负责人（rw）与复核人（r）；其余人**无任何权限** |
| 防误改 | 对受控文件设 `svn:needs-lock`，编辑前必须 `svn lock` |
| 客户端 | **只 checkout 需要的子目录**（稀疏检出），禁止整库检出 |
| 命令示例 | `svn propset svn:needs-lock yes lexicon_controlled/A1-05.txt`<br>`svn co --depth immediates <repo>/lexicon_controlled` |

#### 方案 C｜Git 独立私有裸库（团队只有 Git 能力时）

| 项 | 做法 |
| --- | --- |
| 库位置 | **裸库放受控机器**，**不走 GitHub / Gitee / 云效等任何公有平台** |
| 工作副本 | **仅受控机器持有**；**禁止在工程师个人电脑上 `clone`** |
| 关键认知 | **一次 `clone` 就等于全量导出一份受控资产** → 必须纳入 §三 的「导出审批」流程 |
| 加固 | `git config core.hooksPath` 挂 pre-commit 钩子，检出内容含受控路径即阻断 |

### 3.5 无论选哪种，这 5 条必须全部做到

| # | 硬措施 | 检查方式 |
| --- | --- | --- |
| 1 | 工程库 `.gitignore` 必须含 `_受控区/` 与 `**/_受控区/` | `git check-ignore -v _受控区` 应输出匹配行 |
| 2 | 受控库与工程库**不同库、不同账号、不同权限** | 权限清单（须留存） |
| 3 | **禁止**推送任何公有平台 | 仓库设置截图 / 服务端 ACL |
| 4 | **提交信息（commit message）不得含受控内容**——提交信息本身也是受控资产 | 提交前自查；钩子拦"敏感路径+内容" |
| 5 | 每季度执行一次**泄漏排查** | 见 3.6 |

### 3.6 季度泄漏排查命令

```bash
cd <工程根>

# ① 忽略规则是否生效（应输出 _受控区/）
git check-ignore -v _受控区

# ② 受控区是否曾被加入过版本库（应无输出）
git log --all --diff-filter=A -- '_受控区/*'

# ③ 全历史对象中是否含受控路径（应无输出）
git rev-list --objects --all | grep -i '受控'

# ④ 未忽略的文件里是否混入受控目录（应无输出）
git status --porcelain --ignored=no | grep -i '受控'

# SVN 场景（应显示 '?' 或 'I'，不应是 'A'）
svn status --no-ignore _受控区
```

### 3.7 若已误入库的处置

| 情形 | 处置 |
| --- | --- |
| 尚未提交 | 加入 `.gitignore` 即可（本文件已建） |
| 已提交、未推送 | `git rm -r --cached _受控区` + 提交。**注意：文件仍在本地磁盘，只是移出版本控制** |
| 已推送到**内部库** | ① 立即通报安全负责人；② 用 `git filter-repo` 重写历史并强推；③ **通知所有曾克隆过的人删除本地副本**；④ 按本文件 §六 登记事件 |
| 已推送到**公有平台** | 按泄露应急预案处理：立即转私有/删除仓库 → 评估影响范围 → 上报。**涉政内容外泄须同时评估法律后果** |

> ⚠️ **Git 不能保证历史被彻底擦除**（重写历史后，他人已有的克隆副本仍可能残留）。
> **唯一的可靠做法是：让受控资产从未进入版本库。** 这就是方案 A 被列为首选的根本原因。

## 五、对评估方的可核查性

受控不等于不可核查。申报时应能提供：

| 提供物 | 说明 | 本库对应实体 |
| --- | --- | --- |
| 受控资产台账 | 编号、类别、条数、更新日期、操作人/复核人（**不含内容**） | `05-台账与制度/SEC-009_受控资产台账.md` |
| 受控类规模计数（机读） | 供自动核验的条数文件，可由脚本重算 | `05-台账与制度/controlled_assets.json` |
| 入库流程与工具 | 说明受控区如何建立、计数如何回填 | `06-构建工具/init_controlled.py`（`--init` / `--sync`） |
| 抽样展示 | 在监管方要求的受控环境下，可现场抽样展示内容 | `<受控区>/lexicon_controlled/`、`bank_controlled/`、`refuse_controlled/` |
| 制度文件 | 本文件 + 培训记录 + 权限清单 | 本文件 §三/§四 |
| 更新记录 | 与 `SEC-011_词库更新台账.md` / `SEC-014_题库更新台账.md` 对应 | 两份更新台账的受控类行 |

> **核心原则**：**内容是受控的，过程是可核查的。** 备案评估关注的是"你是否真的建立了并维护着这套资产"，而不是要求你把涉政词条打印出来提交。
