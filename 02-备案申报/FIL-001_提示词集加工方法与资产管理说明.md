## 1 概述

### 1.1 编写目的

本文说明本算法项目在**提示词工程层**所做的自主技术工作：加工方法、资产结构、版本管理机制与效果验证方式。本文既是工程实施规范，也是算法备案材料中「二次开发说明」与「算法优化机制」的技术依据。

### 1.2 定位说明

在文本合成的可控生成体系中，提示词工程处于最基础但性价比最高的一层：

| 层次 | 手段 | 训练成本 | 生效速度 |
| --- | --- | --- | --- |
| **① 提示工程** | 模板设计、约束显式化、少样本示例 | 无 | 立即 |
| ② 结构化约束解码 | JSON Schema → 有限状态机 | 无 | 立即 |
| ③ 检索增强 RAG | 外部知识注入 + 可溯源引用 | 无 | 立即 |
| ④ 参数微调 LoRA | 领域数据训练适配器 | 有 | 需训练 |

本层工作的工程价值在于：**在不训练模型的前提下，显著改善输出质量、格式稳定性与安全边界**，并形成可登记、可追溯、可迭代的工程资产。

### 1.3 资产规模

当前提示词资产共 **9 个模板**，覆盖 5 类任务：

| 任务类型 | 模板数 | 模板 ID |
| --- | --- | --- |
| 内容生成 `generate` | 2 | `gen_article_v1`、`gen_reply_v1` |
| 摘要归纳 `summarize` | 2 | `sum_digest_v1`、`sum_meeting_v1` |
| 改写润色 `rewrite` | 2 | `rw_polish_v1`、`rw_compress_v1` |
| 结构化抽取 `extract` | 1 | `ext_json_v1` |
| 安全兜底 `guard` | 2 | `guard_refuse_v1`、`guard_clarify_v1` |

## 2 加工方法

### 2.1 结构化重组

将自由形式的提示重组为固定骨架，保证每次调用的输入同构。所有模板遵循统一分节顺序：

```
[system]      角色定义、能力边界、硬性约束
[task]        任务定义与具体目标
[context]     上下文素材占位（用户输入、检索片段）
[output]      输出约束（格式、长度、语气、语言）
[examples]    少样本示例
```

**规范要求**：

- 分节顺序固定，不可调换；
- 每节以固定标记符包裹（`<|system|>` / `<|/system|>`），避免模型把素材误判为指令；
- 素材类内容一律置于 `context` 节，不得进入 `system` 或 `task` 节。

此项加工直接对应**提示注入防护**：结构隔离使外部素材无法提升为指令层。

### 2.2 指令精确化

将模糊表述转为可观测、可判定的具体规则。这是提升输出一致性最直接的手段。

| 模糊表述 | 加工后表述 | 加工要点 |
| --- | --- | --- |
| 写得专业一点 | 使用行业标准术语，避免口语化表达，不使用感叹号 | 形容词 → 可判定规则 |
| 总结一下 | 输出 5 条要点，每条不超过 30 字，按重要性降序 | 补充数量、长度、排序 |
| 语气友好 | 使用第二人称，每段开头用动词，不加敬语堆砌 | 转化为句式约束 |
| 别太啰嗦 | 直接输出结果，不解释过程，不加过渡语 | 明确禁止项 |

**加工规律**：每个模糊形容词必须转译为「可观测、可判定、可自动校验」的规则。不可判定的规则一律舍弃，避免无效约束。

### 2.3 少样本示例构造

示例对输出质量的提升最为显著，但构造有明确规范：

| 维度 | 规范 |
| --- | --- |
| 数量 | 2–5 条。超过 5 条边际收益递减，且挤占上下文预算 |
| 覆盖面 | 必须包含边界情况（空输入、超长、歧义、拒答），而非只放标准样例 |
| 格式一致 | 示例的输入输出格式须与真实调用完全一致，否则模型学到错误格式 |
| 内部一致 | 示例间风格必须统一；相互矛盾的示例会显著劣化输出 |
| 反例价值 | 每个模板至少给出一组「错误示例 + 说明」，明确什么是不合格输出 |

本资产库中的示例均采用「**正确输出 + 错误输出 + 不合格原因**」三段式，使约束可被模型准确理解。

### 2.4 约束显式化

针对已验证的失败模式逐条添加约束。约束按「失败模式 → 加工动作」配对，不做无针对性的堆砌。

| 失败模式 | 加工动作 | 落地模板 |
| --- | --- | --- |
| 编造事实 | 「仅使用提供的素材，信息不足时明确说明」 | 全部 |
| 数值被改写 | 「数字、日期、专有名词一律原样保留」 | `rw_polish_v1` |
| 丢失限定语 | 「保留时间、范围、条件等关键限定」 | `rw_compress_v1`、`sum_digest_v1` |
| 格式漂移 | 「严格按 Schema 输出，禁止增删字段」 | `ext_json_v1` |
| 输出啰嗦 | 「不输出应答性文字与过渡语」 | 全部 |
| 无依据承诺 | 「不承诺政策未明确的条件」 | `gen_reply_v1` |
| 语义反转 | 「不删减否定词，不把不确定改为确定」 | `rw_compress_v1` |
| 过度表述 | 「不使用绝对化与主观评价词」 | `sum_digest_v1`、`gen_article_v1` |
| 规则泄露 | 「不说明判定规则与触发词」 | `guard_refuse_v1` |
| 重复追问 | 「不重复追问已提供的信息」 | `guard_clarify_v1` |

### 2.5 任务分解与链路化

复杂任务拆为串行提示链，每步只承担单一职责。以「长文转客户简报」为例：

```
原始需求：把长文改成给客户看的简报
        ↓ 分解
① sum_digest_v1    → 提炼要点（结构化输出）
② （服务层）        → 识别受众与关注点
③ rw_polish_v1     → 转为商务简报风格
④ （服务层）        → 格式包装（标题、分段、行动项）
```

**分解原则**：

- 每步输出必须是下一步的合法输入；
- 每步可独立评测，失败可定位到具体环节；
- 单步职责单一，不混入多种风格要求。

### 2.6 模板参数化

模板不硬编码文本，全部转为带变量的参数化模板：

```yaml
variables:
  - name: max_points
    required: false
    default: "5"
    description: 要点数量上限
```

**校验规则**：服务层加载模板时校验 `required` 变量是否齐备，缺失则返回参数错误，不进入推理。

### 2.7 领域适配与术语对齐

- 通过 `variables` 注入领域术语表，避免模型用通用词替换专业词；
- 通过 `guards` 声明术语的禁用别名，保证输出术语一致；
- 术语表随业务变更独立维护，不需修改模板结构。

## 3 资产管理机制

### 3.1 版本规范

采用三段式版本号 `主版本.次版本.修订号`：

| 位 | 递增条件 | 示例 |
| --- | --- | --- |
| 主版本 | 模板结构变更（变量增删、职责调整、分节变化） | 1.x.x → 2.0.0 |
| 次版本 | 约束或示例调整（影响输出风格但不改结构） | 1.0.x → 1.1.0 |
| 修订号 | 文案微调（不影响语义） | 1.0.0 → 1.0.1 |

**强制要求**：

1. 修改模板必须提升版本号，**禁止原地覆盖**；
2. 历史版本保留，保证任意历史合成的可复现性；
3. `CFG-008_manifest.yaml` 中的版本号必须与模板文件内一致。

### 3.2 登记索引

`CFG-008_manifest.yaml` 为资产登记主索引，记录每个模板的：

- 唯一 ID、中文名称、任务类型、文件路径
- 当前版本与状态（`active` / `deprecated`）
- 变量清单、适用场景、约束摘要、使用备注

**登记流程**：

```
新增模板 → templates/ 建文件 → CFG-008_manifest.yaml 登记 → 加入评测集
修改模板 → 提升版本号 → 更新 manifest → 回归评测
下线模板 → status 改为 deprecated（不删除）
```

### 3.3 可追溯性

合成记录与提示模板双向关联，记录字段包括：

| 字段 | 说明 |
| --- | --- |
| `template_id` | 使用的模板标识 |
| `template_version` | 模板版本号 |
| `model_version` | 模型版本 |
| `params_snapshot` | 采样参数快照 |

**作用**：任一历史输出均可复现「用了哪个模板的哪个版本 + 哪个模型 + 什么参数」，满足备案对可追溯性的要求，也便于问题定位。

### 3.4 与服务的集成

| 环节 | 说明 |
| --- | --- |
| 加载 | 服务启动时加载 `CFG-008_manifest.yaml`，校验模板文件完整性 |
| 校验 | 请求中声明的变量对照模板 `variables` 校验 |
| 渲染 | 按 `sections` 固定顺序渲染，标记符包裹 |
| 采样 | 使用模板 `sampling` 作为默认值，可被请求覆盖（受租户上限约束） |
| 约束解码 | `extract` 类模板启用 `decode.mode: constrained` |
| 追溯 | 写入 `generations` 表，记录模板 ID 与版本 |

## 4 加工流程（迭代机制）

```
① 基线采集
   收集真实业务场景的原始提示与输出
        ↓
② 失败归因
   对基线输出分类：幻觉 / 格式 / 风格 / 遗漏 / 越界
        ↓
③ 定向加工
   按失败模式逐项处理：加约束 / 补示例 / 拆链路 / 调参数
        ↓
④ 小样评测
   固定测试集对比，量化提升幅度
        ↓
⑤ 版本固化
   打版本号入册，关联合成记录
        ↓
⑥ 持续迭代
   上线后收集新失败模式，回到 ②
```

**该闭环即备案材料中的「算法优化机制」**：说明本算法的效果改进不是随机的，而是由失败归因驱动的可重复过程。

## 5 效果验证

### 5.1 评测指标

| 指标 | 定义 | 采集方式 | 目标 |
| --- | --- | --- | --- |
| 格式合规率 | 输出可被 Schema/规则解析的比例 | 自动校验 | 抽取类 > 99% |
| 指令遵循率 | 满足全部显式约束的比例 | 规则 + 人工抽样 | 逐版本提升 |
| 要点覆盖度 | 摘要覆盖原文关键点的比例 | 与人工标准答案比对 | 逐版本提升 |
| 要点精确度 | 摘要中可回溯原文的比例 | 人工核验 | > 95% |
| 事实一致性 | 无原文外事实的比例 | 人工核验 | > 98% |
| 限定语保真度 | 数字/时间/范围未被改动的比例 | 自动比对 | 100% |
| 拒答准确率 | 该拒答的拒答、不该拒的放行 | 双向测试 | 双向均达标 |
| 澄清有效率 | 追问项确为缺失项的比例 | 人工核验 | > 90% |

### 5.2 评测方法

1. **固定测试集**：每个模板配固定测试样本，保证跨版本可比；
2. **自动优先**：格式、限定语、术语等可自动判定的指标优先自动化；
3. **人工抽样**：涉及语义质量的指标按比例抽样人工评分（1–5 分）；
4. **双盲对比**：版本对比时隐藏版本标识，避免评分者偏见；
5. **拒答双向测试**：既测「该拒的拒答率」，也测「正常请求的误拦率」。

### 5.3 与备案材料的关系

评测数据同时服务于两处：

| 用途 | 说明 |
| --- | --- |
| 备案「效果验证」 | 提供提示工程层的量化改进证据 |
| 备案「安全评估报告」 | 拒答测试集与拒答准确率直接作为安全能力证据 |

> 一份数据两处复用，需保证测试集构造方法与判定标准在材料中说明清楚、可复现。
