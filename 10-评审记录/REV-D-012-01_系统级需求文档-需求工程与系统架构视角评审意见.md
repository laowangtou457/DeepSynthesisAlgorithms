### `RQ4-01` 两条已存档的强制法源在本文件全无承接：漫剧/网络视听侧（微短剧）与网络信息内容治理侧

- **问题**：同一个「状态」概念在四处给出互斥口径。

### `RQ4-03` `SYS-015`「总体性能与容量」无测量口径，且以「均以软件级为准」自我空心化

- **问题**：这条是系统级的**总体指标条目**，但它既没有自己的口径，也没有把口径的**唯一定义处**钉在某一层。
- **证据**：
  - L117 描述：`内部研发阶段支撑文本合成任务的并发、时延与可用性总体要求；**当前为暂定值，随开发期实测校准**（团队规模：1 名开发）`；
  - L117 验收标准：`短期同步合成 <3s（P95）、服务可用性 ≥99%、单卡 10 并发（**均以软件级为准**）`；
  - 下游 `REQ-005` §5（L133~L135）：`SW-101 <3s（P95）｜压测采样`、`SW-102 <1s｜压测采样`、`SW-103 ≥99%｜监控统计`——**同样只有目标值**；
  - 三层中**没有任何一处**定义：并发是「同时在跑的请求数」还是「同时在飞的 token」、上下文长度取多少、输入/输出长度假设、P95 的统计窗口与样本量、可用性是否扣除计划维护与降级窗口；
  - `REQ-001` L58（`HW-001` 验收标准③）已把「单卡 **8K 上下文** ≥10 并发**实测**通过（P95 <3s）」写成硬件验收判据——**它引用的正是这三个未定义口径**。
- **影响**：切面 ③ 要求的「方法 / 责任人 / 时点 / 达标值」四要素**缺三项**；`REQ-001` 的硬件验收无法判定通过与否；备案安全评估「服务与技术条件」栏无法给出**可复现**的指标；「暂定值」会一直暂定下去。
- **建议方向**：二选一并写进文档——（a）在本条定义四要素；（b）明确本条只做**指标登记**、口径唯一落在软件级，**同时在软件级补齐四要素并在本条交叉引用**。当前「均以软件级为准」是一句**转授权**，转出去之后下游并未接住，等于双方都不定义。

## 2 P1 · 妨碍可用（7 条）

### `RQ4-04` 角色表缺「客服」角色，与本文件 `SYS-020` 及软件级四角色分离不一致

- **证据**：L46~L51 角色表仅 4 行（客户 / 内部内容审核人员 / 系统管理员 / 下游消费者）；而 L107（`SYS-020`）要求「客服可受理、回复、转交审核/技术、关闭工单」；`REQ-005` §6 L150 已写明「**客户 / 客服人员 / 内容审核人员 / 系统管理员四角色分离**」，§1 L31 亦新增「客服工作台模块」。
- **影响**：跨层角色集合不一致；客服岗位的**权限边界与主要诉求在系统级无来源**，`REQ-005` SW-024（L92）的「四角色权限分离」验收标准在系统级找不到上位依据。
- **建议方向**：在 §2 角色表补「客服人员」行（说明 + 主要诉求），使系统级与软件级角色集合一致。

### `RQ4-05` 认证方式跨层不一致，且软件级把「微信登录」混入真实身份认证

- **证据**：L93（`SYS-003`）：「基于**移动电话号码、身份证件号码、统一社会信用代码或国家网络身份认证**等方式对使用者做真实身份认证」；而 `REQ-005` L89（`SW-020`）：「支持真实身份认证接入（**微信小程序登录**/手机号认证等）」、L105（`SW-I05`）同。微信登录提供的 `openid`/`unionid` 是**账号标识**，不等于《深度合成管理规定》§9 的「**真实身份信息认证**」。
- **影响**：合规承接被表述层面的宽松化；备案材料若照抄软件级表述，会被认定为认证方式不符合 §9。软件级无法判断「微信登录能否充抵实名」。
- **建议方向**：在系统级明确「**账号体系**（登录）与**真实身份认证**（实名）」的分界与各自适用场景；软件级据此改写 SW-020 / SW-I05 的表述，把微信登录归入账号体系。

### `RQ4-06` 导出文件格式清单跨层冲突，且软件级自称的依据不成立

- **证据**：L94（`SYS-017` 验收标准）与 L170（`SYS-Q16`）均为 **`TXT/MD/JSON/Excel`（4 种）**；而 `REQ-005` L91（`SW-022`）写「TXT/MD/JSON/Excel/**PDF**」并标注「依据 SYS-Q16」。
- **影响**：实现者无从判定是否必须支持 PDF；SW-022 的 PDF 分支在系统级**无授权**，属超范围实现；反向若去掉 PDF，则软件级超出系统级的部分无人发现。
- **建议方向**：二选一——在 `SYS-017`/`SYS-Q16` 补 PDF（并说明依据），或从 `SW-022` 移除 PDF。二者必须一致。

### `RQ4-07` `SYS-008` 训练数据治理未承接已存档的两部专项国标

- **证据**：L104 来源列仅「规定 §14；暂行办法 §7、§8」；而 `08-法律法规依据/L3-国家标准` 已登记 **`GB/T 45652`（预训练和优化训练数据安全规范）** 与 **`GB/T 45674`（数据标注安全规范）**，`REQ-006` §6「内容安全资产」行亦以二者为训练数据治理依据；L104 的验收标准（「数据来源清单 + 授权核验 + 标注规则成文」）未挂到该两标的具体要求。
- **影响**：训练数据治理是本项目「二次开发」合规实质的核心举证项（`C-002`）；验收标准与国标条目之间缺映射，备案时难以逐条应对。
- **建议方向**：在 `SYS-008` 的来源列补这两部国标，并把验收标准拆到「数据来源/授权/标注规则/标注质量评估」四个可核查项，与 `05-数据管理`（D-009）的产出物一一对应。

### `RQ4-08` 缺条：未成年人保护与个人信息保护两条主线在系统级无独立承载

- **证据**：
  - **未成年人保护**——L106（`SYS-010`）仅有「防范未成年人过度依赖」6 字，无年龄识别、防沉迷、监护人同意等任何机制；`LAW-015_未成年人网络保护条例`、`LAW-016_未成年人节目管理规定` **均已存档却未被任何条目引用**；`REQ-005` 全文 `未成年人` 命中 **0**（即**系统级有要求、软件级无承载**，断链）。
  - **个人信息保护**——仅出现在 L100（`SYS-004`）的八类制度清单中（「个人信息保护」4 字），无独立条目、无验收标准；`LAW-020_网络数据安全管理条例` 已存档未引用；软件级仅有 SW-019（L82）一条笼统条目。
- **影响**：本服务面向**境内公众**提供文本生成，且提供信息发布/导出（`SYS-017`），未成年人保护与个人信息保护是备案与监督检查的常规审查项。当前状态下这两条主线**既无条目、又无验收标准、更无下层承载**。
- **建议方向**：新增系统级条目（或明确并入 `SYS-004` 并给出验收标准），来源列引用已存档法源；并让 `REQ-005` 增设对应软件级条目，闭合「系统级有 → 软件级无」的断链。

### `RQ4-09` 备案法定时限未登记；ICP 未在系统级标为阻断项

- **证据**：① L113（`SYS-011`）描述「履行算法备案及变更注销手续」，未写备案的**法定时限义务**（《深度合成管理规定》§19 引致《互联网信息服务算法推荐管理规定》（`LAW-007`）的「**提供服务之日起十个工作日**内」办理）——`REQ-004`/`REQ-005` 全文 `十个工作日` 命中 **0**；② L162（`SYS-Q8`）对 ICP 仅写「**仍建议**按对外服务形态逐项核对落实」，而 `REQ-001` L85（`HW-010`）已把「固定公网 IP + 可办理 ICP 备案的接入线路」明确列为**上线阻断项**，`REQ-001` §5 风险提示亦称「**此项为上线阻断项，须尽早办理**」。
- **影响**：阻断项在**系统级缺席**，与硬件级、任务层（`REQ-006` §6「公网线路：上线阻断项」）不一致；备案时限未登记会导致「先上线后备案」的合规风险无人预警。
- **建议方向**：在 `SYS-011` 补备案时限义务；把 `SYS-Q8` 的 ICP 表述从「建议」改为与 `REQ-001` 一致的**阻断项**并写明前置要求。

### `RQ4-10` `SYS-005` 的「国标门槛」不可核验，且与项目自有台账口径各说各话

- **证据**：L101 验收标准：`**以 09-合规资料库 的词库与题库为可计数资产支撑评测**，达到国标门槛：正确拒答率 ≥95%、误拒率 ≤5%、违法内容输出率 = 0%`——**未标来源条款**。核对结果：
  - `09-合规资料库/05-台账与制度/SEC-007_人工签核规程.md`「附录 B」转引的国标阈值为：**生成内容合格率 ≥90% ｜ 正确拒答率 ≥95% ｜ 误拒率 ≤5% ｜ 违法内容输出率 = 0%** → 本文件**漏了「生成内容合格率」这一项**；
  - `09-合规资料库/05-台账与制度/SEC-013_达标指标对照表.md` 第 18 行给出**项目自定线**（生成内容合格率 **≥95%**，严于国标 90%）——与本文件**未互指**；
  - `09-合规资料库/README.md`「国标量化门槛」另有**规模门槛**（关键词库 ≥10,000 / 生成内容题库 ≥2,000 / 拒答 500+500），本文件 L137（§6）虽提到「逐步扩充至 GB/T 45654—2025 规模门槛」，但**验收标准未纳入规模口径**。
- **影响**：`SYS-005` 是内容安全的总验收条，其「国标门槛」四字无法核验到条款；跑测（`REQ-006` §3.3 的「正确拒答率 ≥95%/误拒率 ≤5%/违法内容输出率 0%」门槛）与资料库台账存在**口径分叉**，备案评测时会出现「按文档跑还是按台账跑」的分歧。
- **建议方向**：在 L101 标明来源（`GB/T 45654—2025` 附录 B，经 `SEC-007` 转引）；把「生成内容合格率」补入；把**规模门槛**与**合格率门槛**分列；与 `SEC-013` 明确「国标线 / 项目自定线」两级口径并互指。

## 3 P2 · 质量提升（4 条）

### `RQ4-11` §7 章节名与内容名实不符，且 §7 与 §7.1 内容同构

- **证据**：L144 标题「## 7 待明确事项」，但 L146~L152 的 SYS-Q1~SYS-Q5 **状态列全部为「✅ 已确认」**；L154 的 §7.1 已更名为「**决策记录**」；两张表结构相同（编号 / 事项 / 结论 / 影响 ↔ 编号 / 事项 / 决策结论 / 决策方 / 落地位置），属同一信息的两套登记。
- **影响**：新读者会按标题去「待明确事项」找未决问题，落空；同一事项存在两处载体，后续修订易只改一处。

### `RQ4-12` 重复分隔线

- **证据**：L194 与 L196 各有一条 `---`（其间隔一行空行），形成空段；`REQ-005` L157/L159 同病。
- **建议方向**：删除其一。

### `RQ4-13` 简称未在正文定义处统一

- **证据**：L85 的字段说明只约定「规定」与「暂行办法」，但正文 L94、L105、L118、L120 直接使用「**标识办法**」而**无简称约定**；`REQ-005`（L91、L104 等）同样直接使用「标识办法」。
- **建议方向**：在 L85 的简称约定中补「标识办法」指《人工智能生成合成内容标识办法》。

### `RQ4-14` 「来源」列混入用途/理由；§4 边界三分被解释性文字稀释

- **证据**：① 部分条目的来源列填的是用途或决策出处而非上位依据，例如 L117（`SYS-015`）来源「项目级；SYS-Q13」、L91（`SYS-001`）来源「立项、备案目标；SYS-Q6、SYS-Q8」、L115（`SYS-013`）来源「规定 §24；暂行办法 §2；SYS-Q6」——切面 ① 要求「来源指向真实上位依据（法规、业务、架构）」，此处「项目级」「立项」属自述；② L78「不包含」项内夹入「（下游独立承担）」的责任归属说明，并把「C 端大规模商业化运营」「从零训练基座模型」两类不同性质项并列，削弱三分表的可判性。
- **影响**：前者使「来源」字段不可用于反向追溯上位依据；后者使切面 ④ 要判的「包含/不包含/外部依赖可判且互斥」出现含混。
- **建议方向**：来源列只放上位依据（法规条款 / 业务决策编号 / 架构文件），用途与理由移入描述列；§4 三分表把责任归属说明移到表下注释。
