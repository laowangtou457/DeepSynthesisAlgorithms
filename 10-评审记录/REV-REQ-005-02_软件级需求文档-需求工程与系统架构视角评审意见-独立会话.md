## §0 评审结论

### 0.1 总判断

> **`REQ-005`（V2.6）是一份结构完整、追溯骨架基本健全、可以作为开发与测试依据的文档；本层最核心的制度设计——「测量口径唯一定义在软件级」——已经落地且被系统级正确引用，是本工程需求管理中最扎实的一处安排。本次评审未发现 P0 阻断级问题。**
>
> 但它**还不是"可以直接照着写代码和写用例"的需求**，差距集中在三处：
>
> 1. **一批条目的验收标准仍是"能力断言"而非"判据"**——说的是"能做什么"，不是"做到什么程度算过、谁在什么时点用什么东西测"。`SW-015`/`SW-017`/`SW-018`/`SW-021`/`SW-023`/`SW-024` 六条属此类，其中 `SW-023`（检索增强）**没有任何一个数值、阈值或检查方式**，是全部 28 条功能需求中可验证性最弱的一条。
> 2. **「诚实标注未达成」的做法只做了第一处，没有制度化**——`SW-001` 的「状态可恢复」未达成写得很好（且我认同这种做法，见 RW-05），但**同一类问题在 `SW-D01`、`SW-010`、`SW-101`/`SW-102` 三处同样存在而未被标注**。请求书 §2.4(2) 问的正是这个，答案是：**三处**。
> 3. **接口、数据、非功能三类表在判据底座要求的「验收标准 / 优先级 / 关联 / 状态」四字段上系统性缺位**——`README.md` §四 明确「每条需求至少包含以下八项」，而 §5.2 的软件级模板对这三类表只给了 7/6/7 列。这不是执行偏差，是**判据底座自身的模板缺口**，责任在规范侧；但软件级文档因此有 26 条条目（`SW-I01`~`I08`、`SW-D01`~`D10`、`SW-101`~`SW-111`）**没有任何验收判据可依**。
>
> 另有 **4 条来自项目级条目（`REQ-006` §3/§4 的 `F-xxx`）的断链**未被软件级承接或显式排除：限流与配额、流式 SSE 接口、异步长任务与幂等、断连取消。其中「**幂等性」在 `REQ-005` 全文中一次都没有出现**——而请求书 §2.2 第 2 项正是问接口是否说清幂等性。答案是：全文无此要求。
>
> **一个此前未被记录的口径内部矛盾**（本次最实质的新发现之一）：`SW-103` 规定「降级窗口按不可用计」，而 `SW-007`/`SW-015`/`SW-023`/`SW-025` 四条都把「降级」设计成正常容错行为，且**文档从未定义"什么算降级"**。这意味着系统主动降级（这是好事）会直接扣减 99% 的可用性指标，设计上会抑制降级。见 RW-08。

再看性能：`SYS-015`（行 123）**只登记指标**（「短期同步合成 <3s（P95）· 首 token <1s · 可用性 ≥99% · 单卡 10 并发」），**并明确写「本条只做指标登记，测量口径的唯一定义处落在软件级 `REQ-005` §5」**——这是本工程最规范的一处跨层处理。

**但 `README.md` §二 的归属判断表（行 41~51）对此完全无话可说**。它给的 9 条示例都是"一句话归一层"，其中「生成内容需带显式与隐式标识 → 软件级」（行 47）如果被机械套用，会得出"标识只应在软件级出现、系统级不得提及"的结论——**而这与合规举证的现实相反**：备案材料中标识义务必须以系统级条目的形式出现并挂法源。

**因此判据表落后于实践。建议补三条规则：**

| # | 建议补入 `README.md` §二 的规则 | 依据（本工程既有实践） |
| --- | --- | --- |
| **规则 1 · 侧面分工** | 同一要求跨层承载时：**「为什么必须」归系统级**（义务 + 法源 + 指标登记）、**「怎么做、怎么测」归软件级**（机制 + 判据 + 口径）、**「跑起来要什么」归硬件级**。三层承载的是**不同侧面**，不是同一句话的三次复制 | 标识四层承载（见上表）；`SYS-016`/`SYS-019` 与 `SW-014`/`SW-026` 的责任切分 |
| **规则 2 · 判据唯一** | 同一指标的目标值可在多层出现，**但判据（口径 / 检查方式 / 达标值）只允许在一处定义**；其余层**只引用、不另定义、也不得反向转授权为"以某某级为准"** | `SYS-015` 已明写"不用『均以软件级为准』作转授权"（`REQ-004` 行 123，该表述已被明确废除）；`SW-101` 为口径唯一定义处 |
| **规则 3 · 双向互指** | 跨层重复登记时，上层「关联」列须写明下层条目、下层「来源」列须写明上层条目；**任一侧缺失即视为断链** | 现有 28 条功能条目已 100% 回指上位（✅）；但系统级侧对 `SW-024`/`SW-111`/`SW-023`/`SW-D09`/`SW-D10` 的回指缺失（见 RW-20），说明规则须双向强制 |

**同时说明为何不选"维持唯一归层、其余层只引用"**：本项目是**面向备案的合规项目**，标识、实名、未成年人保护、交付合规声明这四件事**都同时有"外部义务"和"内部实现"两个侧面**，且备案举证材料恰恰需要义务侧的完整呈现。若强行"唯一归层"，只会导致两种坏结果之一——要么合规义务漏挂在系统级（举证缺项），要么把可测判据塞进系统级（污染系统级粒度）。**"唯一归层"在这个项目里不是一个可选项。**

**但必须补一句约束**：多层承载**不等于**"同一句话抄三遍"。判据表应显式写明：**同一侧面的内容不得在两层各写一份**——例如"标识文案的具体字符串"只在软件级写，系统级只写"文案按 `SYS-Q15` 定稿"（`SYS-009` 行 110 已如此，写法正确，可作范例）。

### 待议 C：「验收标准」与「测量口径」在同一张表里，是否应分列？

**结论：设问的前提在非功能表已经解决（口径**已经**是独立列），真正需要处理的是**两处"一格多义"——非功能表的「测量口径」列语义不纯、功能需求表的「验收标准」列混装了三类信息。建议按下面方式收敛，而非简单拆列。**

**先纠正设问前提**：请求书 §3.2 待议 C 的背景写「现状：非功能条目把『目标值』与『测量口径』写在同一条目内」。实测**并非如此**——`README.md` §五.2 模板（行 155）与 `REQ-005` §5 表头（行 147）都是 **7 列独立结构**，「测量口径（**唯一定义处**）」已是独立的一列。**这一点不需要改。**

**真问题一：`REQ-005` §5「测量口径」列里混装了三种语义**（这是切面③最主要的结构发现）：

| 编号 | 该列实际写的内容 | 语义类别 |
| --- | --- | --- |
| `SW-101`（行 149） | 并发定义 / 上下文长度 / 输入输出长度假设 / P95 窗口与样本量 / **不含降级与重试请求** | 前 4 项是**前提假设**，末 1 项是**测量规则** |
| `SW-102`（行 150） | 「输入 / 上下文假设**同 `SW-101`**」 | **引用**，非自身口径 |
| `SW-103`（行 151） | 统计期 / 扣除计划维护窗口 / **不扣除降级窗口** | 统计规则 |
| `SW-104`（行 152） | 「控制器层不得含业务逻辑；逐文件核对调用链」 | ⚠️ **这是验收判据，不是口径** |
| `SW-105`（行 153） | 「每请求有唯一 ID 且贯穿全链路日志」 | ⚠️ **这是验收判据** |
| `SW-106`（行 154） | 「扫描仓库 / 日志 / 代码库无密钥明文」 | ⚠️ **这是检查方式** |
| `SW-110`（行 158） | 「本地私有化；对外经宿主平台统一入口（本算法不自行开对外域名/端口）」 | ⚠️ **这是功能约束** |
| `SW-111`（行 159） | 「软件侧提供备份触发与校验、数据导出/恢复接口；RPO/RTO 口径与 `HW-008` 对齐」 | ⚠️ **这是职责分工 + 跨层引用** |

即：**11 条里有 6 条的口径列写的不是口径**。机器校验时无法按统一语义处理这一列（例如无法自动判断"某条是否已声明其前提假设"）。这才是请求书 §3.2 所担心的「妨碍机器校验」的真正落点。

**建议**：该列**只允许写前提假设与统计规则**（如 SW-101 前四项、SW-103 全部）；判据类内容归入新增的「**验收标准**」列；检查方式归入「**检查方式**」列；职责分工类内容下沉到 `SW-024` 等功能条目或 §6 安全与权限表。

**真问题二：功能需求表的「验收标准」列一格多义**——这是比待议 C 原设问更值得处理的一处。实测至少 5 条在该格内混装了**四种语义**：

| 条目 | 该格内的四种语义 |
| --- | --- |
| `SW-001`（行 48） | ①达标要求「全链路一步不缺、可回退」②**检查方式**「七阶段逐段推进＋回退路径逐条走通（锚 `TRANSITIONS`）」③**门控形态要求**「必须为转移表形态、非散落 `if`」④**实现现状标注**「状态可恢复当前未达成……不得判为合格」 |
| `SW-002`（行 49） | ①达标要求「漂移 0 处」②**检查方式**「`R1~R40` 脚本化比对＋人工抽检 ≥30 例」③**判据族编号** ④**归档落点要求**「落 `qa/<pack_id>.drift.r<N>.json`……缺失即阻断交付」 |
| `SW-004`（行 56） | ①达标要求「覆盖全部给定要点」②**检查方式**「事实类字段逐项比对」③**不合格判定**「出现输入之外的事实类取值即判不合格」④抽检量 |
| `SW-010`（行 69） | ①达标要求「零漏放」②**检查方式**「题库 ≥2,000 全量跑测＋抽检 ≥300」③**阈值引用**「`SEC-013` §二」④**不合格判定**「漏放 1 例即不合格」 |
| `SW-014`（行 79） | ①产出要求 ②**判据跨条引用**「判据取自 `SW-026` 的自检结果」③**分工声明** |

**建议**：功能需求表在现有 12 列基础上增设两列——

- **「检查方式」**：怎么测（方法 + 样本量 + 判据编号）
- **「实现现状 / 前置条件」**：如实标注未达成项与前置依赖（**把 `SW-001` 那段极有价值的诚实标注从验收标准格里搬到这里，给它一个正式位置**）

这样「验收标准」列可还原为**纯达标判据**，一行一义，机器可校验，且未达成项有统一登记位（顺带解决 RW-06 的三处漏标注）。

**结论**：不是「拆为独立列 / 拆为独立条目」的二选一，而是**功能表增设 2 列、非功能表口径列收敛语义**两件事。

### RW-05 · `SW-001` 的如实标注恰当，但**检查方式未覆盖被标注的那一项本身**；且该能力应从状态机条目拆出

| 要素 | 内容 |
| --- | --- |
| **问题** | 「状态可恢复」被如实标注为未达成，写法很好；但该条的「检查方式」只写了状态流转与回退的验证步骤，**没有任何"跨进程重启后读回"的步骤**——也就是说，被标注为"当前未达成"的那一项，至今没有写明"将来如何判定它达成"。此外，会话持久化是一项独立的存储能力，与状态机混在同一条目内，导致该条验收标准必然长期携带一个未达成项。 |
| **证据** | `REQ-005` §2.1 `SW-001`（行 48）：验收标准列写「全链路一步不缺、可回退。**检查方式**：七阶段逐段推进 ＋ 回退路径逐条走通（锚 `03-工程代码/app/app/services/state_machine.py` 的 `TRANSITIONS` 转移表与 `tests/test_state_machine.py`）；**门控为转移表形态**——未确认梗概时的推进请求须被拒（HTTP 409）……⚠️ **「状态可恢复」当前未达成**：会话存储为内存实现，进程重启即丢失；待 `T-004` 接入 PostgreSQL／Redis 后闭环——**本项在服务化跑测通过前不得判为合格**」。<br>**检查方式的三项动作均为进程内行为**（推进、回退、拒 409），**无一项跨进程**。 |
| **影响** | ① **标注本身是恰当的，建议保留并推广**（见 RW-06）：它如实区分了「需求已确认」与「实现未达成」，与 `README.md` §四 状态取值域语义一致，未把状态改判为「已完成」，且绑定到具体任务号 `T-004` 可追踪。② 但**闭环判据缺失**：`T-004` 完成后，"怎样才算 `SW-001` 合格"仍然只由一句"在服务化跑测通过前不得判为合格"承担——"服务化跑测"本身未定义。③ 归位问题：条目同时承载状态机（可独立验收）与持久化（当前未达成），二者验收结论被绑在一起。 |
| **建议方向** | ① 在该条补一步可判定的闭环检查（例：kill 服务进程 → 重启 → 以原 `pack_id` 读回会话与阶段快照 → 断言成功），使"未达成"变成"待达成且已写明如何判定达成"；② 评估将会话持久化与恢复拆为独立条目（参考同文档 `SW-111` 对硬件 `HW-008` 的做法：把跨层/跨模块的独立能力单列），使 `SW-001` 可独立判合格。 |

## §4 P2 质量提升意见（`RW-15` ~ `RW-28`）

### RW-15 · `SW-024`（管理控制台）在系统级无对应条目，属弱挂靠

- **问题**：管理控制台是内部运营界面（审核 / 用户认证 / 审计日志 / 模板热更 / 模型后端配置 / 监控 / 工单监督），但系统级 21 条中无"内部管理后台"条目，其来源 `SYS-004`（制度）与 `SYS-006`（治理闭环）均为弱挂靠。
- **证据**：`REQ-005` §2.6 `SW-024`（行 98）来源列：「SYS-004、SYS-006」；§1 功能划分表（行 30）列为独立模块。`REQ-004` §2 用户与角色表（行 51）有「系统管理员：配置、模型管理、日志与监控」这一诉求，但 §5 无对应条目；§5 中 `SYS-004` 的关联列为「09-合规资料库/05-台账与制度、SW-019」，`SYS-006` 的关联列为「SW-016~018」，**均未回指 `SW-024`**。
- **影响**：追溯侧，该功能无上位依据可回溯；`SW-024` 验收标准「四角色权限分离」的"四角色"定义实际来源于系统级 §2 的角色表，但两处未互指。
- **建议方向**：如实标注无 SYS 对应条目，或推动系统级补一条"内部运营与管理系统"条目并互指。**是否补系统级条目由系统级责任方决定（不在本次范围）。**

### RW-16 · `SW-016` 与 `SW-107` 是同一件事在功能表与非功能表各写一遍

- **问题**：「输入输出全链路可审计 + 日志留存 ≥6 个月」被同时登记为功能条目 `SW-016` 与非功能条目 `SW-107`，两处内容重叠。
- **证据**：`REQ-005` §2.5 `SW-016`（行 87）：「每次合成可追溯（会话/阶段/模型/模板/时间/结果），**日志留存 ≥6 个月**」；§5 `SW-107`（行 155）：「输入输出全链路可审计、**日志留存 ≥6 个月**｜强制｜任一合成记录可反查输入输出与模板版本；留存 ≥6 个月｜审计核查｜SYS-006、`REQ-006` §4 `N-007`」。两者验收要求实质相同；`SW-107` 来源 `N-007`，而 `SW-016` 来源亦含 `SYS-006`。
- **影响**：修改一处漏改另一处的风险；复查时可能重复计数为两条已满足项。
- **建议方向**：明确分工（如 `SW-016` 承载"记录什么"，`SW-107` 承载"必须留多久、如何核查"）并在两处互相引用；或合并。

### RW-17 · 全部条目无「验证时点」，无法与里程碑挂钩

- **问题**：请求书 §3 切面③ 要求验收标准说清"用什么方法测、**谁测**、**在什么时点测**、达到什么值算过"。实测：四张表均**无责任人字段、无验证时点字段**；文档中"责任人"一词从未出现，"时点"仅在 `SW-102`/`SW-103` 的统计窗口语境中出现（非验证时点）。
- **证据**：`REQ-005` §2~§5 全部表格列头（行 46~48、108、125、147）无相关列。`README.md` §四（行 79~90）八项必备字段亦未含责任人/时点——**属规范层缺口**。可挂钩的时点基准存在但未被使用：`REQ-006` §9 里程碑（行 337~341）M1~M5 已与交付物绑定。
- **影响**：验收无排期，需求无法进入测试计划；里程碑表与需求验收之间没有连线。
- **建议方向**：本项目团队规模为 1 名开发（`REQ-004` §6 行 137），加"责任人"列性价比低，建议只增「**验收时点 / 触发条件**」（如"服务化跑测通过后"「`T-0xx` 完成后」）；是否入规范由规范侧决定。

### RW-18 · 非功能条目无状态列，成熟度无法表达

- **问题**：11 条非功能条目没有状态字段，无法区分"指标已达成"与"指标尚未验证"。`README.md` §四 将「状态」列为必备字段且取值域含「内部确认 / 开发中 / 已完成」。
- **证据**：`REQ-005` §5 表头（行 147）7 列无状态列。对比功能需求表有状态列且 `SW-004`~`SW-008` 标「开发中」（行 41 字段说明）。
- **影响**：验收盘点时非功能项只能靠测量方式栏推测进度。
- **建议方向**：随 RW-09 的规范侧修订一并补齐。

### RW-19 · 「未达成 / 前置条件」类信息无统一登记位

- **问题**：本类信息当前散落在条目正文的不同位置（`SW-001` 在验收标准格内、`SW-D10` 在说明列的括注「人工台账承担」、`ISSUE-024` 等则完全不在需求文档内），无统一登记位，检索与复查均不可靠。

- **影响**：同类信息分散，评审方难以快速判断"哪些条目当前客观不可验收"——这正是 RW-06 的成因。
- **建议方向**：与 RW-12 同源，随功能表增设「实现现状 / 前置条件」列一并解决；或在 §5 之前加一张小表集中登记。

### RW-20 · 系统级 → 软件级的反向回指不完整

- **问题**：软件级 28 条功能条目 100% 回指了上位条目（✅ 优点），但系统级对软件级的反向关联存在缺口，跨层追溯因此不是双向闭合的。
- **证据**：`REQ-004` §5 中：`SYS-006` 关联列「SW-016~018」（行 107）——未含 `SW-111`（软件级却挂在该条上，见 RW-13）、未含 `SW-027`/`SW-024`；`SYS-007`（行 108）关联列为「09-合规资料库/05-台账与制度」——**未回指 `SW-D09`**；`SYS-008`（行 109）关联列为「D-009、GB/T 45652、GB/T 45674」——**未回指 `SW-D10`**；`SYS-012`（行 120）关联列为「D-009、09-合规资料库」——未回指 `SW-016`；`SYS-020`（行 112）关联列含 `SW-027` ✅。对照软件级侧：`SW-D09`/`SW-D10`（行 135~136）来源分别写 `SYS-007`/`SYS-008` ✅。
- **影响**：从系统级出发的追溯会断链；监管/备案举证若从系统级条目向下展开，会漏掉 `SW-D09`/`SW-D10` 这两条数据承接条目。
- **建议方向**：按待议 B 建议的**规则 3（双向互指）**在规范层强制；本层可主动推动系统级侧补齐（不在本次范围）。

### RW-21 · 无「约束与假设」章节，假设散落在口径列且不可管理

- **问题**：软件级需求隐含多项前提假设（上下文 8K、并发 10、输入 500 字 / 输出 600 字、模型可替换、宿主平台承载对外入口），但文档没有承载假设的章节，这些假设写在非功能表的口径格内，无法作为"假设"被识别、评估与在变更时复查。

- **影响**：假设变更（如模型换为长上下文、硬件换卡）时无复查触发点。
- **建议方向**：在规范侧为软件级模板补该章；文档侧把现有假设（尤其口径列的前四项）归集列出。

### RW-22 · `SW-017`（拒答与兜底）的关联未覆盖输入侧触发路径

- **问题**：拒答可由输入侧命中（`SW-009` 拦截）或输出侧命中（`SW-010` 复检）触发，但 `SW-017` 只关联 `SW-010`。

- **影响**：实现侧可能只实现输出侧拒答，输入侧拦截后无兜底话术。
- **建议方向**：关联列补 `SW-009`，并明确两种触发路径各自的拒答话术来源。

### RW-23 · `SW-028` 的「加强审核档」与年龄信息来源均未定义

- **问题**：`SW-028` 规定涉未成年人内容「命中即拦截，走 `SW-009`/`SW-010` 双闸的**加强档**」，但"加强档"相对正常档差异未定义；同时"年龄识别"的输入"年龄信息"来源与判定方式未说明。

### RW-24 · 部分验收阈值只存在于契约层 / 实现层，需求层不自证

- **问题**：两条功能条目把达标值指向交付规范章节号或校验脚本，需求层无法独立判定达标。

### RW-25 · `SW-021` 与 `SW-027` 的职责边界未互斥界定

- **问题**：`SW-021`（申诉举报接口）与 `SW-027`（客服工作台）在"处理"与"时限"上职责重叠，文档未写清二者分界。

### RW-26 · `SW-101` 的样本量与窗口组合缺"样本不足时如何处置"的规则

- **问题**：口径要求「P95 统计窗口＝连续 10 分钟、**样本 ≥1,000 次**」「**不含**降级与重试请求」——若窗口内降级较多，可能无法凑满 1,000 样本，文档未规定此时如何判定。

### RW-27 · 表头「文档状态」格承载了整条升版链，应归入 §7
