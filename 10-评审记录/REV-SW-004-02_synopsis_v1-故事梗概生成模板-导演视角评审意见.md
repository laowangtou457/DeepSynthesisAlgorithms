## 0 评审结论

> **这份模板把「叙事结构」做到了 SW-004 的范本级，把「视觉原料」留成了空白——它是一款合格的「故事梗概生成器」，但还不是一条「镜头提示词链路的源头」。**
>
> 模板反复强调「不得编造、缺失写未指定」（第 45–47 行），这在**叙事层**是正确的；但链路最终要交付的是**镜头级提示词集**（SW-007），而下游 `characters[]` 的外观锁定、`style_bible` 的风格锚点、逐镜的空间载体，这份梗概**一个字段都不产出**。于是「不编造」与「下游必须有」在链路中段直接顶死：**要么在下游编造（违反本模板第 1 条硬性约束），要么卡住（视觉锚点无来源）。**

**对导演视角最要紧的一句话**：

> 梗概层不给视觉锚点，等于把「角色长什么样、场景是什么空间、色光什么基调」三件事**推迟到最贵的地方去决定**——而这三件事正是 AI 视频一致性漂移（角色/风格/空间）的三大失败源，本工程 v1.1 已为此把它们提升为**包级顶层结构**（§3.3 / §3.4）。

## 3 P0 阻断级（3 条）

> 这一级的共同特征：**下游有「必须」字段，而链路源头没有任何地方能产出发给它。** 缺的不是措辞，是**字段承载位置**。

### D-01 角色视觉锚点结构性缺失 ★★★

| 项 | 内容 |
| --- | --- |
| 位置 | `output` 字段结构 L79–84（`protagonist`）、L95–97（`supporting`） |
| 现状原文 | `protagonist` 仅四键：`name` / `identity` / `goal` / `flaw`（L80–83）；`supporting` 仅三键：`name` / `role` / `relation`（L96） |
| 下游要求 | v1.1 §3.4 L361 `character_id`（**必须**）、L363 `appearance_lock_zh`（**必须**，内容为「发型/发色/瞳色/服装/体态/年龄感」） |

**问题（导演视角）**：下游 `characters[]` 是 v1.1 为「避免同一角色在不同镜头长得不一样」而设的**结构性手段**（v1.1 L368），其中 `appearance_lock_zh` 是**必须字段**、且明确要求承载「年龄感/服装/体态」。而梗概给到下游的角色信息只有**身份与职能**——`identity`（外卖员）、`role`（情感线）、`relation`（妹妹）——**外观维度为零**。

这不是「下游可以自己补」的问题：本模板第 1 条硬性约束（L45–47）明令「不得用看起来合理的虚构值填充」。**下游若补外形，就是在本工程自己的硬约束下编造；下游若不补，`appearance_lock_zh` 这个必须字段就空着。** 两条路都是错的。

**影响**：

1. **最终提示词集的结构性风险**——SW-007 验收标准是「角色/场景/镜头描述完整、无歧义」（需求文档 L53）；角色外观锚点缺位，直接命中最常见的失败源（跨镜角色漂移，v1.1 L269 明确点名）。
2. **返工最贵**——外观一旦在分镜提示词阶段才第一次被决定，任何一处调整都要求重跑该角色出现的所有镜头。
3. **与「年龄感」相关的地基**——角色年龄段同时决定选角、表演与镜头距离（近景拍儿童与近景拍中年人的构图不同）；梗概层不接住，下游无处对齐。

**建议方向**：

1. 在梗概 `output` 中**新增 `characters[]` 数组**（或在 `protagonist` / `supporting` 内扩键），至少承载：**稳定 id + 年龄段 + 外形要点（发型/服装/关键识别特征）**；客户未给的一律写「未指定」，但**字段本身必须存在**——「写未指定」与「没有字段」是两回事，前者下游可消费，后者下游只能编。
2. 字段命名直接对齐 v1.1 §3.4（`appearance_lock_zh` 语义），避免下游二次翻译。
3. 同步在 `examples/CASE-004_synopsis-case01.md` 补一条「角色外观未指定」的占位示例，把写法固化。

**依据**：`TPL-013_synopsis_v1.yaml` L79–84 / L95–97；`SPEC-002_分镜提示词交付规范-v1.1.md` §3.4 L361 L363 L368。

### D-02 角色无稳定标识，跨阶段一致性校验无锚 ★★

| 项 | 内容 |
| --- | --- |
| 位置 | `output` L79–84（`protagonist.name` 允许填「未指定」）、L95–97（`supporting.name`） |
| 现状原文 | 「主角名（客户未提供则填『未指定』）」（L80）——**当 name 为「未指定」时，该角色在本链路中没有任何唯一标识** |
| 下游要求 | v1.1 §3.4 L361 `character_id`（必须，如 `CHR-01`）、L440 `character_refs`（必须，镜头引用 `characters[].character_id`）；需求 SW-002 验收含「**数字/专名/设定零漂移**」（需求文档 L43） |

**问题（导演视角）**：梗概是**链路最上游**（`stage: synopsis`，manifest L28；v1.1 §3.2 stage_chain 首段 L320）。SW-002 要求跨阶段「专名/设定**零漂移**」——**要校验漂移，先得有一个贯穿全程的稳定标识去比对**。而本模板对角色只给了 `name`，且在用例里 `name` 恰恰是「未指定」（`CASE-004_synopsis-case01.md` L35、L51）。

于是出现一个真实的死结：**主角在梗概里叫「未指定」，到剧本阶段必须起名（SW-005 输出角色表），到分镜提示词阶段又要用 `CHR-01` 去引用**——三段之间**没有任何可承接的键**。SW-002 的「零漂移」校验在此**无锚可校**。

**影响**：

1. **零漂移不可验证**——不是「校验没做好」，而是「**没有校验对象**」；SW-002 的验收标准（需求文档 L43）在这一环无法举证。
2. **下游引用断裂**——v1.1 把引用完整性列为**阻断交付**项（`character_refs` 引用不存在的 `character_id` 即阻断，v1.1 §3.5 L642「引用不存在的 `character_id`」）；源头无 id，下游每个阶段都要**新发明一套编号**，这正是漂移的温床。
3. **与「单人替身法则」冲突**——v1.1 §4.4 L737 要求单角色镜头**必须用具名锚点（角色名或稳定 ID）指向**；源头不给稳定 ID，下游只能靠「角色名」，而角色名在梗概层是「未指定」。

**建议方向**：

1. 在角色结构（`protagonist` / `supporting`，或 D-01 建议的 `characters[]`）中增**稳定标识键**（如 `character_key` / `chr_id`，取值 `CHR-01`…），**与 name 解耦**——name 可以是「未指定」，**标识不可以**。
2. 该标识须写入 `output` 的明文示例与 `examples` 少样本（L116–131），让模型学会「没有名字也要发号」。
3. 在 `CFG-008_manifest.yaml` 的约束清单（L36–39）登记「角色标识稳定、跨阶段不改号」，作为下游 SW-005 / SW-007 的承接约定。

**依据**：`TPL-013_synopsis_v1.yaml` L80 / L96；`SPEC-002_分镜提示词交付规范-v1.1.md` §3.2 L320、§3.4 L361、L440、§4.4 L737、§3.5 L642；`REQ-005_软件级需求文档.md` SW-002 L43；`CASE-004_synopsis-case01.md` L35 L51。

### D-03 「未指定」在视觉层无交接责任定义 ★★

| 项 | 内容 |
| --- | --- |
| 位置 | 硬性约束 L45–47、`unspecified` 字段 L108、`guards` L133–136 |
| 现状原文 | 约束 1：「客户未提供的关键信息，写『未指定』占位」（L47）；`unspecified`：「客户未提供、但下游需要确认的关键信息」（L108）；guard：「输出中出现的所有人名／地名／机构名，必须能……找到来源」（L134） |
| 用例现状 | `unspecified` 实列 4 项：「主角姓名」「妹妹姓名」「失联的具体年数」「失联原因」（`CASE-004_synopsis-case01.md` L68）——**无一项属于视觉锚点** |

**问题（导演视角）**：模板对「未指定」的**义务范围**定义得过窄——`guards`（L134）把它限定在**专名**（人名/地名/机构名），`unspecified`（L108）的语义虽宽（「下游需要确认的关键信息」），但**没有任何规则要求把视觉缺失项放进去**，用例的 4 项也全是叙事项。

后果是：**「未指定」这个机制在叙事层很锋利，到了视觉层直接失效**——角色外形没给 → 不进 `unspecified` → 下游不知道这里有缺口 → 到分镜提示词阶段才发现，只能现场决定。**交接责任没有落在任何一个字段上，就等于没人负责**（这正是本工程 v1.1 已确立的口径：「靠人记着做的事，等于没人做」，v1.1 §8.3 L1411）。

**影响**：

1. **漏斗式掩盖**——缺口在梗概层被「未指定」这个看起来合规的占位**掩盖**，越往下游越难发现，发现时越贵。
2. **违背 SW-004 的边界处理精神**——用例评测第 5 项自评「列出 4 项，覆盖下游剧本阶段必需的姓名与失联设定」（`CASE-004_synopsis-case01.md` L82），口径**只到剧本阶段**，未覆盖视觉锚点，说明这不是疏漏，而是**设计里没有这一层意识**。

**建议方向**：

1. 在硬性约束中**明确「未指定」的两类**：**叙事类**（可留待剧本阶段）与**视觉锚点类**（角色外形/场景空间/光线色调/风格，**必须**在 `unspecified` 中单列）。
2. 把 `unspecified` 的填写规则（L108 附近）从「下游需要确认的关键信息」细化为**可判定的清单**（外形、年龄感、服装、空间类型、光线、风格锚点），并注明「缺失即视为下游阻断输入」。
3. `guards`（L133–136）增一条：**视觉锚点类的缺失不得静默——必须出现在 `unspecified` 中并标明其对下游的影响**（现 L135 只覆盖了「要点无法融入故事」一种情形）。

**依据**：`TPL-013_synopsis_v1.yaml` L45–47 / L108 / L133–136；`CASE-004_synopsis-case01.md` L68 L82；`SPEC-002_分镜提示词交付规范-v1.1.md` §8.3 L1411。

## 4 P1 妨碍可用（2 条）

> 这一级的共同特征：**下游能跑，但跑出来的东西「不受控」——因为源头没给确定性，下游只能自由发挥。**

### D-04 `scenes_outline.beat` 是叙事事件，不是可拍场景 ★

| 项 | 内容 |
| --- | --- |
| 位置 | `output` L98–100 |
| 现状原文 | `{"no": 1, "beat": "该场核心事件（≤40 字）", "purpose": "叙事作用（建立／升级／反转／收束）"}` |
| 用例实证 | 第 1 场 `beat`＝「暴雨夜送单途中，主角在楼道口发现一只受伤的流浪猫」（`CASE-004_synopsis-case01.md` L54）——这是一条**事件陈述**，不是一条**可拍场景描述** |

**问题（导演视角）**：`beat` 字段的语义是「核心**事件**」，`purpose` 字段的语义是「叙事**作用**」——**两个字段都在叙事层，没有一个在拍摄层**。而下游 SW-006 要从「剧本场景」切镜头（需求文档 L52），SW-007 的每一镜必须有明确的**空间类型**。

导演的基本功是「**场景必须自包含**」——写「雨夜的便利店玻璃门内侧」「狭窄的出租屋厨房」，而不是写「在楼道口发现猫」。两者对下游的差别是：

| | 叙事事件（现状） | 可拍场景（下游需要） |
| --- | --- | --- |
| 给出什么 | 发生了什么 | **什么样的空间 + 什么时相 + 什么光** |
| 下游动作 | 必须**自行推导**空间载体 | 直接转译 |
| 跨镜风险 | 每镜各自推导 → **空间漂移**（v1.1 §4.4 L753 要求「用场景自身的两个方向做轴」，无空间载体则轴线无处可立） | 全片共用一套载体 |

用例的 `beat` 恰是**一个反面样本**：「楼道口」是模糊的空间类型（哪栋楼？室内外？光源来自哪？），下游要拍它，必须**补出**空间、时相与光线——而这三样一旦由下游各自补，一致性就没了。

**影响**：

1. **轴线失效**——v1.1 的单人戏用「场景自身的两个方向（窗↔门）」做空间轴（§4.4 L753）；空间载体不定，轴线无从建立。
2. **一致性漂移**——同一场戏在不同镜头里被推导成不同空间，是本工程 v1.1 明确要防的失败源（§3.1 L269）。
3. **`purpose` 的信息浪费**——`purpose` 只写「建立/升级/反转/收束」，未与镜头语言挂钩（如「反转」场在导演上通常需要角度/景别跳级），下游无从承接。

**建议方向**：

1. `scenes_outline` 每场**增 `location`（空间类型）与 `time_of_day`（时相，决定光线）两个子字段**，与 `beat` 并列；`beat` 保留为事件，二者互补。
2. 在 `output` 的字段注释中写清：`location` 须为**可识别的空间类型**（对齐导演「场景自包含」口径），不得只写「门口」「里面」。
3. `purpose` 可补一句下游映射（如「反转场建议预留角度/景别跳级空间」），把叙事作用与镜头语言接上。

**依据**：`TPL-013_synopsis_v1.yaml` L98–100；`CASE-004_synopsis-case01.md` L54；`SPEC-002_分镜提示词交付规范-v1.1.md` §3.1 L269、§4.4 L753；`REQ-005_软件级需求文档.md` SW-006 L52、SW-007 L53。

### D-05 风格锚点断层：`world.tone` 撑不起下游 `style_bible` ★

| 项 | 内容 |
| --- | --- |
| 位置 | `output` L85–89（`world.tone`） |
| 现状原文 | `"tone": "整体气质（如冷峻写实／温暖治愈／荒诞喜剧）"`（L87） |
| 下游要求 | v1.1 §3.3 L331 `style_anchors`（**必须**，**固定 3–5 条**）；L329 `style_prompt_zh`（必须，30–80 字）；L332 `color_palette`（可）；L333 `lighting_default`（应当） |

**问题（导演视角）**：`world.tone` 是**一个叙事气质词**（用例取值「克制温情」），它回答的是「故事什么味道」；下游 `style_bible` 要的是**一组可复用的视觉锚点**（画风/材质/色调/质感，固定 3–5 条）加**色彩板**与**默认光照**（v1.1 §3.3 L343 明示示例：「日式动画电影质感/柔和赛璐璐上色/冷蓝色调/细腻雨丝质感」）。**「气质」到「锚点」之间没有桥，且数量级差一个量级（1 个 vs 3–5 个）。**

更要命的是 v1.1 定了**「锚点封闭」**规则（L344）：`prompt_*` 中**不得出现锚点清单之外的风格词**。这条规则的**前提**是「锚点清单必须先在链路源头被确定」——而本模板**不产出锚点清单**。于是下游要么在下游凭空立一张清单（与「不编造」冲突），要么每镜各自带风格词（直接违反锚点封闭）。

**三条下游锚点的对接核查**（针对本任务第 4 维度）：

| 下游锚点（v1.1） | 必填 | 梗概层对应字段 | 对接结论 |
| --- | --- | --- | --- |
| 角色锚点 `characters[]`（L357–366） | 必须 | `protagonist` / `supporting`（L79–97） | **断层**：缺 id 与外观（见 D-01、D-02） |
| 场景载体（`units[].scene_no` L388 / `shots[].scene_no` L419） | 必须 | `scenes_outline.beat`（L99） | **断层**：只有叙事事件，无空间类型（见 D-04） |
| 风格锚点 `style_bible`（L324–335） | 必须 | `world.tone`（L87） | **断层**：1 个气质词 ≠ 3–5 条视觉锚点，且无色彩/光照 |

**影响**：

1. **风格漂移**——没有源头锚点清单，全片风格在第 3 镜与第 7 镜之间散发（v1.1 L344 的原话场景）。
2. **锚点封闭规则空转**——该规则要落地，必须先有「清单」；清单无来源，规则只能在下游临时补，补法因人而异。
3. **色彩/光照缺失**——`color_palette`、`lighting_default` 在下游是「可/应当」，本可低成本在源头埋下，现状是**空白**。

**建议方向**：

1. 梗概 `output` **增 `visual_style` 字段**（或在 `world` 内扩键），承载：**画风基调 + 主色调 + 光线基调**，字段语义与 v1.1 §3.3 `style_bible` 对齐。
2. 明确该字段是**下游 `style_anchors` 的候选池**，允许「未指定」，但字段须存在；若客户未给风格，下游据此**先向客户确认**，而非自行发明。
3. 与 D-03 联动：风格缺失时须进 `unspecified`（视觉锚点类）。

**依据**：`TPL-013_synopsis_v1.yaml` L85–89；`SPEC-002_分镜提示词交付规范-v1.1.md` §3.3 L324–335、L343、L344；`CASE-004_synopsis-case01.md` L42（`tone`＝「克制温情」）。

### D-06 `unspecified` 扁平字符串数组，不利自动化校验与排期

| 项 | 内容 |
| --- | --- |
| 位置 | `output` L108 |
| 现状原文 | `"unspecified": ["客户未提供、但下游需要确认的关键信息"]` |

**问题（导演视角）**：`unspecified` 目前只是**字符串清单**（用例：`["主角姓名","妹妹姓名","失联的具体年数","失联原因"]`，`CASE-004_synopsis-case01.md` L68）。它**能说明缺什么，但说不清「缺的是下游哪个字段、该由哪个阶段补、是否阻断」**。而本工程已把「靠人记着做的事等于没人做」立为口径（v1.1 §8.3 L1411）——扁平清单正是「靠人记着」的典型形态。

**影响**：跨阶段的一致性校验（SW-002）与交付自检无法**脚本化**消费这份清单；哪些缺口会阻断下游、哪些可以放行，全靠人工判断。

**建议方向**：`unspecified` 改为**结构化对象数组**，每项含 `{field, reason, owner_stage, blocking}`——`field` 指下游对应字段名、`owner_stage` 指应由哪一阶段补齐（synopsis / script / storyboard / shot_prompt）、`blocking` 标明是否阻断下游。这样本字段即可作为**跨阶段缺口台账**，被 v1.1 §8.3 的自检清单直接引用。

**依据**：`TPL-013_synopsis_v1.yaml` L108；`CASE-004_synopsis-case01.md` L68；`SPEC-002_分镜提示词交付规范-v1.1.md` §8.3 L1411。

### D-07 用例评测口径未覆盖视觉锚点下潜，缺口在评测中不可见

| 项 | 内容 |
| --- | --- |
| 位置 | `examples/CASE-004_synopsis-case01.md` L82（评测结论第 5 项）、L68（`unspecified`） |
| 现状原文 | 「✅ 列出 4 项，覆盖**下游剧本阶段**必需的姓名与失联设定」（L82） |

**问题（导演视角）**：用例的评测口径把「边界处理」的达标线**只画到剧本阶段**——4 个待确认项全是叙事项（姓名、年数、原因），**没有一项是视觉锚点**。这意味着：即使 D-01~D-05 的缺口存在，**现用例也会判「通过」**——**评测与真实下游需求之间没有对齐**。

本工程已确立「三层里的前两层必须脚本产出结论」（`examples/README.md` §四 L52），而「无编造」层的脚本口径（README L49）是「抽取输出中所有专名 → 回溯输入」——**视觉锚点不在抽取范围内**，故现有自动化评测同样看不见这类缺口。

**影响**：缺口不写进问题清单 = 没人跟进；这与 D-03 同源，但发生在**评测留痕层**——备案时拿不出「已覆盖视觉锚点下潜」的证据。

**建议方向**：

1. `CASE-004_synopsis-case01.md` 的评测表**增一行**「视觉锚点下潜」：核查 `unspecified` 是否含角色外形/空间类型/光线色调/风格锚点类缺失。
2. `examples/README.md` §四的「无编造」脚本口径（L49）**扩一条**：除专名外，抽查「下游必填字段的缺失是否被标记」。

**依据**：`CASE-004_synopsis-case01.md` L68 L82；`examples/README.md` L49 L52。
