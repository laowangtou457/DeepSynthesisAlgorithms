## 1 评审口径与分级

### 1.1 本轮只评四件事

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **能不能投** | 客户拿到适配文本，原样粘贴进目标模型，能否跑通 |
| 2 | **可不可控** | 跑通之后，运镜／景别／动作／时长是否"照我们要的那样动" |
| 3 | **拍不拍得出来** | 动作与时长是否匹配、主体是否唯一、跨镜是否连续 |
| 4 | **谁发现** | 现有门禁能否在交付前拦住上述问题 |

**明确不评**：法规条款引用准确性、AIGC 元数据字段合规性、标识素材尺寸计算、需求映射完整性。这些层做得好，见 §7。

### 1.2 问题分级

| 级别 | 定义 | 后果 |
| --- | --- | --- |
| **P0 阻断级** | 不改则交付物**投喂即错**或**结构性不可用** | 客户拿到手用不了／用错 |
| **P1 妨碍可用** | 都能跑，但不改则**生成结果不可控** | 客户能出片，但出不了想要的片 |
| **P2 质量提升** | 影响专业度与长期可维护性 | 能用，但每接一个模型都要重新发明轮子 |

## 3 P0 阻断级（6 条）

> 这 6 条的共同特征：**不是"缺"，而是"错"或"空"。** 缺的东西客户会问你要；错的东西客户会照做。

### D-01 运镜写法与 H3 官方规范冲突 ★

| 项 | 内容 |
| --- | --- |
| 位置 | §3.6.2、§5.4 P0-1、§9 适配样例 |
| 现状原文 | `[Push in]`、`[Static shot]`；§5.4 写「**支持显式镜头指令**（方括号形式，如 `[Push in]`）」，并规定「适配时把 `camera.move` 映射为对应指令并**前置**」 |

**问题（导演视角）**：H3 **不使用方括号指令**。它的运镜是**英文自然语言末句**，且必须写成「**类型 + 幅度 + 速度**」三元组。客户照抄粘贴后，`[Push in]` 会被模型当作**画面正文**处理——轻则忽略运镜（镜头不动），重则把方括号内容理解成"画面里要出现的文字"。

**建议方向**：

1. 废弃 `camera_directive_map` 一类方括号映射；
2. 适配输出改为**末句自然语言**，例如：
   `The camera pushes in with small amplitude at slow speed.`
3. 幅度／速度**按官方建议仅在需要强调时出现**（`small`/`large`、`slow`/`fast`；`medium`/`normal` 省略），不要每句都挂；
4. `Static Shot` / `POV` **不得携带幅度与速度**。

**依据**：`h3_compiler.py` → `CAMERA_VERB`（**官方 20 类**）、`AMPLITUDE`、`SPEED`、`NO_AMP_SPEED = {"Static Shot", "POV"}`

### D-02 负向词自相矛盾，样例会把负向词写成正向正文 ★★

| 项 | 内容 |
| --- | --- |
| 位置 | §3.5 `negative_prompt`、§5.4 P0-1、§9 H3 适配样例 |
| 现状原文 | §5.4 说「以平台实际支持为准；**不支持时把 `negative_prompt` 转写为正向约束句**」；但 §9 的 H3 样例里直接写着 `（负向：雨势过大、现代建筑）` 和 `（负向：直视镜头、微笑）` |

**问题（导演视角）**：**这是全篇最危险的一处。**

H3 基础模式是**三字段结构**，**没有 Negative 字段**。§9 样例里那两行"（负向：…）"如果被客户原样粘贴——模型会把它理解成**画面要出现"雨势过大"和"现代建筑"**。**负向词直接变成正向指令**，客户拿到的是他明确不要的东西。而规范自己在 §5.4 又写了"不支持则转写为正向约束句"——**正文与样例自相矛盾**。

**建议方向**：

1. §3.5 中 `negative_prompt` **不得列为通用字段**，改为「**按模型能力可选**」；
2. 明确规定 H3：**删除该字段**，改在正向描述里写成「保持画面…」「画面无…」；
3. §9 示例必须重写，**不得残留任何形式的负向字段**——包括用中文括号伪装的写法；
4. §7.3 自检增一条：「目标模型不支持负向字段时，交付文本中不得存在负向残留」。

**依据**：H3 基础模式三字段（`integrated_multimodal_description` → `overall_soundscape` → `non_diegetic_music`），无 Negative 字段

### D-03 中英双写「以中文为主」与 H3 语言约束方向相反 ★

| 项 | 内容 |
| --- | --- |
| 位置 | §3.6.4、§5.4 P0-1 |
| 现状原文 | §5.4 P0-1：「中文描述可读性好；**建议中英双写并以中文为主**，专业术语保留英文」 |

**问题（导演视角）**：H3 的硬约束是——**框架描述里中文只允许出现在 `<d>…</d>` 与英文双引号内的画面文字**。若按「以中文为主」投影，H3 适配文本会**整段判违规**：要么被拒，要么效果完全不可预期。§5.3 适配 10 维的第 1 维「语言倾向」**被当成了自由选项**，但它其实是**模型的硬约束**。

**建议方向**：

1. §5.4 P0-1 改为：「**H3 以英文为基底**（`prompt_en`），中文仅用于 `<d>` 内的台词」；
2. §5.3 第 1 维补一句约束：「**当目标模型对语言位置有硬约束时，语言倾向不得覆盖该约束**」；
3. §3.6.4 补一句：「`prompt_zh` 用于人工阅读与中文模型投喂；**英文优先模型以 `prompt_en` 为投喂源**」。

**依据**：`h3_compiler.py` 第 804–811 行 —— 框架描述里出现中文即记 issue；画面可见文字必须用**英文双引号**

### D-04 只设了时长上限、没设下限；示例包已踩线 ★

| 项 | 内容 |
| --- | --- |
| 位置 | §3.5 `duration_ms`、§5.3 第 6 维、§5.5、§9 demo_pack |
| 现状原文 | §5.5 只写「单镜头时长 **> 模型上限** → 按语义边界拆分」 |

**问题（导演视角）**：H3 的时长是 **4–15 秒整数**，**下限同样是硬约束**。而 §9 示例包的两个镜头都写着 `"duration_ms": 3000`——**低于 H3 下限**。客户把示例当模板，**第一镜直接失败**。

**下限比上限更容易踩**：分镜习惯天然写短镜（2–3 秒切一次），而视频模型的下限普遍在 3–4 秒。这份规范防住了"太长"，漏掉了"太短"。

**建议方向**：

1. §5.5 增一行：「**低于模型下限** → 合并相邻镜头，或延长至下限（**只延长时长，不改画面**）」；
2. `duration_ms` 增**整秒校验**——模型侧不接受毫秒精度，毫秒会制造虚假的精细感；
3. §9 示例包改为 ≥4 秒；
4. §5.3 第 6 维由「单镜头时长上限」改为「**单镜头时长上下限**」。

**依据**：`MIN_DUR, MAX_DUR = 4, 15`

### D-05 缺「生成单元」结构，单镜交付在数学上结构性不达标 ★

| 项 | 内容 |
| --- | --- |
| 位置 | §3.1 顶层结构、§3.5 `shots[]` |
| 事实核查 | 全文检索「单元」**仅 2 次命中**，且均为他义（"最小生成单元"的术语定义、"合并单元格"） |

**问题（导演视角）**：项目铁律是 **每个生成单元 ≥2 镜**。质量门的运镜类型数门槛是：

```
运镜类型数要求 = min(5, max(2, ceil(镜数 / 4)))
```

**分母就是镜数。** 所以 **1 镜单元在数学上必然不达标**——这不是"建议"，是结构性失败。规范以 `shot` 为唯一粒度，等于把"**每次只生成一个运镜**"固化进了交付物。

**建议方向**：

1. 在 `shots` 与包之间**增加一层「生成单元 / unit」**（建议每单元 **2–3 镜**，3 镜是实测天花板）；
2. 规定 **unit 内运镜类型不得重复**，由单元承担"运镜丰富度"责任；
3. §7.3 自检增一条：「**不得存在单镜生成单元**」。

**依据**：`audit_shots.py` → `need = min(GATE["运镜类型数"], max(2, -(-rep["shots"] // 4)))`

## 4 P1 妨碍可用（9 条）

> 这一级的共同特征：**改不改都能跑，但不改则客户拿到的东西「能动，但不是我们要的那样动」。**

### D-07 运镜只有「类型 + 速度」，缺「幅度」

| 项 | 内容 |
| --- | --- |
| 位置 | §3.5 镜头字段表 |
| 现状 | `camera` 对象只有三个键：`move` / `speed` / `angle` |

**问题**：**推 ≠ 猛推**。同一个 `push_in`，可以是从容缓推，也可以是骤然急推——画面情绪完全不同。规范自己已经意识到速度是个维度（设了 `camera.speed`），却漏掉了**幅度**。而 H3 的官方运镜写法是**三元组**：类型 + 幅度 + 速度。

**建议方向**：

1. `camera` 增 `amplitude`，取值 `small` / `medium` / `large`；
2. 明确声明：`Static Shot` / `POV` **不得携带幅度与速度**；
3. 幅度与速度**仅在需要强调时输出**（对应官方建议，`medium` / `normal` 省略）。

**依据**：`AMPLITUDE = {"small": "with small amplitude", "large": "with large amplitude"}`、`SPEED`、`NO_AMP_SPEED = {"Static Shot", "POV"}`

### D-08 运镜缺「起点—路径—终点」

| 项 | 内容 |
| --- | --- |
| 位置 | §3.5 `camera.move`、§3.6.2 运镜枚举 |

**问题**：`camera.move` 只是一个**类型标签**。`push_in` 说不清三件必要的事：**从哪里推**、**推多少**、**停在哪**。缺了这三点，模型只会「随便动一下」，客户永远拿不到「推到眼特写定住」这种确定性结果。

**建议方向**：

1. `camera` 增 `from` / `to`（或 `start_frame` / `end_frame` 的运动描述）；
2. 至少在 `prompt_*` 的要素顺序里，把运镜一项明确为「**运动描述**」（起点 → 路径 → 终点），而不是「运动类型」；
3. 简单运镜至少给**起点与终点**；复杂运镜给**起点 → 中间 → 终点**。

### D-09 缺光学维度（焦距 / 景深 / 焦点）

| 项 | 内容 |
| --- | --- |
| 位置 | §3.5 字段表、§3.6 词表 |
| 事实核查 | 全文检索「光学」**命中 0 次** |

**问题**：镜头语言的八维里，「光学」与「画面结果」是独立的两维——但这份规范**没有任何字段承载它**。这不是作者写漏，而是**结构上没地方写**。

后果是可预测的：客户按此规范产出的包，**必然复现原始稿「光学 0%」的分布**。而且缺的不只是光学——**构图 / 轴线 / 光线**同属此列（原始稿分别为 2% / 0% / 20%）。

**建议方向**：

1. `camera` 增 `optics`，建议取值：`deep_focus` / `shallow_focus` / `rack_focus`（焦点变化）/ `long_lens_compression`（长焦压缩）/ `wide_angle_distortion`（广角畸变）；
2. 同步在 §3.6 补**光学词表**；
3. 与 D-06 的质量门挂钩：光学覆盖率是门禁项之一（阈值 ≥30%）。

### D-10 缺「动作起止状态」与「动作复杂度—时长预算」

| 项 | 内容 |
| --- | --- |
| 位置 | §3.5 `prompt_zh` / `duration_ms` |

**问题**：规范给了**动作描述**的位置（就在 `prompt_zh` 里），但没给**动作状态**的位置，也没有任何「动作复杂度 ↔ 时长」的关联校验。

导演的基本功是：**一个 Clip 只服务一个核心动作**，且必须写清**开始 / 核心变化 / 结束**三段状态。缺了它，最常见的翻车是——**3 秒里写了一个 8 秒才能完成的动作**，模型只能给你一个糊掉的中段。

**建议方向**：

1. 增结构化字段 `action`：`{start, change, end}`；
2. 给出**动作复杂度—时长参考表**（示例口径）：

| 动作类型 | 建议最短时长 | 超出时处置 |
| --- | --- | --- |
| 单一姿态或表情变化 | 2–3s | — |
| 单一位移（走、转身） | 3–5s | 拆镜 |
| 位移 + 情绪变化 | ≥6s | 拆镜 |
| 复合动作（转身 + 出手 + 落地） | ≥8s | **必须拆镜** |

3. 与 D-04 的时长上下限校验联动。

### D-11 缺「台词—时长」校验，语速必然超标

| 项 | 内容 |
| --- | --- |
| 位置 | §3.5 `dialogue`、§3.7 校验项 |

**问题**：规范有 `dialogue` 字段，但它与 `duration_ms` **没有任何联动校验**，§7.3 的门禁里也没有这一项。

**实测口径**：中文语速约 **6.5 字/秒**，**超过 9 字/秒即不可行**（配音赶不上，或必须变速导致失真）。

**后果最贵**：台词念不完，客户一投喂就发现，只能回改——而回改意味着**动画面**，是所有处置里成本最高的一种。

**建议方向**：

1. §3.7 增校验项：「`dialogue` 字数 ÷ (duration_ms / 1000) ≤ 9」，超标**提示并给出建议时长**；
2. 处置口径**限定为只延长时长、不改画面**（延长窗口是唯一低成本的解法）；
3. §7.3 自检增列该检查项。

### D-12 适配 10 维里没有「声音结构」

| 项 | 内容 |
| --- | --- |
| 位置 | §5.3 适配维度（10 项） |
| 事实 | 10 维中无一项涉及声音或音轨 |

**问题**：H3 是**三字段**结构，其中 `overall_soundscape`（环境音）与 `non_diegetic_music`（画外配乐）是**独立字段**。而规范把 `sfx` 与音乐信息散落在各个 `shot` 里——投影到 H3 时**没有任何机制把它们聚合起来**，结果是这两条音轨**丢失或全空**。

**建议方向**：

1. §5.3 增**第 11 维「声音组织方式」**：单字段合并 / 分轨字段 / 逐镜标注；
2. 明确 H3 适配需**跨镜聚合成两条音轨**，并规定聚合规则（环境音取并集去重；配乐按段落归并）；
3. 在 `meta` 或新增块中增 `soundscape` / `music` 两个包级字段，作为聚合容器。

### D-13 转场只有入点，且无跨模型映射

| 项 | 内容 |
| --- | --- |
| 位置 | §3.5 `transition_in`、§5 适配 |
| 现状 | `transition_in` 值域 `cut` / `fade_in` / `dissolve` / `wipe`；**无 `transition_out`** |

**问题**：两层。

**第一层**——衔接只写一侧（后镜的入点）。相邻两镜之间，容易「两头都写」（互相矛盾）或「两头都不写」（衔接丢失）。

**第二层，更严重**——H3 只有 **5 条官方剪切短语**，而且都是「切」这一类：

```
the camera cuts to   /   the shot cuts to   /   the shot transitions to
the shot changes to  /   the shot switches to
```

**`fade_in` / `dissolve` / `wipe` 在 H3 里没有对应写法。** 客户按 `dissolve` 投 H3，无从下手。

**建议方向**：

1. 增 `transition_out`，或明确「衔接由**后一镜的 `transition_in`** 单侧表达」并写进填写规则；
2. 增**转场映射表**：通用值 → 各模型字面或句法 → **不支持的降级写法**（如 `dissolve` 在 H3 降级为 `the shot transitions to`）；
3. 值域与官方短语对齐——**不得出现官方 5 条之外的自造剪切短语**。

**依据**：`CUT_PHRASES`（仅 5 条）

### D-14 Seedance 适配样例未采用项目已确立的写法

| 项 | 内容 |
| --- | --- |
| 位置 | §5.4 P0-2 Seedance、§9 适配样例 |
| 现状 | 一段平铺中文散句，无权重、无负向行、无素材引用 |

**问题**：项目里**已经有实测可用的 Seedance 写法**（见 `07-提示词工程/悬崖吊桥刀战_Seedance提示词集.md`），与规范样例不一致：

| 维度 | 项目已确立 | 规范样例 |
| --- | --- | --- |

**建议方向**：P0-2 样例按四段结构重写，补权重语法与 `Negative prompt:` 行，并说明权重值的取用范围。

### D-16 负向词表缺视频专属项

| 项 | 内容 |
| --- | --- |
| 位置 | §3.3 `negative_global`、§9 示例 |
| 现状 | `lowres` / `blurry` / `watermark` / `text` / `extra fingers` / `deformed` / `extra limbs` |

**问题**：这七个词全是**图像时代**的负向词。视频特有的两大类伪影**一个都没有**：

- **时域伪影**：闪烁（flicker）、抖动（temporal jitter）、帧间不一致；
- **形变延续**：穿模（clipping）、物体形变或融化（morphing）、肢体跨帧跳变。

**建议方向**：负向词表按三类组织——**通用图像项 + 视频时域项 + 场景专属项**，并给出每类的建议默认值。

### D-17 风格锚点缺「数量规则」

| 项 | 内容 |
| --- | --- |
| 位置 | §3.3 `style_bible` |

### D-18 `camera.angle` 混装了两个正交维度

| 项 | 内容 |
| --- | --- |
| 位置 | §3.5 `camera.angle`、§3.6 |

**问题**：值域 `eye_level` / `high_angle` / `low_angle` / `overhead` / `dutch` 里——前四个是**机位高度角**，`dutch` 是**摄影机轴向（roll）**。两者正交，不该塞进同一个枚举。

**后果**：**无法同时表达「低角度 + 荷兰角」**——而这恰是武侠与悬疑最常用的组合（仰拍 + 倾斜 = 压迫与失衡）。

**建议方向**：拆为 `camera.height`（`eye_level` / `low` / `high` / `overhead` / `ground`）与 `camera.roll`（`level` / `dutch` / `roll_cw` / `roll_ccw`）。注意 H3 侧 `Roll Clockwise` / `Roll Counterclockwise` 是**独立运镜类型**，映射时需说明归并规则。

### D-19 适配文件的「首行标识」与「可投喂性」冲突

| 项 | 内容 |
| --- | --- |
| 位置 | §5.7 适配输出格式规范 **对** §8.2 各格式标识注入 |
| 冲突 | §5.7 要求适配文本是「**纯文本提示词**」、不含元数据；§8.2 要求 **TXT 首行必须有显式标识** `【AI生成内容】…` |

**问题**：客户要投喂，最自然的动作是**全选复制**。这一下就把 `【AI生成内容】本文件由AI生成…` 一起粘进模型——**生成出来的画面里会真的出现这行字**。合规做对了，可用性做没了。

**建议方向**：适配文件做成**两段式**：

```
【AI生成内容】本文件由AI生成，已经过合规验证        ← 标识区（标注「请勿复制」）
════════════ 以下为提示词区，请从此行以下复制 ════════════
━━━ 镜头 S01-SH001 ━━━
（纯提示词内容）
```

**两段都保留**——合规不掉、可投喂性也保住。并在文件头用一句话写清复制方法。

### D-20 缺「枚举 — 各模型中文字面 — 各模型英文句法」三向映射表

| 项 | 内容 |
| --- | --- |
| 位置 | §5.3 `shot_vocab.yaml`、§3.6 |

**问题**：现有映射只到「维度 → 规则」这一层（如「运镜表达方式：自然语言 / 指令语法 / 不支持」），**没有逐值的对照词典**。

### D-21 缺「任务类型」维度，只覆盖一种生成形态

| 项 | 内容 |
| --- | --- |
| 位置 | §3.1 顶层结构、§5 |
| 事实 | 全文无 `task_type` 一类字段 |

**问题**：H3 有 **6 种任务类型**，这份规范只覆盖了「文生 / 首帧」这一种：

```
keyframe completion（关键帧补全）      reference generation（参考生成）
video editing（视频编辑）              video continuation（视频续写）
audio reuse（音频复用）                audio reference（音频参考）
```

**后果**：客户要做「视频续写」「视频编辑」「音频复用」时，规范给不出任何可交付形态。

**建议方向**：

1. `meta` 增 `task_type`；
2. 补 Ref2VA 分支结构（六段）与素材上限表；

### D-22 多主体镜次缺约束（主体唯一性）

| 项 | 内容 |
| --- | --- |
| 位置 | §3.4 `characters[]`、§3.5 `character_refs` |

**问题**：`character_refs` 是数组，**允许一镜多角色**，但规范里**没有任何「主体唯一性」规则**。

导演的基本要求是：**画面主体唯一明确**。多主体同框时如果没做画面区隔，AI 视频会**身份互相污染**——两个角色的脸开始互相「借」特征。这是 AI 视频最典型的翻车点，而且**一旦出现就是整段报废**。

**建议方向**：增「**单镜主体上限**」与「**多主体区隔要求**」（前后景分离 / 左右分侧 / 一主一虚），或直接沿用项目已确立的**单人替身法则**。

## 6 结构性缺口：三条缺失的轴线

前面 23 条是逐点意见。如果只让我说一句，这句是核心：

> **这份规范只有一条轴（单镜），而「可生成、可控制」需要三条轴。**

| 轴 | 应当有 | 现状 | 后果 |
| --- | --- | --- | --- |
| **纵向 · 任务类型轴** | 文生 / 首帧 / 参考生成 / 续写 / 编辑 / 音频复用 | 只有「文生 + 首帧」 | **一半以上的生成形态没有交付路径**（D-21） |
| **横向 · 生成单元轴** | 单元（2–3 镜）→ 镜 | 只有「镜」 | **单镜交付在数学上结构性不达运镜门槛**（D-05） |
| **深度 · 质量轴** | 格式门 + 合规门 + **镜头语言门** | 只有前两道门 | **全绿交付，但全片固定机位**（D-06） |

补上这三条轴，这份规范才从「**合规交付包规范**」变成「**可生成、可控制的交付包规范**」。
