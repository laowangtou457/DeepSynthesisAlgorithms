## §0 评审结论

**总判断：文档的「内容质量」已明显高于本项目同期其他工程件——`SYS-001`~`SYS-021` 编号连续无缺号、八项必备字段 21×8 无空缺、来源列均指向真实上位依据（法规条文号 / 国标号 / 业务决策记录 / 交付物号）、合规承接（标识、内容安全、日志留存、备案主体与范围、微短剧专项义务）已逐条落到条目而非仅写在叙述里，V1.8 以来的整改方向正确且多数到位。本次不判为「通过」，原因是三个结构性问题尚未闭合：**

1. **§4 系统边界「包含」侧与 §5 二十一条目集不一致**（`RS-01`）——「包含」仅列 8~10 项能力，21 条中有 **11 条**（`SYS-004/007/008/010/011/012/013/015/017/019/020/021` 中的多数）在边界三分中**无任何归属**，导致「不包含」的补集不可判定、系统边界**不闭合、不互斥**。系统级是业务与合规的落点，此项不闭合会直接波及备案材料中「系统功能范围 / 外部依赖」的陈述准确性。
2. **外部依赖登记不全且性质混杂**（`RS-02`）——请求书点名的四类依赖中，**宿主平台及其 ICP 备案资质、模型权重、第三方词库 / 内容安全资产三项未进 §4**；而「算法备案申报材料（`02-备案申报`）」「法务 / 合规审核支持」实为**内部产物与内部资源**，被登记为外部依赖；§4 与 §6 两处重复登记且互不互指，**均未写失效后果与替代路径**。宿主平台是本系统**唯一公网入口且其资质由平台持有**，一旦不可得则全系统无法对外服务——这是本项目等级最高的外部依赖，却不在外部依赖表内。
3. **层级归属缺「跨层规则」**（`RS-06`，兼答待议 B）——`SYS-009`（标识）、`SYS-015`（性能）、`SYS-017`~`SYS-019`（导出 / 脱钩 / 合规声明）与软件级 `SW-012~014` / `SW-022` / `SW-026` / `SW-101~103` 存在**整段级重复**；而判据底座 §二 归属表明确把「生成内容需带显式与隐式标识」「单次同步合成响应时间 < 3s（P95）」判为**软件级**。判据只回答「一句话归一层」，未回答「同一要求可否多层承载、哪层是入口」，责任因此无处安放。

**分级统计：P0 阻断级 2 条、P1 妨碍可用 11 条、P2 质量提升 6 条，合计 19 条。** 另有 **11 项「已核查、不成立」**（见 §4），其中 3 项为请求书 §3.1 指定必答。

## §3 P2 · 质量提升（6 条）

### RS-14 §5 前言的「简称约定」只覆盖 5 部法规，未覆盖本文档实际出现的标准号与内部编号，来源无法在本文档内解析

- **问题**：§5 前言（第 88–90 行）只定义了「规定 / 暂行办法 / 标识办法 / 生态治理规定 / 微短剧办法」五个简称，而正文与决策记录还引用了 `GB 45438—2025`、`GB/T 45652—2025`、`GB/T 45654—2025`、`GB/T 45674—2025`、`LAW-001/006/007/014/015/016/019/020`、`SEC-007 / SEC-013`、`D-008/009/011`、`REQ-001 / REQ-005 / REQ-006` 等，读者须逐个下钻才能解析。
- **证据**：`REQ-004` 第 88 行（五部法规简称）；正文引用示例：第 105 行「个人信息保护法（`LAW-001`）」「网络数据安全管理条例（`LAW-020`）」；第 106 行「GB/T 45654—2025 附录 B……`SEC-007_人工签核规程.md`……`SEC-013_达标指标对照表.md`」；第 109 行「GB/T 45652—2025 / GB/T 45674—2025」；第 119 行「`LAW-007` 第二十四条，经 `LAW-006` 第十九条引致」；第 195 行「GB 45438—2025」；第 123 行「`REQ-005` §5」「`HW-001`」。
- **影响**：外部评审与备案核查方需频繁跳出本文档；`LAW-xxx` 尤其无法就地解析（须进 `08-法律法规依据`）。
- **建议方向**：把 §5 前言扩为**「本文件引用代号一览」**（代号 → 全称 → 所在目录），并保持随新增引用同步更新。

### RS-15 `SYS-013` 验收标准第 ① 项把「待办事项」写成验收条件，不可判定通过与否

- **问题**：验收标准应是判定条件，而该条写的是「**已明确并成文**」这一尚未完成的动作。
- **证据**：`REQ-004` 第 121 行 `SYS-013` 验收第 ① 项：「**微短剧分类分层备案与发行许可的办理主体、办理时点已明确并成文**（见 §6 外部依赖，含外部审核周期）」。
- **影响**：验收时该项只能判「未完成」，无法判「已完成」；同时把办理任务混在验收标准里，责任人与目标日期无处登记。
- **建议方向**：把「办理主体 / 时点」作为**带责任角色与目标日期的约束或里程碑**登记于 §6 或 §7 决策记录，`SYS-013` 验收改为可判定条件（如「交付前具备办理主体与时点的书面确认」）。

### RS-16 `SYS-015` 的「暂定值」无转正机制；§6 未登记项目周期，「何时必须转正」无时点

- **问题**：`SYS-015` 声明性能为暂定值、「随开发期实测校准」，但**未定义校准时点、批准人、以及实测不达标时的处理**；`REQ-004` §6 亦无「周期」约束行。
- **证据**：`REQ-004` 第 123 行「**当前为暂定值，随开发期实测校准**（团队规模：1 名开发）」、状态「内部确认（暂定值）」；`REQ-004` §6 第 132–147 行**无周期 / 里程碑行**；周期事实仅存于 §1.3 `C-005`（第 40 行「周期 4–8 周至可提交｜瓶颈在数据准备与审核等待」）与 `REQ-006` §1.3 / §9 里程碑（`REQ-006` 第 80、337–341 行）。
- **影响**：暂定值长期挂账 → 备案材料中的性能承诺始终是暂定值；无转正时点则无法判断何时应冻结基线。
- **建议方向**：为暂定值补「校准触发条件 + 目标时点 + 批准角色 + 未达标处置」；§6 增设「周期 / 关键时点」行，登记 `C-005` 周期口径并与备案提交时点对齐。

### RS-17 目标形态以同业产品名作参照，不可判定，且在对外举证中不适宜作为需求表述

- **问题**：目标形态三处均以某同业产品名作参照（「类似某产品的微信小程序 + 网页」），属**不可判定的需求表述**；在面向监管的文档中，以他方产品名定义自身形态，既无法验收也不利于举证。
- **证据**：`REQ-004` 第 32 行 §1.2「目标形态｜类似某同业产品的**微信小程序 + 网页**形式，对外公开传播」；第 141 行 §6「目标形态｜类似某同业产品的微信小程序 + 网页，对外公开传播 → 触发影视创作合规 + 算法备案双重义务」；第 161 行 `SYS-Q5`「目标播出渠道的具体形态｜✅ 已确认：类似某同业产品的微信小程序 + 网页」；下层 `REQ-005` 第 116 行 `SW-I07`「面向「某同业产品」形态的小程序 + 网页端服务接入」、第 158 行 `SW-110` 同口径。
- **影响**：验收时无法判定「做到什么程度算达到目标形态」；对外材料中以他方产品名描述自身，易被质疑需求不严肃或形态定义不清。
- **建议方向**：改为**功能形态描述**（端数、必备能力、是否对外公开传播、是否需备案资质），同业参照仅作为说明性括注并注明「非验收依据」。

### RS-18 §4「包含」写「版权提示」，§5 与下层为「版权校验 / 相似度检测」——同一能力的用词强度不一致

- **问题**：系统边界对同一能力的表述强度弱于条目与下层实现（提示 vs 校验 / 检测），边界与条目不互洽。
- **证据**：`REQ-004` 第 78 行 §4 包含栏末项「**版权提示**」；第 122 行 `SYS-014`「版权与知识产权管理……**提示词/剧本生成不侵害他人知识产权**」，验收「改编来源声明/授权核验机制；**相似度风险可提示**」；`REQ-005` 第 86 行 `SW-015`「版权校验｜**检测**生成内容与受保护作品的**相似度**、改编侵权风险**提示**」。
- **影响**：边界表述若被引为范围依据，会低估该项能力（只做「提示」vs 实际含「检测」），影响工作量估计与举证口径。
- **建议方向**：统一为「版权校验（相似度检测 + 风险提示 + 改编来源声明）」，使 §4 与 `SYS-014` / `SW-015` 同一表述。

### RS-19 关联列语义混用（同层条目 / 下层条目 / 交付物 / 法规 / 目录混列），无法机检，也不利于自动追溯

- **问题**：「关联」列同时承载 `SYS-xxx`（同层）、`SW-xxx`（下层）、`D-xxx`（交付物）、`LAW-xxx`（法规）、目录路径（`09-合规资料库/05-台账与制度`）五类语义，无类型标注，机器无法区分「本条的下层承接」与「相关材料」。
- **证据**：`REQ-004` 第 96 行 `SYS-001` 关联＝「D-011、C-001」（交付物 + 前提结论）；第 105 行 `SYS-004` 关联＝「09-合规资料库/05-台账与制度、SW-019」（目录 + 下层）；第 121 行 `SYS-013` 关联＝「`LAW-014`、SYS-009、SYS-016」（法规 + 同层）；第 125 行 `SYS-018` 关联＝「SYS-016、SYS-017、SW-025、SW-026」（同层 + 下层）；第 112 行 `SYS-020` 关联＝「SYS-010、SW-027、SW-021」（同层 + 下层）。
- **影响**：无法编写机械化的追溯完整性检查（如「每条 SYS 是否至少有一个 SW 承接」），跨层一致性只能靠人工通读——这正是 `RS-08` 类问题长期未被发现的原因。
- **建议方向**：关联列统一采用**类型前缀**（如 `下层：SW-027 / 同层：SYS-010 / 交付物：D-018 / 依据：LAW-014`），使追溯检查可脚本化；此项与判据底座 README §五.1 模板的列定义宜一并修订。

## §5 请求书 §3.2 三个待议项 · 专门回应

### 待议 A：主登记的项目级条目（`F-xxx` / `N-xxx`）与层级条目（`SYS-` / `SW-` / `HW-`）是否需要显式映射表？

**结论：应补，但不必全量——建议补一张「最小映射表」，覆盖三类高风险条目即可。**

**判断依据**

1. **文字描述在当前规模下已接近承载上限，且缺口可举证**。`REQ-006` §2.3（第 105–135 行）对三层的登记是「编号范围 + 文档 + 状态 + 已分配编号名称串」，**无条目级对照**。而项目级条目已有 **F-001~F-306（21 条）+ F-101~F-103（3 条）+ N-001~N-009（9 条）**共 33 条，与层级条目（`SYS-` 21 / `SW-` 28+18 / `HW-` 18）之间**无任何显式对照**。
2. **缺口已经在下游被如实记录**。`REQ-005` 第 40 行明确写：「**「无对应 SYS 条目」本身即为待议 A（主登记与层级条目的映射）的实证，如实暴露、不强行挂靠**」——软件级已用「来源」列填 `架构约束（REQ-006 §5）` 或 `REQ-006 §4 N-xxx` 来**绕过**系统级（如 `SW-104`/`SW-105` 来源＝架构约束、`SW-106` 来源＝`N-006`、`SW-108`/`SW-109` 来源＝`N-008`/`N-009`）。这说明**缺映射已在事实上造成跨层挂靠混乱**：项目级非功能条目被下层直接引用，而系统级对此无感知。
3. **已发生实际口径漂移**（两次）：① 导出格式 4 种 vs 5 种（`REQ-004` §8 V1.9 行，登记 `ISSUE-016`）；② `SYS-015` 的性能值与 `N-001~N-003` 数值一致但**无映射关系可查**——若任一侧改动，无法判断另一侧是否需同步。
4. **「最小映射表」的可行边界**（不必全量 33×N）：只需覆盖——① **合规类**：`F-204` / `F-205` / `F-206` / `F-207` ↔ `SYS-009` / `SYS-006` ↔ `SW-012~014` / `SW-016` / `SW-017`；② **非功能类**：`N-001~N-003` ↔ `SYS-015` ↔ `SW-101~103`（与硬件 `HW-001`）；③ **无下层承接项**：`F-101~F-103`（模板库）、`N-004` / `N-005`（可维护性 / 可观测性）——显式标注「**无层级承接 + 原因**」。
5. **配套动作**：软件级 §2 功能表**回填 `F-xxx`**（目前仅 §5 非功能表回填了 `N-006~N-009`），使双向可查。

### 待议 B：层级归属判据对「同一要求的多层承载」是否够用？

**结论：不够用。应补跨层规则，且规则形态应为「同一要求可多层承载 + 显式指定入口层」，而非维持「唯一归层、其余层只引用」。**

**判断依据**

1. **「其余层只引用」在本项目已被证明不可行**。若严格执行「唯一归层」，则：标识（判为软件级）会使系统级**无法承接其法规来源**（`SYS-009` 的来源全部是法规条文），而备案举证恰恰要求系统级呈现「受什么外部约束」；性能（判为软件级）会使系统级**无法登记总体指标**，而 README §二 判断表本身就把「性能容量总体指标」列为系统级典型内容（`SYS-015`）——**归属表内部已含张力**（第 35 行典型内容含「性能容量总体指标」，第 44 行又把响应时间判为软件级）。
2. **本项目已事实按「多层承载」运行，且口径一致、并未冲突**：`SYS-009`（义务来源，法规条文）＋ `SW-012/013`（实现）；`SYS-016`（责任边界）＋ `SW-014/SW-026`（实现）；`SYS-015`（指标登记）＋ `SW-101~103`（口径与验证）。**这些组内并未出现数值或阈值冲突**——说明问题不在「多层承载」本身，而在**缺少「入口层」与「分工声明」**。
3. **真正出问题的是「整段复制」而非「分层承载」**：`SYS-019` 与 `SW-026`、`SYS-018` 与 `SW-014` 是**近乎逐句复制**（`RS-07`），根源是没有规则说明「同一要求在两层各写什么」，于是每层都把整条要求抄了一遍。
4. **建议的跨层规则（可直接进 `README` §二）**：
   - **入口层＝系统级**：凡有外部依据（法规 / 国标）的要求，**义务的来源、责任归属、合规边界一律在系统级登记**；
   - **实现层＝软件级**：实现方式、数据、接口、异常处理、判据与测量口径在软件级登记；
   - **系统级条目必须写明其对应的下层条目编号**（现已部分做到，如 `SYS-002`→`SW-001~008`），**未写明者视为断链**；
   - **同一要求在两层不得整段复制**：系统级只写「义务 + 边界 + 对应下层编号」，软件级写「实现 + 判据」；
   - **硬件级仅在系统级已登记物理资源约束时**才展开（`SYS-015` → `HW-001` 为正例）。
5. **一句话结论**：判据表从「**一句话归一层**」升级为「**一句话定入口 + 分层写什么 + 必须互指**」，即可覆盖本项目的天然跨层要求，无需否定多层承载。

### 待议 C：系统边界的「外部依赖」是否应给出「失效后果 + 替代路径」？

**结论：应升级为「依赖 ｜ 失效后果 ｜ 替代 / 降级路径 ｜ 是否阻断上线」四列，并强制区分「阻断」与「可降级」两类。**

**判断依据**

1. **本项目的外部依赖恰好横跨两种性质，用同一套写法必然失真**：
   - **阻断型（不可降级）**：宿主平台及其 ICP 资质（唯一公网入口，`SW-110` 明写「对外经宿主平台统一入口」）、微短剧分类分层备案与发行许可（决定能否「对外公开传播」）、模型权重（无基座则无生成能力）。
   - **可降级型**：第三方词库 / 内容安全资产规模（未达国标门槛时影响 `SYS-005` 的规模门槛项，但可用更严的拦截策略 + 人工复核降级运行）、下游 AI 视频生成工具适配（`SYS-Q18` 已定为通用规范 + 多模型适配 + 未知模型降级，`REQ-005` `SW-025` 异常列已写「未知模型降级为通用规范 + 使用说明」——**这是全工程唯一已写明的降级路径，应上提到系统级**）。
2. **「监管审核周期 4–8 周」不应按依赖处理，应按里程碑输入处理**。该周期（`REQ-004` §1.3 `C-005`、§6 第 145 行「须在提供服务之日起十个工作日内办理」）**不可压缩、不可替代**——它的「替代路径」在技术层面不存在。因此建议：**不写成「依赖 + 替代路径」，而写成「外部审核事项 + 最早启动时点 + 对上线时点的约束」**，避免责任方误以为可通过降级绕过审核。
3. **「失效后果」的写法建议具体到「哪条条目不成立」**，而非泛泛的「有风险」。例如：宿主平台不可得 → `SYS-001`（对外公开传播形态）、`SW-110`（对外服务）不成立，且法定期限（`SYS-011` 描述「自提供服务之日起十个工作日内办理备案」）将开始计。
4. **附加收益**：四列结构可直接产出**依赖台账**，与 `09-合规资料库/05-台账与制度` 已有台账体例一致，并可在每次项目决策（如 `SYS-Q8` 的 ICP 口径变更）时**强制复核**——本次 `SYS-Q8` 口径变更（2026-10-14「ICP 由宿主平台持有」）正好是一次依赖属性变更，若有四列表，已可直接改列而不必在正文多处同步（实际正文改了 §7.1 / §6 两处，`REQ-006` 改了四处）。
5. **注意落点**：`RS-02` 已把「四列 + 阻断标注 + 合并 §4/§6 两处登记」作为同一问题立项，本待议项的结论与 `RS-02` 一致，二者可一并处置。
