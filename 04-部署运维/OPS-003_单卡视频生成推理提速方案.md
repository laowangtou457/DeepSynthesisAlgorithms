## 1 本方案的边界与前提

| 做 | 不做 |
| --- | --- |
| 给出单卡内可落地的六条提速路径与优先级 | **不承诺具体秒数**（未实测，一律给区间并标注 `<待实测>`） |
| 给出参数组合、显存预算、验证方法 | **不改模型权重与训练**（只做推理侧工程改造） |
| 说明为何多卡张量并行在本机型无效 | **不替代多卡吞吐方案**（8-worker 部署另立文档） |

**前提纪律**：

1. 本方案**只解决单条视频的延迟（latency）**。若目标是提高每日出片总量（throughput），走 §7 的 8-worker 并行路径，二者不得混谈。
2. 所有性能数据必须在**固定输入**下采集（固定分辨率、帧数、步数、随机种子），否则不可比。
3. 精度与画质的取舍必须**留证**——每次降精度都要保留前后对照样片，供后续合规与质量评审引用。

## 2 为什么本机型不能靠多卡提单条速度

### 2.1 硬件事实

| 项 | 实测/规格 | 影响 |
| --- | --- | --- |
| GPU | 8×RTX 4090 24GB（Ada，compute_cap 8.9） | 单卡算力充足，**显存是唯一硬约束** |
| NVLink | **无**（4090 未提供 NVLink 接口） | 卡间通信只能走 PCIe |
| P2P（GPUDirect） | **不支持** | 无法显存直连，须过主机内存 |
| 拓扑 | 双 NUMA（各 4 卡），跨节点走 **UPI** | 跨 NUMA 通信代价再上一层 |
| 卡间有效带宽 | PCIe 4.0 x16 ≈25 GB/s；跨 NUMA 更低 | 相对 NVLink 4（≈450 GB/s）差 **约 18–25 倍** |

### 2.2 加速比公式与代入

任意并行策略的实际收益服从：

```
加速比 S(n) = n / (1 + T_comm / T_comp)
```

其中 `T_comp` 为该单元的计算耗时，`T_comm` 为同步一次所需的通信耗时。

**张量并行（TP）在本机型的代入结果**：

| 量 | 本机型取值 | 说明 |
| --- | --- | --- |
| `T_comp`（单层 DiT，2 卡切分后） | 数毫秒级 | 单层计算量本就小 |
| `T_comm`（单层 AllReduce，MB 级数据） | 数毫秒级 | 25 GB/s 带宽下的实测有效值更低 |
| `T_comm / T_comp` | ≈0.8~1.2 | **关键比例接近 1** |
| **S(2)** | **≈0.8~1.1** | 并行收益被通信全部吃掉，常**低于单卡** |

**补充事实**：NCCL 在无 P2P 环境下退化至 SHM / PCIe 通路，`TP=2` 在本机型上**曾实测段错误**，不是「慢」而是「不可用」。

### 2.3 视频 DiT 为何比 LLM 更不适合 TP

| 特征 | 大语言模型（70B 级） | 视频扩散 DiT |
| --- | --- | --- |
| 单卡能否装下 | ❌ 装不下，**并行是为了能跑** | ✅ 单卡可装 |
| 单层计算量 | 大（batch × 长序列） | 相对小 |
| 串行步数 | 1 次前向 / token | **20–50 次去噪，步间强依赖** |
| TP 适配性 | 好 | 差 |

> **结论**：视频 DiT 的三个特征（装得下、层计算小、串行步多）全部指向「不适合张量并行」。这是物理层面的判断，不是配置调优能改变的。

## 3 提速总览与优先级

按「收益 ÷ 实施成本」排序，**必须按序推进**——第 1、2 步完成后，后续步骤的收益基数会变化，应重新测量。

| 序号 | 手段 | 预期加速 | 实施成本 | 显存变化 | 画质代价 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 蒸馏 / 少步采样 | **3–8×** | 低（换权重） | ↓ | 小—中 | ⭐⭐⭐⭐⭐ |
| 2 | fp8 / int8 量化 | 1.5–2× | 中 | **↓↓** | 小 | ⭐⭐⭐⭐⭐ |
| 3 | `torch.compile` + CUDA Graph | 1.2–1.5× | 中 | ≈ | 无 | ⭐⭐⭐⭐ |
| 4 | 注意力算子优化 | 1.1–1.4× | 中 | ↓ | 无 | ⭐⭐⭐⭐ |
| 5 | VAE 解码分块 | 1.1–1.25× | 低 | **↓↓** | 极小 | ⭐⭐⭐ |
| 6 | 分辨率分级 + 超分 | **2–3×** | 中（改流程） | ↓ | 中（需评估） | ⭐⭐⭐ |

**串行叠加说明**：上表倍数是**相对各自基线**的独立值。实际叠加会因共同瓶颈而衰减（阿姆达尔定律），不可直接相乘。真实总收益须由 §8 的实测得出。

## 4 六条提速路径详解

### 4.1 路径一：蒸馏 / 少步采样（收益最大）

视频生成提速的**首选手段**，收益远超任何硬件侧优化，且不需要改代码。

| 手段 | 步数变化 | 加速 | 画质代价 | 适用 |
| --- | --- | --- | --- | --- |
| **DMD2 / LCM 蒸馏权重** | 30→4~8 | **4–8×** | 小，细节轻微损失 | **首选** |
| **一致性模型（CM）** | 30→1~4 | 8–15× | 中，动态略僵 | 草稿/预览 |
| **Flow Matching 少步调度** | 30→10~15 | 2–3× | 很小 | 兜底（无蒸馏权重时） |

**实施要点**

1. 优先寻找**与目标模型同架构、同 latent 空间**的蒸馏权重；跨架构权重直接不可用。
2. 蒸馏模型对 **CFG（guidance scale）** 敏感，少步下需要重新标定 guidance 区间，通常要下调。
3. **必须保留对照样片**：同一 prompt + 同一种子，分别在原步数与少步数下出品，存档以备画质评审。
4. 模型权重获取途径：本机 `huggingface.co` 不可达，走 **ModelScope** 或 `hf-mirror.com`。

**验收判据**：步数降为 `N'` 后，人工比对动态连贯性与细节锐度是否在可接受范围；记录 `N'` 与对应 guidance。

---

### 4.2 路径二：fp8 / int8 量化

Ada 架构（compute_cap 8.9）**原生支持 fp8 E4M3/E5M2 的 Tensor Core 通路**，算力翻倍、访存带宽减半，是本机型性价比最高的精度侧优化。

| 项 | 说明 |
| --- | --- |
| 量化对象 | DiT 的 **Linear / Attention 投影层**；**VAE 与文本编码器建议保留 BF16** |
| 推荐格式 | fp8 E4M3（权重 + 激活）；保守方案仅量化权重（W8A16） |
| 实现途径 | `torchao` 的 fp8 通路 / `TensorRT` fp8 / 框架内置 fp8 linear |
| 显存影响 | 模型权重由 BF16 近似**减半**，为更高分辨率或更长帧数腾空间 |
| 精度风险 | 需 **calibration**（可用少量代表性 prompt 的 latent 统计）；不标定易出现色偏与高光过曝 |

**实施要点**

1. **先做显存容量测算**再动手：确认 fp8 后单卡显存占用能覆盖目标分辨率，否则量化白做。
2. 逐层量化优于全量一把梭——Attention 的 QKV 与 FFN 敏感度不同，先试 FFN。
3. 保留 BF16 基线输出，逐分辨率对比 PSNR / LPIPS（有工具时），无法量化时靠人工盲评。

**验收判据**：同一输入下，fp8 输出与 BF16 基线肉眼无可辨差异；显存峰值下降幅度记录在案。

---

### 4.3 路径三：`torch.compile` + CUDA Graph

视频模型去噪循环执行 20–50 次，**每次的 Python 调度与 kernel launch 开销被放大 20–50 倍**，这部分合计开销常占总耗时的 15–30%。

| 手段 | 作用 | 注意 |
| --- | --- | --- |
| `torch.compile(mode="max-autotune")` | 算子融合、消除多余 kernel | 首次编译耗时数分钟，需缓存到 `TORCHINDUCTOR_CACHE_DIR` |
| **CUDA Graph** | 捕获整个去噪循环，彻底消除 launch 开销 | **要求输入 shape 固定** |
| `mode="reduce-overhead"` | 自动启用 CUDA Graph | 折中方案，编译更快 |

**关键约束与对策**

- **shape 固定的问题**：视频任务的分辨率、帧数组合多，无法一个 Graph 通吃。对策：**为高频 shape 组合分别捕获并缓存**，低频组合回落到 eager 模式。
- **动态维度**：若模型内部有动态 shape（如可变帧数），CUDA Graph 会失效或正确性出错，须显式 pad 到固定 shape。
- 编译缓存必须持久化到 `/data`，容器重建后不重复编译。

**验收判据**：固定 shape 下连续跑 ≥10 次，第 2 次起（排除首次编译）的平均单条耗时对比 eager 基线。

---

### 4.4 路径四：注意力算子优化

视频模型的 token 数 = 帧数 × 分辨率 / patch 面积，序列极长，**注意力是主要显存带宽瓶颈**，优化收益直观。

| 算子 | 收益 | 前提 |
| --- | --- | --- |
| **FlashAttention-2** | 基线，必开 | compute_cap ≥8.0 ✅ 本机满足 |
| **FlashAttention-3** | 较 FA2 再提升 | 需 Hopper；**本机不可用** |
| **SageAttention / SageAttention2** | 1.2–1.4× | int8 量化注意力，Ada 支持；社区实测视频 DiT 上有明显收益 |
| 稀疏 / 线性注意力 | 视模型而定 | 需改模型结构，非开箱可用 |

**实施要点**

1. 先确认模型实现里注意力是否**已经**走 FA2 路径（部分框架默认退回 eager，白白损失）。
2. SageAttention 对 latent 分布敏感，建议**同 §4.2 一起标定**，避免两处量化误差叠加。
3. 收益随序列长度增长，**分辨率越高收益越大**——要与 §4.2 一起实测，不要分别单独下结论。

---

### 4.5 路径五：VAE 解码分块

去噪完成后的 VAE decode 常占总耗时 **15–25%**（长视频更甚），是最容易被忽略的一段。

| 手段 | 作用 |
| --- | --- |
| **tiling / slicing 解码** | 分块处理，显存峰值大幅下降，可启用更大分辨率 |
| **fp16 / bf16 VAE** | 避免 fp32 解码的额外开销 |
| 解码 worker 并行 | 若多卡空闲，可把 decode 卸载到另一张卡 |

**时序要点**：decode 是**单次大计算**而非循环，与去噪阶段的瓶颈不同。若去噪已被蒸馏压缩到很短（如 4 步），**decode 占比会升至 40% 以上**，此时解码优化的边际收益反而最高。**必须先测分段耗时再决定投入**。

---

### 4.6 路径六：分辨率分级 + 超分

工程侧最实用的一招：**降低生成分辨率，再用超分补回**。

```
480p 生成（步数已压缩）  →  2× 超分  →  720p / 1080p 交付
```

| 项 | 说明 |
| --- | --- |
| 加速原理 | 扩散计算量与 token 数近线性，480p 的 token 数约为 720p 的 45% |
| 总耗时 | 常为直接生成 720p 的 **1/2 ~ 1/3** |
| 画质代价 | 中——超分无法恢复生成阶段不存在的高频细节，快速运动场景易糊 |
| 适用 | 草稿、预览、批量内容、对细节要求不极端的交付 |

**必须留证的取舍**：分级生成 + 超分属于**画质降级路径**，须在样片评审中明确标注，不得与全分辨率产物混同交付。若用于对外产品，需评估是否触及生成合成内容标识义务。

## 5 显存预算（24GB 卡的硬约束）

### 5.1 估算口径

单卡显存占用由四部分构成：

| 部分 | 说明 | 可压缩性 |
| --- | --- | --- |
| 模型权重 | DiT + VAE + 文本编码器 | ✅ 量化可降（§4.2） |
| 激活 / 中间张量 | 随分辨率 × 帧数增长，**主变量** | ✅ 分块、少步不降此项 |
| KV / 注意力缓存 | 视频序列极长，占比可观 | ✅ FlashAttention / Sage 可降 |
| 框架与碎片 | CUDA context、编译缓存 | ⚠️ 固定开销 1–2 GB |

### 5.2 参考区间（`<待实测>`）

以下为同档位开源视频模型的**经验区间**，**非本机实测**，落地前必须替换：

| 档位 | 精度 | 参考显存 | 24GB 结论 |
| --- | --- | --- | --- |
| 480p / 5s | BF16 | 18–22 GB | ✅ 可跑，余量小 |
| 480p / 5s | fp8 | 11–14 GB | ✅ 宽裕，可考虑并发出片 |
| 720p / 5s | BF16 | 22–24 GB+ | ⚠️ 贴顶，易 OOM |
| 720p / 5s | fp8 | 14–18 GB | ✅ **推荐路径** |
| 1080p | fp8 | 24 GB+ | ❌ 单卡不足，需流水线并行或另一台 48G 机 |

**显存安全余量**：建议保留 **≥2 GB** 余量，防止长尾输入触发 OOM。触顶运行会导致 `torch.compile` 的 CUDA Graph 失效退化。

## 7 与多卡的关系（不属本方案，但须说明）

| 目标 | 该做什么 | 不该做什么 |
| --- | --- | --- |
| **单条更快** | 本方案的六条路径 | 张量并行（无收益，且会崩溃） |
| **出片更多** | **8 个独立 worker + 队列调度**，每卡一份完整模型 | 数据并行以外的多卡协作 |
| 单卡装不下（1080p+） | 流水线并行（PP），多请求填气泡；或路由到 48G 机 | 张量并行 |

8-worker 部署形态（Docker Compose、`CUDA_VISIBLE_DEVICES` 绑定、NUMA 亲和、队列调度）**另立部署文档**，不在本文展开。

> ⚠️ 若确需多卡协作，只考虑**序列并行（SP）**，且必须限制在**同一 NUMA 内的 4 卡**（0–3 或 4–7）。跨 NUMA 会退化到无收益。

## 9 落地顺序与里程碑

| 阶段 | 内容 | 前置 | 交付物 |
| --- | --- | --- | --- |
| P0 | 建立**原生基线 B0** | 模型可跑 | `t_*` 时序基线 |
| P1 | 路径一：换蒸馏权重 | P0 | B1 数据 + 画质对照 |
| P2 | 路径二：fp8 量化 | P1 | B2 数据 + 显存峰值 |

| P4 | 路径三：编译 + Graph | P3 | B4 数据 |
| P5 | 路径五：VAE 分块 | P4 | B5 数据（含 decode 占比） |
| P6 | 路径六：分辨率分级 | P5 | B6/B7 数据 + 取舍评审 |
| P7 | 固化两档参数基线 | P6 | §6 参数文件 + 全量对照表 |

**纪律**：P1–P6 **不得跳步**。每一步的基线都是下一步的比较基准，跳步会导致归因失效、收益无法拆分。

## 10 风险与回退

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| 蒸馏权重不可得 | 找不到同架构蒸馏版 | 回落 Flow Matching 少步（2–3×），并评估自行蒸馏成本 |
| fp8 精度失控 | 色偏、高光过曝 | 仅量化权重（W8A16）；对 FFN 先试，Attention 后试 |
| CUDA Graph 崩溃 | shape 变化时结果错乱 | 严格固定 shape + pad；低频组合回落 eager |
| 显存贴顶 | 长输入偶发 OOM | 保留 ≥2 GB 余量；降低帧数或启用 tiling |
| 收益衰减 | 叠加后总加速远低于预期 | 阿姆达尔定律所致——重新测分段占比，转向新瓶颈（常是 VAE） |
| 画质降级越界 | 超分/少步导致交付不达标 | 样片评审设闸；分级产物明确标注，不混同全分辨率交付 |

**统一回退原则**：任何一步改造都必须能**一键回到上一步的配置**。参数文件版本化，不得原地覆盖。
