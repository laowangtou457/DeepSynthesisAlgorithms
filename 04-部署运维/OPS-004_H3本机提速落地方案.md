## 1 现状基线（✅ 本机实测）

### 1.1 单条耗时构成

固定：`1344×768 / 4.44 s / 107 帧 / 50 步 / seed 0`，t2va（fl2va），8 副本在线。

| 阶段 | 耗时 | 占比 |
| --- | --- | --- |
| 前处理 + 文本编码 | < 5 s | < 1% |
| **去噪（50 步）** | **606 s**（12.1 s/it） | **≈96%** |
| VAE 解码 | 13.1 s（独占） | ≈2% |
| 端到端 | **621 s（10.4 分）** | — |

**去噪是唯一的主战场**，而它 100% 是 attention + Linear 的计算，这就决定了 `sage_attn` 为什么有效。

### 1.2 当前参数（`ops/restart-card.sh:115-127`）

```
--model-variant {fl2va|ref2va} --num-gpus 1
--quantization convrot_int8 --attention-backend fa --performance-mode memory
--layerwise-offload-components dit,text_encoder
--dit-offload-prefetch-size 1 --dit-layerwise-resident-layers 0
--enable-torch-compile false
```

**这套就是 4090 官方推荐配方，没有配置错误可捞。** 唯一没动的就是 `--attention-backend`。

### 1.3 与官方 4090 基准的差距

| 配置 | 官方 4090（50 步） | 我们实测 | 判断 |
| --- | --- | --- | --- |
| `convrot_int8` + FA | 718.5 s | 606 s（fl2va）/ 937 s（ref2va） | fl2va **已优于**官方；ref2va 慢属变体特性 |

> 官方 718.5 s 未标注变体。我们的 fl2va 606 s 已经比它快，说明**工程侧没有明显余量可捞**。
> 这与 §1.1 的结论一致：想快，只能换算法。

### 1.4 解码抖动（历史包袱，已解决）

| 场景 | 解码 | 端到端 |
| --- | --- | --- |
| 独占 | **13.1 s** | 621 s（10.4 分） |
| 与另一副本解码窗口重叠 | **670.4 s** | 1865 s（31 分） |

**极差 51 倍。** 线程补丁（`patch-worker-threads.py`）后复测两卡并发：`1098.9` vs `1101.6 s`，**差 0.25%**。

> ✅ 已修好，不需要再投入。列在这里是为了防止重复劳动 —— 这是历史上「10.4 分 vs 31 分」的真正来源。

## 2 主攻：`sage_attn` 注意力后端

### 2.1 为什么是它

视频 DiT 的 token 数 = 帧数 × 分辨率 / patch 面积，序列极长，**第 1.1 节那 96% 的去噪时间里，attention 占大头**。SageAttention 用 int8 量化 Q/K 与 fp16 P/V 计算注意力，直接砍掉这部分的核心开销。

关键优势：**它只是换 `--attention-backend` 的一个参数，且支持 `sglang serve`。**

### 2.2 官方 4090 实测（📖 20 NFE / 1344×768 / 107 帧 / 单卡 24GB）

| 配置 | Timed e2e | Denoise | vs BF16 | **vs 我们现状** | PSNR vs BF16 |
| --- | --- | --- | --- | --- | --- |
| BF16 + FA | 405.6 s | 370.2 s | 1.00× | 0.75×（更慢） | — |
| **`convrot_int8` + FA（我们现在的）** | **303.3 s** | 273.7 s | **1.34×** | **1.00×** | 24.81 dB |
| `convrot_int8` + `sol_attn` | 223.9 s | 203.9 s | 1.81× | **1.35×** | 24.44 dB |
| **`convrot_int8` + `sage_attn`** | **174.9 s** | **154.2 s** | **2.32×** | **1.73×** | **23.51 dB** |
| `convrot_int8` + Sage→Sol hybrid | 163.8 s | 143.1 s | 2.48× | **1.85×** | 23.04 dB |

> 🔑 **两列加速比不是一回事，别混用**（2026-11-06 澄清）：
> - 「vs BF16」= 相对**纯 BF16 + FA**（405.6 s），列的是每个优化各自**从零加起来**的总账；
> - 「vs 我们现状」= 相对**已经上了 `convrot_int8`** 的现网配置（303.3 s），**这才是换 attention 后真正多拿到的东西**。
>
> 我们已经吃到 int8 权重量化那 1.34× 了，所以后面任何一环只能按第二列估。举例：`sol_attn` 是 1.81× 对 1.34×，**不是 1.81/1.00**。

**相对我们现状的净收益**（换 attention 的实际增量）：

```
sage_attn :  303.3 / 174.9 = 1.73×
sol_attn  :  303.3 / 223.9 = 1.35×
hybrid    :  303.3 / 163.8 = 1.85×
```

| 我们现在的 50 步基线 | 🧮 按 1.73× 推算 | 备注 |
| --- | --- | --- |
| fl2va 606 s | **≈ 350 s（5.8 分）** | 推算值，非实测 |
| ref2va 937 s | **≈ 542 s（9.0 分）** | 推算值，非实测 |

> ⚠️ **两点必须诚实交代**：
> 1. 官方这张表是 **20 步**的，我们跑 **50 步**。attention 开销随步数线性增长，所以 1.73× 在 50 步下**大概率成立甚至略好**（去噪占比更高），但**必须实测确认**。
> 2. 官方的 50 步表里，`sage_attn` 只出现在**与 Spectrum 组合**的行（245.3 s），**没有单独 50 步的 sage 数据**。所以 1.73× 是**跨步数推算**，属 🧮 级证据。

### 2.3 质量代价

**PSNR 23.51 dB**（对 BF16 基线）。对比其他选项：

| 后端 | PSNR | MSE 增幅 | 相对现状速度 |
| --- | --- | --- | --- |
| FA（现状） | 24.81 dB | — | 1.00× |
| `sol_attn` | 24.44 dB | +8.9% | 1.35×（303.3→223.9） |
| **`sage_attn`** | **23.51 dB** | **+34.9%** | **1.73×**（303.3→174.9） |
| Sage→Sol hybrid | 23.04 dB | +50.3% | 1.85×（303.3→163.8） |

换算口径：`MSE = 255² / 10^(PSNR/10)`，RMSE 从 14.66/255 升到 17.02/255（sage）。

**取舍建议**：

- **稳妥档**：先上 `sol_attn`（PSNR 只掉 0.37 dB，拿 **1.35×**）。若盲评完全看不出差异，再升到 `sage_attn`。
- **激进档**：直接 `sage_attn`（掉 1.30 dB，拿 **1.73×**）。
- **性价比对照**：sage 相对 sol 再多 28% 速度（1.35→1.73），代价是**再掉 0.93 dB**（0.37→1.30）。若盲评在 sol 上过关、在 sage 上不过关，就停在 sol。
- **不建议**：hybrid（相对 sage 只多 7% 速度，再掉 0.47 dB）。

> 官方明确：`sol_attn` / `sage_attn` **改变注意力算法**，**不能作为一致性 ground truth**。若日后要做「同种子可复现」的合规举证，必须保留 `fa` 作为基准路径。

### 2.5 为什么不用 `sol_attn` / hybrid 直接上

`sol_attn` 需要 `--attention-backend-config dense_backend=sage_attn,dense_steps=10` + `--component-attention-backends`，**配置复杂度高**，而且它的 dense 段仍然要用 sage —— **等于还是要装 SageAttention**。

所以：**先装 SageAttention，先用最简单的一行 `sage_attn`。** 等它验证通过，再考虑 hybrid。

## 3 暂缓：Spectrum 跳步（看起来最美，但现在用不了）

### 3.1 为什么暂缓

OPS-003 最推崇的「少步采样」，在 sglang 里对应 **Spectrum**。官方 4090 数据确实惊人：

我们是 `sglang serve` 提供 HTTP 服务给平台调用的。**这个限制直接封死了落地路径。**

### 3.2 还有一个矛盾需要澄清

| 来源 | 说法 |
| --- | --- |
| `Spectrum Acceleration` 专页 | ❌ 不支持 `sglang serve` |
| MiniMax-H3 Cookbook §3 | 「同样 flags 可用于 `sglang serve`」 |

**两处官方文档互相矛盾。** 我的判断：

- 专页是**功能契约**（说能力边界），可信度更高；
- Cookbook 那句可能是**沿用了其他模型的模板文字**；
- 而且当前版本 0.5.23 **连 `--spectrum` 参数都没有**（已实测 `--help` 无此 flag）。

**结论：无论哪边对，0.5.23 都用不了。** 需要升级到 **v0.5.21+**（该版本 release notes 有 `[Diffusion] MiniMax-H3 Spectrum skip-step + fused RMSNorm/AdaLN: #35684`）—— 注意我们装的 0.5.23 版本号更高却仍无此 flag，说明**该特性可能是另一个发布通道或需要额外编译**，这一点**未查清**。

## 7 明确不要做的（已证伪，勿重复试错）

| 手段 | 为什么 | 证据 |
| --- | --- | --- |
| `--enable-torch-compile true` | 官方：收益**低于测量噪声** + **改变数值输出** + 启动变慢 | 官方 Cookbook；`01-单卡基线部署手册.md:145` |
| 多卡张量并行 / Ulysses | 4090 无 P2P/NVLink，NCCL 退化；`TP=2` **实测段错误** | `OPS-003 §2`；本机实测 |
| `--performance-mode speed` | 24 GB 装不下 62 GB transformer | 本机实测 |
| `--dit-layerwise-resident-layers >0` | 官方对 4090 就推荐 0 | 本机已验证 |
| NUMA 绑核提速 | 实测**无改善**（23.9→24.2 s/it），仅保留防抖动 | `05-性能诊断` §2.1-2.2 |
| `allow_cudnn_tf32=false` | 默认 true，关掉更慢 | `05-性能诊断` §6.3③ |
| `OMP_NUM_THREADS=1` | 解码前处理与 VAE 反量化需并行，限到 1 更慢 | `05-性能诊断` §6.6 |
| **`subblock_sparse_attn`** | **不支持 SM89**，4090 会被拒绝 | 官方：仅 SM90/SM100/SM120 |
| 降分辨率 480p + 超分 | 与「只做 768p」口径冲突；超分无法恢复不存在的细节 | 项目口径 |
| `quality: "high"`（Cache-DiT 审计档） | **只支持 4×H200**，其他硬件 fail-closed | 官方原文 |
