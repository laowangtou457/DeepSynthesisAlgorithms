## 一、目录结构

```
E:\深度合成算法工程材料\
├── .gitignore                 版本控制忽略规则（排除受控资产与密钥）

├── 00-需求\                   ★ 所有需求（系统级 / 软件级 / 硬件级）

├── 10-评审记录\               ★ 收到的意见：评审意见 / 修改意见（他人 → 我方）
├── 11-过程文档\               ★ 过程件：发出的要求（编制要求\）+ 工程留痕（开发历史\）

├── 13-项目配置管理\           ★ 配置管理：配置管理计划（上位）+ 文件取号表（编号唯一登记处）+ 追溯矩阵（双向追溯）
└── _受控区\                      ★ 受控资产实体（涉政 / 涉民族内容，**不入版本控制**）
```

> **说明**：`10-评审记录` 与 `11-过程文档` 是**过程留痕目录**，不对应工程阶段，而按**信息流向**划分：
>
> | 目录 | 流向 | 放什么 | 时机 |
> | --- | --- | --- | --- |
> | `10-评审记录` | **收**（他人 → 我方） | 谁评审了哪份文档、提了什么问题、是否采纳 | 文档**产出后** |
> | `11-过程文档` | **发**（我方 → 他人） | 我方要求谁编制什么、达到什么标准 | 文档**产出前** |
>
> 两者的共同点：**都不是交付物本身，而是围绕某份专项文档的过程件**；被指向的文档**始终留在原归属目录、不移动**。
>
> 编号说明：`10`/`11` 是过程留痕区的编号段，语义上不属于 `00`~`09` 的工程阶段序列，但保留编号以便与其余目录统一排序。

4. 涉及数值须给出**来源**（实测 / 官方文档 / 内部规则实现）；要求件**永久保留**，不随对象文档修订而删除或覆盖。

**`开发历史/` 四条约定**：

1. **一份文档只记一个动作**；互不相关的对象拆多份，编号 `DEV-YYYYMMDD-NNN` 按日流水、永不复用；
2. 判定依据为双源（`git log`/`git status` + 工作区文件 `mtime`），**无新增动作时不产出文档**；同一动作幂等只记一次；
3. **无证据不闭环**——无验证证据的动作状态标「未验证」而非「已完成」；
4. **该目录随版本控制提交**，故须遵守脱敏纪律：不出现真实企业名与人名，一律用占位符；受控类只记计数变化、不落明文。

**与 `10-评审记录` 的关系**：同一份专项文档的完整过程链为 —— `11-过程文档/编制要求`（我方下达）→ 文档正文（原地不动）→ `10-评审记录`（他方反馈）→ 文档修订。`开发历史/` 不在此链上，它记录的是**整个工程**的时间轴。**三者各归其位，正文不动。**
