## 0 给专家的一句话说明

`synopsis_v1` 是本项目「AI 漫剧」业务链路的**第一个模板**，产出一份 JSON 故事梗概。它的下游依次是：**剧本生成（SW-005）→ 分镜脚本（SW-006）→ 分镜提示词（SW-007）→ 提示词解析重构（SW-008）**，最终要投喂 MiniMax H3 / Seedance 等视频生成模型。

所以本次评审**不是评「梗概写得动不动人」**，而是评：**这份梗概，够不够当一条镜头提示词链路的源头。**

## 1 评审对象的界定（三档，请严格区分）

### 1.1 主评：`TPL-013_synopsis_v1.yaml`（模板本体）

这是**契约**——它规定了下游能拿到什么字段、什么约束。评审的重心在这一份。

### 1.2 连带评：`CASE-004_synopsis-case01.md`（用例）

**必须一起评，理由是它承担三项不可替代的功能：**

| # | 功能 | 只看模板会漏掉什么 |
| --- | --- | --- |
| 1 | **契约的实例化**——模板写的字段约束，落到具体内容时长什么样 | 只看模板会以为「字段有就够了」，看不到**字段值的信息密度**是否够下游用（例如 `world.tone` 在模板里是个合法字段，在用例里只有「克制温情」四个字） |
| 2 | **约束的边界证明**——用例第 2、3 项专门设了「编造陷阱位」（主角姓名、失联年数） | 看不到模板的硬约束在**真实内容压力**下会不会把下游顶死 |
| 3 | **评测口径的样本**——用例 §4 的 7 项评测结论，是「怎么判这份产出合格」的第一版定义 | 看不到**质量尺子量了什么、漏了什么** |

> **一句话**：模板是「承诺」，用例是「承诺的一次兑现」。**只评承诺，会漏掉兑现时的失真。**

### 1.3 重要前提：本用例**尚未经模型实测**

`CASE-004_synopsis-case01.md` §3 的 JSON 标注为「**待回填**」，且 §5 明确「**未验证**」——它是**人工构造的目标输出样例**，不是 Qwen2.5-7B-Instruct 的真实输出。

因此请**不要**把它当作「模型实测证据」来评判生成能力。请把它当作：
- **输出形态的基线样本**（这份 JSON 的字段分布、粒度、详略程度，就是设计者认为合格的样子）；
- **下游输入的代表样本**（下游 SW-005 拿到的，就会是这种信息密度的东西）。

并请在意见中明确指出：**这类形态，下游能不能承继。**

## 2 评审角度（导演视角的四问）

导演视角的三把尺子是**可投喂性 / 可控性 / 可拍摄性**（见你的技能输出检查清单）。但梗概是**链路最上游**，它本身不产出可投喂文本——所以三把尺子要做一次**承继转译**：

| # | 转译后的判据 | 原始尺子 | 要问的问题 |
| --- | --- | --- | --- |
| **①** | **可承继性** | ← 可投喂性 | 这份梗概交给下游。为了做出剧本→分镜→镜头提示词，下游**必须**知道的信息里，有多少是它给的、有多少是它没给要不来的？未给的部分，下游要额外做多少「翻译」工作，这部分工作在链路里由谁承担、在哪个模板完成？ |
| **②** | **可锚定性** | ← 可控性 | 跨阶段一致性（数字/专名/设定/外观零漂移）需要「锚」。角色锚、场景锚、风格锚三类，各自有没有**稳定标识 + 足够属性**？缺锚会怎样传导到最终镜头提示词？ |
| **③** | **可拍摄性** | ← 可拍摄性 | `scenes_outline` 提供的是**叙事事件**（发生了什么）还是**可拍场景**（在哪、什么时相、谁在场、有哪些可见动作）？两者差别对下游意味着什么代价？ |
| **④** | **缺口可追溯性** | （新增，本模板特有） | 模板的硬约束是「缺失一律写『未指定』、不得编造」。这个立场在**叙事层**是正确的——那么落到**视觉层**呢？「未指定」的项，下游能否机器可读地知道「缺什么、在哪一环补、补不上时降级为什么」？现有设计是否把**视觉层的交接责任**交代清楚了？ |

> **第 ④ 问是本次评审最要紧的一问。** 它直接决定：这份模板产出的梗概，是不是一个「下游拿到后必须自己编造才能用」的产物。请重点核查。

### 2.1 明确不在评审范围（请勿出意见）

| 不评 | 原因 |
| --- | --- |
| 备案流程、法律法规引用、AIGC 标识与合规声明 | 属合规视角，非本次视角 |
| YAML 语法、文件命名、目录结构、版本号格式 | 属工程规范，除非**妨碍引用或导致歧义** |
| `CFG-007_SCHEMA.md` / `CFG-008_manifest.yaml` 本身的字段设计 | 只作参照件，用于判断「模板是否符合既有结构约定」 |
| SW-004 需求条文本身是否合理 | 需求已确认，本次只评**实现是否达成需求** |
| 「Qwen2.5-7B 能不能生成出这个」 | 本用例未跑模型，无实测证据，无法评 |

### 2.2 请同时给出「已核查、不成立」的项

只报问题不报核查范围，会让责任方无法判断边界。请对**你考虑过但判定不成立**的点，也写明「已核查：不成立，理由是…」。至少覆盖：
- `stage: synopsis` 与下游 `分镜提示词交付规范-v1.1` §3.2 `stage_chain` 的对齐是否成立；
- `covered_points` 的要点级追溯是否可靠；
- 直接输出 JSON（而非自然语言）的约定是否可对接下游；
- 模板对 `examples` 节的少样本密度是否足够。
