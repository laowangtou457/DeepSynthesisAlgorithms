## 2 为什么 RAG 不能走在 `T-004` 前面

三条理由，任一条单独成立即足以否决"先做 RAG"：

1. **没有注入点。** `SW-023` 的输出栏写的是「向量化、检索、**上下文注入**」——注入的对象是**生成调用**。`T-004` 未完成时，生成链路上跑的仍是 `mock` 后端，注入进去也没有语义效果，无法验证"检索是否真的改善了输出"。做出来的只能是**离线检索脚本**，而那不是 `SW-023`。
2. **语料是"为生成服务的"，其形态由生成侧决定。** 语料怎么切、切多长、要不要保留场次/风格锚点元数据，取决于 `SW-004`~`SW-007` 四段模板的输入契约（`CFG-007_SCHEMA.md` 的 `context` 段）。**先建库再定契约，必然返工**。
3. **降级路径无法验证。** `SW-023` 的兜底栏是「检索不可用降级为无检索生成」——这是一条**故障路径**，只有在生成链路可跑通之后才能做故障注入测试。链路没通，这条验收标准**无法举证**。

## 3 落地方案（`T-004` 完成后即可开工）

### 3.1 阶段划分（建议拆为 R1~R4，与 `T-007` 的 4–6 人日对应）

| 阶段 | 内容 | 前置 | 预估 |
| --- | --- | --- | --- |
| **R1 · 语料与授权** | 语料清单落 `05-数据管理/`（`T-011` 的 D-009 为上位）；逐项登记来源、授权、可对外举证性；**先小样（数十条）打通，再扩量** | P2 | 1.0 人日（**须项目方提供语料来源**） |
| **R2 · 检索层** | `Retriever` 协议（`encode` / `build_index` / `query`）+ embedding 选型落地 + 向量库持久化（落 E/F 盘）+ 元数据保留（场次/风格锚点） | P3、P4、P5、R1 | 1.5–2.0 人日 |
| **R3 · 注入与溯源** | 生成调用前检索 → 组装 `context` → 注入；生成结果侧产出 `sources[]`（**承载形态见 §6 ISSUE-022**） | R2、**P1（`T-004`）** | 1.0–1.5 人日 |
| **R4 · 降级与评测** | 故障注入（索引下线／超时／空命中）→ 生成照常且登记；**有检索 vs 无检索的对照评测**（否则无法证明"增强"二字） | R3 | 1.0 人日 |

> **刻意不做的两件事**：① **不引入 Agent／重排（rerank）大模型**——本期检索质量目标只是"补参考知识"，多一个模型就多一份显存与一份备案说明；② **不做 LoRA**——`REQ-005` 明写"为后期 LoRA 微调**预留扩展接口**"，本期只留接口（§3.2）。

### 3.2 架构落点与扩展接口预留

按 `03-工程代码/app/` 既有分层（`api` / `services` / `repositories` / `inference`）落地，**不新开平行结构**：

```
app/
├── repositories/retriever_repo.py    # 向量库读写（唯一接触向量库的地方）
├── services/rag_service.py           # 检索编排 + 上下文组装 + 溯源
└── inference/embedding_backend.py    # embedding 推理（与生成后端 registry 同构，可替换）
```

**LoRA 扩展接口预留（本期只留点、不实现）**：检索层与生成层**单向依赖**——`rag_service` 只产出 `retrieved_context`，**不感知生成侧用什么模型**。故后期接 LoRA 只需在 `inference/` 侧新增 adapter，**检索层零改动**。这条写进方案的目的是：**别让检索层与"某个具体模型"耦合**，否则 LoRA 一上就要重构。

### 3.3 语料清单模板（R1 的交付物形态）

`05-数据管理/` 首个文件建议即 `T-011` 的 **D-009 数据来源与处理说明**（取号 `DATA-001`），逐条登记：

| 字段 | 说明 |
| --- | --- |
| 语料名称／路径 | 落 E/F 盘；**不入代码库**（体量 + 授权） |
| 来源 | 自有业务数据／公开数据集／客户提供——**须可追溯到具体文件** |
| **授权与可举证性** | 是否有明确授权；是否含第三方内容（**牵动 `SW-015` 版权校验**）；是否含个人信息（**含 PII 即不得入库**——`funNLP` 已因此被永久排除，见 `CM-001` §11.3） |

> ⚠️ **`SYS-008` 是备案举证项**：语料"从哪来、有没有权用"在备案审查时会被问。故 R1 的产出**不只是技术准备，也是合规准备**——这一点决定了它**不能省**。

### 3.5 向量库选型（倾向，待 R2 定）

| 候选 | 形态 | 优点 | 代价 |
| --- | --- | --- | --- |
| `FAISS` + 本地文件 | 嵌入式，索引即文件 | 无服务依赖、离线可用、**落盘路径可控** | 无内置元数据过滤，需自管 ID 映射 |
| `sqlite-vec` / `Chroma` | 嵌入式 + SQL | 元数据过滤方便 | 多一层依赖 |
| `Milvus` 等独立服务 | 独立进程 | 规模上限高 | **本期语料量级用不上**，且多一个上线件 |

**倾向**：**嵌入式方案**（前两者之一）。理由与本项目一贯口径一致——**备案要的是"可运行、可举证、依赖少"**，不是"架构先进"。

### 3.6 显存与存储预算（**只给方法，不给未实测数字**）

- **显卡实测已知量**：`RTX 4090` / `compute_cap 8.9` / **23028 MiB**（`REQ-001` §10.1、`CM-001` §11.2 `ENV-001`）。
- **已知占用**：`Qwen2.5-7B-Instruct` **BF16** 权重约 15 GB 量级 + KV cache（随并发与上下文增长）。→ **同卡再加一个 embedding 模型的余量很紧**。
- **三条可选路线**（待 `T-012`／`T-013` 实测后定）：
  1. embedding 独立进程 + 限制 batch（延迟可控，显存共享）；
  2. embedding 走 **CPU**（显存让给生成，用延迟换余量）；
  3. embedding 只在**建库期**用（离线），**查询期用轻量编码**（若选型支持）。
- **存储**：向量索引与语料一律落 **E/F 盘**（`REQ-001` §10.1「C 盘只放运行环境」是**必须固化的路径约定**）；规模按 `语料 token 数 × 维度 × 4B × 冗余系数` 测算——**待语料确定后回填**（当前 `REQ-001` §10.1 的 610 GB 口径**不含 RAG 向量库增量**，须一并复核）。

### 3.7 降级与可观测

| 场景 | 处置 | 验证券 |
| --- | --- | --- |
| 索引不可用／加载失败 | **降级为无检索生成**，正常出结果 | 故障注入：把索引路径置空 → 生成成功且 `meta.notes` 登记 |
| 检索超时 | 超时即放弃检索，不拖垮生成 | 注入延迟 |
| 检索命中为空 | 按无检索走，**不编造来源** | 空库查询 |
| 命中内容命中受控词库 | **走 `SW-009/010` 输入侧双闸**（检索产物属"输入"，不得绕过） | 见 §4 |
