## 2 打通受约束解码的接入通道（`uniqueItems` 剥离）

### 2.1 问题

`03-工程代码/app/services/output_schema.py` 的 `load_output_schema()` 把 `CFG-006_shot_prompt_pack.v1.schema.json` **原样**交给后端，而该 schema 含 `uniqueItems`（全 schema 仅 **1 处**：`$.$defs.unit.properties.shot_ids.uniqueItems`）。xgrammar **不支持该关键字**，实测报：

```
{"error":{"message":"Grammar error: Unimplemented keys: [\"uniqueItems\"]","code":400}}
```

⇒ 应用一接真引擎，`shot_prompt` 段**第一次请求即 400**（属 `OPS-002` §4.3.1 已定位、但**尚未在应用侧处置**的缺口）。

### 2.2 处置（只剥这一处，约束换执行位置）

- 新增 `ENGINE_UNSUPPORTED_KEYS = {"uniqueItems"}`（**只列有实测证据的键**，其余逐字保留）；
- 新增 `load_engine_schema()`（**引擎可编译形态**，剥离后返回副本）与 `stripped_paths()`（留痕用键路径）；**`load_output_schema()` 保持返回契约真值** —— 两种形态**语义分离、不得混用**；
- 剥离走**深拷贝**：`_load_cached` 的返回对象被 `lru_cache` 复用，原地 `del` 会**污染契约真值**（静默降级的一种）；并有专门用例锁死；
- `dialogue_service` 下传改为引擎形态，并把 `schema_stripped_keys` 写进 `generation_completed` 日志（**留痕而非静默**）；
- 约束**不丢失**：应用层仍用**完整** schema 走 `jsonschema`（`validate_pack.py` 支持该键）⇒ 只是**换执行位置**。

### 2.3 验证

- 新增 6 条用例（剥净 / 真值仍完整 / **不污染缓存** / 差异只在 `uniqueItems` / 键路径可核查 / 无契约阶段返回 `None`）；
- `pytest`：**98 → 124 项全绿**（本轮 +6，另有并行会话的 `T-005` 安全闸用例）。

## 6 精确定位：窗口不足的真实机理（本段最重要）

用 `/tokenize`（**引擎自身**分词器，非字符数估算）对 `storyboard` 段的**完整渲染 prompt**（上游用本轮真跑的 `script.json`）计数：

| 项 | 数值 |
| --- | --- |
| 渲染后 prompt | **30252 字符**（模板正文 24438 ＋ 上游 `script_json` 5814） |
| **精确 prompt tokens** | **14473** |
| 模板 `sampling.max_tokens` | 8192 |
| **所需窗口 ≥** | **22665** |
| 当前 `--max-model-len` | 16384 |
| **当前剩余输出预算** | **16384 − 14473 = 1911**（缺口 **6281**） |

⇒ 失败**不是**「输入勉强越界」，而是**输入本身吃掉 88% 的窗口**。故「降 `max_tokens`」在本段**不可行**（1911 tokens 远不足以产出 14 镜分镜），正确处置是**提高引擎窗口**。

**为什么提窗几乎无成本**：KV Cache 池容量由 `gpu_memory_utilization` 决定（实测 **88,032 tokens**），**与 `max_model_len` 无关** —— 提窗只改变「单序列最长能到多少」，代价是**满长度并发数下降**（16384 时 5.37x → 32768 时约 2.68x），**不额外占用显存**。且 Qwen2.5-7B-Instruct **原生支持 32768**，无需 YaRN。

`OPS-002` §5 已把这个参数写成「**须 ≥「最长分段提示词 ＋ 8192 输出」**」并标 `<待实测>`，§7.1／§7.4 亦有两条待回填 ——
**本轮实测恰好回答了它**：最长分段提示词 = **14473 tokens** ⇒ 16384 **不够**，建议 **32768**。
