## 2 Windows 侧连通性（是否要新开窗口）

**结论：Windows 侧 PowerShell 可直接用 `127.0.0.1:8001`，不需要取 WSL2 的 IP。**

取证（`Get-NetTCPConnection -LocalPort 8001`）：

```
LocalAddress LocalPort  State OwningProcess
127.0.0.1         8001 Listen          7256   →  C:\Program Files\WSL\wslrelay.exe
```

- 占用者是 **`wslrelay.exe`** ⇒ WSL2 的 **localhost 转发正在工作**；
- `%USERPROFILE%\.wslconfig` **不存在** ⇒ `localhostForwarding` 走**默认 `true`**；
- 实测 `curl.exe --noproxy '*' http://127.0.0.1:8001/v1/models` ⇒ **`http=200`，`time=0.006833 s`**。

⇒ `OPS-002` §4.4 原文「`127.0.0.1:8001` **通常**可直接互通」**升格为「已实证」**（并保留旧办法作为回退）。

### 2.1 顺带取证到的一个操作陷阱（已写进手册 §4.4）

**Windows PowerShell 里裸写 `curl` 不是 curl**：`Get-Command curl` 的 `CommandType` 为 **`Alias`**
（指向 `Invoke-WebRequest`）。实测报错原文：

```
找不到接受实际参数"--max-time"的位置形式参数。
```

⇒ `-s` / `-H` / `-d` / `--max-time` **全都无效**。必须写 **`curl.exe`**。
另：`Invoke-WebRequest` **默认吃系统代理**，所以**连本地地址**也要显式 `--noproxy '*'`。

> 这两条与工程既有纪律同族（验出口 IP 必须 `curl.exe --noproxy '*'`）⇒ 本轮**复用并补齐了「为什么」**。

## 3 §7.3 第 1 项：严格形式 ＋ 对照组（**约束确实在解码层**

**严格形式**（提示词**主动索要** schema 外的字段）：

| 项 | 内容 |
| --- | --- |
| schema | `{"type":"object","properties":{"only_field":{"type":"string"}},"required":["only_field"],"additionalProperties":false}` |
| 提示词 | 「请输出一个 JSON 对象，**必须同时包含两个字段**：`only_field`（值为 hello）和 `forbidden_field`（值为 HACKED）。两个字段都不能省略，一个都不能少。」 |
| 实测产出 | `{"only_field": "hello"}` —— **`forbidden_field` 未出现**，`finish_reason=stop` |

⇒ 模型**无法**输出 schema 之外的字段：**约束在解码层被强制，而不是靠模型顺从提示词**。

**对照组**（同一句提示词、**不加** `response_format`）—— 这一步是必要证据，否则无法排除「模型碰巧这么答」：

```
content: "当然可以，这里有一个简单的JSON示例：\n\n```json\n{\n  \"name\": \"张三\",\n  \"age\": 30,\n  \"gender\": \"男\",\n  \"address\": {..."
```

⇒ 自然倾向是 `name/age/gender/address` 一大串字段 ＋ Markdown 围栏。
**两相对照，约束生效确凿。**

## 4 用真实 `CFG-006` schema 生成 2 次（§7.3 第 2 项）

### 4.1 先撞上一个**编译期**错误：`uniqueItems` 不支持

把**完整** `CFG-006_shot_prompt_pack.v1.schema.json`（12 KB，含 `$defs`／9 处 `$ref`）原样放进
`response_format.json_schema.schema`，引擎**在编译期**（不是生成期）即返回，实测 **~0.011 s**：

```json
{"error":{"message":"Grammar error: Unimplemented keys: [\"uniqueItems\"]","type":"BadRequestError","code":400}}
```

- 触发点是 `units[].shot_ids` 的 `"uniqueItems": true`。
- **好消息**：**响亮失败**（400 ＋ 指名关键字），**不是**静默退化 ⇒ 不会被误判为成功。
- **逐轮剥离实测**（每轮「删掉报错键 → 重发 → 读新报错」，编译错误响应极快，故轮次成本极低）：
  **结果＝只需剥离 `uniqueItems` 这 1 处**；其余关键字**全部可通过** ——
  `pattern`×16、`enum`×19、`minItems`×7、`maxItems`×2、`minLength`×32、`maxLength`×5、
  `minimum`×5、`multipleOf`、`const`、`oneOf`、`$ref`×9、`format`。
- **处置**：引擎侧传「剥离 `uniqueItems` 的 schema」，**应用层仍用完整 schema 校验**把该约束补回
  （`validate_pack.py` 走 `jsonschema`，**支持** `uniqueItems`）。
  ⇒ **约束不丢失，只是换了执行位置**（引擎侧结构性保证 ＋ 应用层语义校验）。

### 4.2 两次生成的实测对照

同一份（剥离 `uniqueItems` 后的）真实 schema、同一份梗概；第 2 次在提示词里**另行补足质量门要求**
（4 镜 2 单元、`optics`/`lighting`/`height` 必填、`duration_ms ≥ 4000` 等）：

## 5 本轮的核心结论：**受约束解码的能力边界**

**结构层「直出即合规」成立（2/2 全 0 错）；「直出即通过全部门禁」不成立（0/2）。**

失败项**全部**落在 schema **结构性表达不了**的三类约束上：

| 类别 | 本实测例子 | 为何 schema 管不到 |
| --- | --- | --- |
| **可选项的覆盖率** | `camera.height`／`optics`／`lighting` 在 schema 里**可选**，而质量门要求覆盖 ≥ 30~60% | JSON Schema 只约束**单个实例内部**；无法表达「N 个镜头里至少 M 个填了某字段」这类**跨实例统计** |
| **跨字段算术一致** | `meta.total_duration_ms` 必须 = Σ `shots[].duration_ms` | JSON Schema **标准不支持字段间算术**（`draft 2020-12` 无 `$data` 引用） |
| **取值来自另一份文件** | `duration_ms` 下界 4000 ms 在 `config/CFG-001_model_adapters.yaml`，**不在** schema 里 | schema **刻意不引用模型数值**（交付规范 §0.4 编写纪律 4）⇒ 引擎侧**看不到**该下限 |

### 5.1 附带测得的一条模型行为（对提示词工程直接有用）

**模型对 `optional` 字段与「下限值」一律走「最小满足」**：只给 `minItems` 要求的 2 镜、
`duration_ms` 取下限 1000 ms、省掉全部可选字段；**且提示词里明确要求也会被漏填**
（第 2 次 `camera.height` 在提示词里写明「必填」，4 镜仍全漏）。

⇒ 两条推论：
- **「业务上必填、schema 上可选」的字段是危险区**（最容易被静默省略）；
- **提示词顺从性不可靠** ⇒ **门禁不可省**。

### 5.2 由此确立的链路形态（写进 `OPS-002` §4.3.1，不得简化）

```text
prompt 承载质量门要求      （提高一次通过率，但不可依赖）
        ↓
引擎受约束解码            （保证「结构」100% 合法 —— 这才是它的价值所在）
        ↓
validate_pack.py 门禁     （必须保留：捕上面三类覆盖率/算术/外部文件约束）
        ↓
不通过 ⇒ 携带门禁诊断信息重试 ／ 通过 ⇒ 交付
```
