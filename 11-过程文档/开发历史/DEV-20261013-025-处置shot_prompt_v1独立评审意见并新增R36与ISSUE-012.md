- **接续前已接触的既有意见内容**：`BR-03`、`R-01`、`SR-01`、`SR-02`、`R-02` 等；
- **自评受影响条目**：`PR-01`、`PR-05`／`PR-06`、`PR-12`／§3-B；

## 4 四处自查发现（**均非评审提出**）

### 4.1 门禁⑯「风格漂移」子串误报

- **现象**：带 schema 跑门禁时 **9 镜**被报「出现锚点清单之外的风格词 `['赛璐璐上色']`」，而正文**逐字复述的正是锚点**「柔和赛璐璐上色」。
- **根因**：判据用 `w in v`（**子串包含**）；词表 `style_tags` 含「赛璐璐上色」、本片锚点是「**柔和**赛璐璐上色」→ 正文写锚点反被判违规。**与 R28 的中英尺度错配同源：字符串粒度 ≠ 语义粒度。**
- **修复**：① 清单词若被任一锚点**包含**则不视为「清单外」；② 比对前先**剔除锚点原文**再在剩余文本里找。**误报归零。**

### 4.2 `CFG-007_SCHEMA.md` 的 R26 与交付契约口径分叉

`R26` 原口径「`amplitude` ∈ {空串, small, large}」在**上游侧**成立，在**交付包侧**与 schema 冲突。处置**不是改 R26**，而是**新增 R33 专管交付包侧**，并在 `CFG-007_SCHEMA.md` 写明「两条合读」。**这是「同一语义在不同层有不同合法表达」的一次显式建模。**

### 4.3 `CFG-008_manifest.yaml` 的失实表述

`shot_prompt_v1.notes` 原写「**可直接过 `validate_pack.py` 门禁**」——实测该包**从来不能**（24 条 BLOCK）。**该类表述正是 PR-02 的技术根源：把「应该能过」写成了「能过」。** 已改为如实表述。

### 4.4 判据只查「必备」不查「多余」→ 清单外字段无人管（**承接 PR-14，本次最有价值的一处**）

**触发**：为落实 `PR-14`「两处清单不一致会留下『清单外字段无人管』的漏洞」，回头逐处核对模板自身的承继清单，发现**第 6 处**不一致——模板头部注释列 `forbidden_items` 而**漏 `notes`**（其余 17 项逐字相同，差异只在末项）。

**顺着再查判据侧**：`R27` 只校「**必备字段是否齐备**」，**完全不校「是否多出契约外的字段」** → 任何上游带来的、规范里没有的字段都能**悄悄进入交付包**，到门禁才被拦下——**拦得太晚，且只看得到一条汇总报错**。

**连带查出一个真实的契约缺口 —— `ISSUE-012`**：上游 `script_v1` 与 `storyboard_v1` **都有顶层 `forbidden_items`**，但交付包**没有它的容器**：

| 可能容器 | 能否承载「内容层禁忌」（如「禁止出现真实人名」） |
| --- | --- |
| 规范 §3.1 顶层六段 | **无此段** |
| §3.3 `negative_global` 四类组织 | **不能**——四类是**通用图像项／视频时域项／形变延续项／场景专属项**，覆盖的是**画质与伪影** |
| `meta.compliance` | **不能**——只含 `safety_check`／`copyright_check`／`marking_check`／`statement_id` |
| `characters[].forbidden` | **不同语义**——那是**角色**不变要素（规范 §3.4） |

而 `CFG-008_manifest.yaml` 却写着「**禁止项承接：剧本 forbidden_items 须原样承继**」——**与模板正文、投影映射表均不符**。**这是本次发现的第 2 处失实表述。**

**处置（两侧都补）**：

1. 模板三处承继清单**逐项对齐** + 头部显式写明「上游**顶层**字段不在本承继清单内，按投影映射表逐项处理」；
2. 投影映射表**补全三行**（上游顶层 `title`/`genre`/`style_ref`/`aspect_ratio_default`/`total_duration_ms`/`quality_gate` 不搬入；`forbidden_items` **无容器**；`unspecified` **无此段**）+ 一句总则「凡上游出现而本表无对应投影行的字段，均属契约缺口，须登记规范层 `ISSUE`，**不得默认照抄**」；
3. `CFG-008_manifest.yaml` 该行**更正**为「不搬运 + 登记 `ISSUE-012`」，并显式区分 `characters[].forbidden`（内建字段，照常产出）；
4. **新增判据 `R36 NO_EXTRA_KEY`**——检查**七处**（顶层／`shots[]`／`units[]`／`characters[]`／`meta`／`style_bible`／`aigc_meta`）是否出现契约外键。⚠️ **字段集直接读交付 schema**（`properties` 与 `$defs`），**刻意不另写一份会陈旧的清单**——PR-14 的病根正是「**再写一份清单就又多一个会不一致的地方**」；schema 不可读时**跳过（不伪判）**，与 R33 的取舍一致；
5. 负向样本 **+3**（顶层 `forbidden_items` / `shots[].continuity_note` / `meta.director_intent`）；
6. 登记 **`ISSUE-012`**。

> **教训**：判据只管「**该有的在不在**」、不管「**不该有的在不在**」，漏洞就一定从后门进来。这与 `PR-02` 是**同一枚硬币的两面**——PR-02 是「**显式的空**不合法」，本条是「**多余的键**不合法」；前者靠枚举比对发现，后者靠**字段集封闭**发现。**而字段集的唯一真值来源只能是交付 schema 本身。**
