## 1 为什么做这一批

`T-006` 的余项里，「版权校验接入」长期是 `compliance.copyright_check` 的一个**硬编码常量**：

```python
"copyright_check": {"status": "not_available", "note": "版权校验未接入（T-008）"}
```

两个问题：

1. **归因是错的**。`T-008` 是**二期人工审核台**，与版权校验无关。真实卡点是
   「**可比对的作品库未建立**」——`REQ-005` `SW-015` 原文自己就写着：
   「相似度比对**依赖可比对的作品库**，该库**当前未建立**（属 `T-011` 数据来源任务范围）
   —— **库未建立前本条不得判达标**」。
   一个错归因会让后续所有人都去追二期任务，永远追不到。
2. **「没检」被一个常量冒充成结论**。`not_available` 本身是正确的语义，
   但它应当是**服务算出来的**（库在哪、多大、扫了几段、阈值多少），
   而不是一个写死的字符串——写死的字符串无法回答审核方任何追问。

## 2 `SW-015` 三条的拆解口径

`SW-015` 有三项要求，可实施性差异极大。本批按「**可实施即落地、不可实施如实降级**」拆：

| `SW-015` 要求 | 本批处置 | 依据 |
| --- | --- | --- |
| ① 相似度检测（≥0.5 即风险提示，阈值可配） | **能力建成、框架可跑**；作品库缺失时结论 `not_available` | 作品库属 `T-011`，原文明确「库未建立前不得判达标」 |
| ② 改编来源声明（必填、可留存、可导出） | **完整落地**（不依赖作品库） | 声明是客户义务，与服务端能力无关 |
| ③ 风险不阻断但须逐条列明 | **完整落地**（进独立交付件） | 依赖 ① 的输出结构，已按「能列就逐条列」设计 |

**没有做的事，也如实写在这里**：本批**不宣称**「版权校验达标」。
`SW-015` 的达标判据是「高风险样本召回率 ≥90%、正常样本误报率 ≤5%（同时满足）」，
而这个判据需要 ≥50 对雷同样本 + ≥50 对正常样本的**作品库**——库不存在，判据无从测量。
`T-011` 交付作品库后，本模块**无需改码**即可启用比对（只改两个配置项）。

## 3 实现要点

### 3.1 相似度算法：字符 3-gram Jaccard

选它而非 embedding 的三个理由：

1. 作品库尚不存在，任何算法都跑不出真实召回率，先上重武器没有意义；
2. 判据语义是「**字面相似** ≥0.5」，3-gram Jaccard 与之同构；
3. **确定性算法可被审阅复核**——embedding 会随模型版本漂移，反而不利于举证。

`similarity()` 是唯一算法入口，未来切换不动外部契约。
阈值只影响判定、**不影响测量**（单测对此有断言：同一对文本在 0.01／0.99 两个阈值下
`max_similarity` 必须相等）。

### 3.2 三态语义必须分清

| `status` | 含义 | 会不会被误读 |
| --- | --- | --- |
| `passed` | 比对**跑过了**，全部低于阈值 | 否 |
| `risk` | 比对跑过了，**检出**超阈值内容 | 否（不阻断，逐条列明） |
| `not_available` | **没比对**（作品库未建立） | ⚠️ 极易被读成「无风险」⇒ 声明件里**加粗明写「未校验」**，并写「这不等于『无风险』」 |

未做比对时 `max_similarity` 返回 `None` 而非 `0.0`——给个 0 就是在暗示「相似度为零」。

### 3.3 声明件为什么是独立文件

`CFG-006` 的 `copyright_check` 是 `additionalProperties: false`，只有 `status` 与 `note`。
而声明需要承载：提交方声明（来源／原作／授权／声明人）＋ 命中项**逐条四列表**＋ 责任边界。
塞进 `note` 会变成一坨自由文本，既不可机检也不可阅读。

⇒ 独立落盘 `copyright_declaration_<pack_id>_<hash>.md`，文件名对同一 `pack_id` **稳定**
（同包重打包不散落多份），并做两件事保证「**可导出**」的完整语义：

1. 文件在交付包目录内（物理可导出）；
2. `AST-004` 合规声明**显式引用**其文件名（可发现）。

第 2 条是必须的：`CFG-005` 清单的 `artifacts` 是**固定五项**且 `additionalProperties: false`，
声明件**没有**清单登记位。**为一份文件去改契约并不划算**——故改由合规声明引用。
这个取舍写在这里，避免后来者误以为「清单里没有＝不需要」。

### 3.4 声明缺失绝不代填

`normalize_declaration()` 对空值返回 `present=False`，声明件写「**未提交改编来源声明**」
并写明「风险由提交方自负」。

**不代填「原创」的理由**：权属陈述的法律主体是客户。服务端替客户写一句「原创」，
等于服务端代替客户作出了一个可能不实的权属声明——这比「缺失」危险得多。

## 4 ★ 同批发现并修复的合规级缺陷（`ISSUE-074`）

这批真正值钱的不是版权功能，是下面这个。

### 4.1 现象

给测试加断言时发现：**同一个交付包，两处编号不一样**。

```
目录名 / DeliveryResult.pack_id / 清单 pack_id   →  FR-PK-20261111-A1B2C3D4
pack.json 的 meta.pack_id / aigc_meta.ProduceID  →  {{PROVIDER_CODE}}-PK-20261111-33A7AACC
```

稳定复现（连跑三次，后者的随机短码每次都不同）。

### 4.2 根因

`pack_delivery` 里有**两处都想写 `pack_id`，后写者赢**：

1. `meta` 装配阶段：`_PACK_ID_RE` 校验既有编号合法则**沿用**（目的是同包重打包不散落多目录），
   接着 `pack["meta"] = meta`、`pack_id = str(meta["pack_id"])` ⇒ 目录名／清单都用这个值；
2. 随后 `apply_service_truth(pack, truth, ...)`：它的 `META_SERVICE_KEYS` **含 `pack_id`**，
   把 `meta.pack_id` **覆盖回** `truth["pack_id"]`（当次新生成的随机短码）。

于是目录与清单是 A，`pack.json` 内的 `meta.pack_id` 与 `ProduceID` 是 B。

### 4.3 为什么这是合规级而非美观问题

- `SW-013`：内容编号**不可被删除篡改隐匿**——一次交付两个编号，等于编号不再唯一标识该交付；
- `R30`：`ProduceID` 必须与 `pack_id` **同源**；
- **审核方比对这个动作的成本极低**：拿交付目录名去对 `ProduceID`，一眼就能看出矛盾；
- **历史真机交付包同样受影响**，此前无人告知。

### 4.4 修法（含为什么不是「把 `pack_id` 从 `META_SERVICE_KEYS` 里删掉」）

在 `apply_service_truth` **之后**加「编号一致性收口」：以已确定的 `pack_id` 为准重新钉
`meta.pack_id` 与 `aigc_meta.AIGC.ProduceID`／`PropagateID`，并把纠偏**如实记进**
`service_truth.overrides`——**不是静默改写**。

没有直接删 `META_SERVICE_KEYS` 里的 `pack_id`：那个集合的语义是「服务层域的键」，
`pack_id` 确实属于服务层域；问题不在归属，而在**同一件事有两处写入权**。
结构性收敛（把「沿用」策略与「覆盖」策略合并到一处）已记入 `ISSUE-074` 待评估，
本批只做**止血 + 回归锁**，因为改契约面太大、收益不确定。

**回归锁**：`test_pack_id_is_identical_across_all_artifacts` 跨五处比对
（目录名／`DeliveryResult`／清单／`pack.json`／两个隐式标识字段），任一漂移即失败。
