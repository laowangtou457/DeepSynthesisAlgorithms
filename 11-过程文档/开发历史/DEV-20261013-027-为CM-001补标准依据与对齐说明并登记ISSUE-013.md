## 2 项目方质询（原话）

> 「你写配置管理计划依据的标准是什么？」

**理解**：这是一次**依据性核查**——`CM-001`（Configuration Management Plan）作为工程配置管理的**上位规则文件**，对外（尤其备案审计）须能回答「凭哪本规范这么做」。质询点即「**依据声明是否成立**」。

---

## 3 核查结论：V1.0 **未声明任何外部标准依据**

| 核查项 | 结果 |
| --- | --- |
| `CM-001` §1.4「引用文件」 | 共 **8 条**，**全部为工程内部文件**（`CM-002` 取号表 / `PRO-001` 评审规程 / `DEV` 留痕 README / `PM-001` / `PM-002` / `CFG-007_SCHEMA` / `SPEC-004` 交付规范 / `SEC-007` 签核规程）——**零条外部标准** |
| 全工程标准引用扫描 | 出现的 `GB/T` **全部是内容安全国标**（`GB/T 45654—2025` 等，挂在 `REQ-003_系统级需求/REQ-003_SYS-内容安全尺度与红线口径-最终版.md`）——**配置管理类标准 0 引用** |
| 首版实际依据 | **按配置管理通行实践自拟**：五要素（配置标识 / 配置控制 / 状态记录 / 配置审计 + 基线）；术语（CI / Baseline / FCA·PCA）取自 `GB/T 11457` 术语体系，**但编制时未查标准原文、未标出处** |

> **如实定性**：对**要交监管的备案工程**而言，CMP 缺依据声明是**实质缺陷**（审计会问「凭哪本规范」）。本节即为此补齐。

| 标准 | 名称 | 现行状态 | 本计划的采信方式 |

### 7.2 一次自检工具误报（**未造成影响，记录以备复用**）

核查 `CM-001` 行尾时，用 `head -c 200 … | od -c | grep -c '\r'` 计数得 **2**，一度判断该文件为 **CRLF**（与同目录两份 LF「不一致」）。改用**二进制逐字节复核**后确认：**该文件实为 LF、与 `HEAD` 完全一致**——

- **根因**：`grep` 的 **BRE 下 `\r` 不表示回车**，被当作**字面字母 `r`** 匹配（命中的是 `od -c` 输出中含字母 `r` 的行）；
- **正确做法**：判断行尾应**在 Python 二进制模式**下 `b.count(b"\r\n")` 比对（本次即用此法复核）；
- **归属**：属**我方自检脚本的用法错误**，与 `CM-001` 内容无关，**无任何文档被误改**。⚠️ 与 `DEV-20261013-026` §7.4 的教训（**批量改写脚本须显式指定行尾**）**同源**——「**行尾相关的一切判断都必须落到字节层**」。
