## 一、问题（`ISSUE-057`）

`delivery_service.build_manifest()` 产出的是**自拟简化清单**：

```json
{"manifest_version": "1.0.0", "files": [...], "counts": {...},
 "compliance": {...}, "is_preview": true, "preview_note": "...", "service_truth": {...}}
```

而 `CFG-005_manifest.v1.schema.json` 要求 `manifest_version` **const `1.1.0`**、
必填 `statement_id` 与 `artifacts.{shot_prompt_pack,aigc_meta,overlay_assets,compliance_statement}`，
且 **`additionalProperties: false`** ⇒ 上述自拟字段**一个都不允许**。

后果：交付门禁的**清单侧判据完全无法启用**（`manifest_checked=false`）。这不是「少一项」，
而是**四件套之④在机器校验意义上不存在**——`SW-014` 的举证链断在这里。

## 三、核心设计：18 项自检「不允许编造 pass」

### 3.1 判据来源分六类

| `from` | 含义 | 用于 |
| --- | --- | --- |
| `pack` | 由包侧门禁条目推导（多对一映射） | 1/2/3/4/5/6/7/10/13/14/15/16/17 |
| `assets` | 清单装配时的**实际素材清点** | 8 |
| `statement` | `statement_id` 实际值 ＋ 声明文件存在性 | 9 |
| `adapters` | 适配条目 `verify_status` | 12 |
| `human_review` | **人工录入台账** | 18 |
| `out_of_scope` | 交付包层面不可机检 | 11 |

### 3.2 三种「拿不到证据」一律非 `pass`

| 情形 | 结果 | 理由 |
| --- | --- | --- |
| 判定对象为空（`shots`／`units` 为 0） | `warn`「未检」 | 判据遍历空集合，**根本没跑**；「没跑」≠「通过」 |
| 交付包层面无判据（第 11 项系统级去标识入口） | `warn` ＋ 指向 `PRO-012` 矩阵 | 不静默豁免，也不谎称通过 |
| 有判据但无机器可判内容（第 9 项「8 项要素齐全」） | `warn` | 文字要素核对无判据，人工承担 |

### 3.3 真机实测抓到的一处假 `pass`（本批最有价值的发现）

第 17 项「无负向残留」的判据 `negative.residue` 是**逐镜遍历 `shots`**：

```python
for s in shots:            # shots 为空 ⇒ 循环体一次都不执行
    v = s.get(f) or ""
    if ...: rep.add(BLOCK, "negative.residue", ...)
```

`shots == []` 时报告里**一条 `negative.residue` 都没有**，而「无条目 ⇒ 无问题 ⇒ pass」的
判定规则会得出「负向残留检查通过」。真机 mock 包（`shots: []`）第一次跑出来就是 `pass`。

⇒ 修正：为该项声明 `"requires": "shots"`，判定对象为空时标 `warn`「未检」。
同批复核其余 17 项，确认第 13/14/15（依赖 `shots`）、5/16（依赖 `units`）已声明，其余不依赖。

⚠️ **这类缺陷无法靠读代码发现**——判据逻辑本身没错，错在「空集合的语义」。
只有把真实空包喂进链路才暴露。

## 四、`human_review` 的唯一合法来源

**只从人工录入台账读**（`APP_HUMAN_REVIEW_LEDGER`，JSON）：

```json
{"records": [{"pack_id": "...", "no": 18, "item": "...", "result": "pass",
              "checked_at": "ISO8601", "operator": "姓名", "detail": "..."}]}
```

⚠️ **绝不**从 `pack["human_review"]` 取——那是「让模型自己证明自己被人工核对过」，
是**假合规**的典型形态。台账未配置 ⇒ 自检第 18 项 `fail` ＋ 清单判据
`human_review.missing` **BLOCK**，**如实拦住**。

## 八、遗留（如实登记，非本批缺陷）

1. **正式包仍被如实阻断**：`compliance.copyright`（版权校验未接入＝`T-008`）与
   `human_review.missing`（台账未建）⇒ 这两条是**真缺口**，不是清单形态问题。
   清单对齐契约后，交付门禁第一次**能够**看见它们——这是修复的**目的**，不是回归。
2. **mock 产物不合 `CFG-006`**：`_mock`／`_backend` 等信封键与空 `shots`／`units`
   会被 `schema.pack` 判 BLOCK。真机（vLLM）产物无此问题，与 `T-099` 无关。
3. `SPEC-008` **文件名 `-v2.3` 与正文 `v2.4` 不同步**（历史遗留）。改名属 C 类变更
   （含全量引用同步），不在本批范围；互锁测试**以正文版本行为准**，已在测试里注明。
4. `app/DELIVERY_OUT_DIR` 与 `HUMAN_REVIEW_LEDGER` 需在部署机配置；台账录入流程
   （谁录、何时录、如何与 `pack_id` 关联）须随人工抽检制度一并落地（`SEC-016` 线）。
