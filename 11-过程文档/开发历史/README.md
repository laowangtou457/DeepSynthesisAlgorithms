# 开发历史

> **本目录按「动作粒度」留存工程推进过程记录**：工程每发生一次推进动作，生成一份独立文档。
> 建立 2026-10-13；由「开发历史巡检任务」（每 2 小时自动执行）产出，也支持手工补录。

---

## 一、目录用途（为什么单独建这个目录）

本工程此前的过程留痕是**围绕单份文档**的：`10-评审记录` 收他方意见、`11-过程文档/编制要求` 发我方要求。但这两者都回答不了「**这个工程是怎么一步步长成现在这样的**」——因为**跨目录、跨文档的工程推进动作没有归属地**：一次代码重构、一次目录结构调整、一次版本控制与脱敏改造、一次硬件需求编制，都不属于任何单一文档的过程链。

本目录填补这一空缺，具体用途：

| 用途 | 说明 |
| --- | --- |
| **时间轴留痕** | 按发生顺序回答「哪天做了什么、为什么做」，交接时提供上下文 |
| **持续投入证据** | 备案与安全评估时证明算法机制机理被**持续审核、评估、验证**（SYS-007），并可在监督检查时提供必要技术数据支持（SYS-012） |
| **变更可追溯** | 每份交付物/文档的变更都能回溯到一次具体动作，避免「文档突然变了、说不清为什么」 |
| **防遗忘** | 单人开发（1 名开发，见 SYS-013 约束）时，工程上下文极易丢失，此为外部记忆 |

## 二、命名与编号

```
文件名：DEV-<YYYYMMDD>-<NNN>-<动作简述>.md
编号  ：DEV-<YYYYMMDD>-<NNN>
```

- `NNN` 为**当日流水号**，自 `001` 起，按动作**实际发生时间**递增；
- 动作简述用中文短语，直述做了什么（例：`建立Git远程仓库并完成首次推送`），不用「工作记录」「今日进展」这类无信息量的词；
- **编号一经分配永不复用**；补录历史动作时按其**实际发生日期**编号，不排到当日末尾；
- 一份文档只记**一个动作**。若一次操作实际改变了多个互不相关的对象，拆成多份。

## 三、记录要素（必备五节）

| 节 | 内容 | 硬要求 |
| --- | --- | --- |
| 1 动作摘要 | 1–3 句说清做了什么、为什么做 | 必须能脱离上下文读懂 |
| 2 变更明细 | 变更对象 / 变更前 / 变更后 / 说明 | 新增与删除的文件须**逐个列出**，不得写「若干文件」 |
| 3 影响与关联 | 关联需求编号、交付物编号、受影响的其他文档 | 无关联写「无」，不留空 |
| 4 验证与证据 | 验证方式 + 证据（命令、输出摘要、提交哈希） | **无证据的动作不得记为「已完成」**，须标「未验证」 |
| 5 遗留 | 本次未闭环的事项 | 无则写「无」 |

头部信息块必备字段：**记录编号、记录时间、动作类型、触发来源、涉及目录、状态**。

**动作类型**取值：`需求` `架构` `代码` `文档` `结构` `配置` `版本控制` `合规资产` `修复` `决策` `机制`。

## 四、巡检机制

| 项 | 约定 |
| --- | --- |
| 频率 | **每 2 小时**一次（自动巡检任务） |
| 判定依据 | **双源**：① `git log` / `git status`（版本控制视角，看提交与工作区差异）；② 工作区文件 `mtime`（看**未纳入版本控制**的变更，如 `_受控区/`） |
| 状态文件 | `_巡检状态.json`：记录 `last_scan_at`、`last_scanned_commit`、`recorded_actions[]`（已记录动作的编号、时间、指纹、涉及文件） |
| 幂等 | **同一动作只记一次**。判定靠「文件指纹 + 变更清单」比对；同一文件在同一批次内的多次修改**合并为一条动作** |
| 无新增时 | **不生成任何文档**，不写占位文件，巡检直接结束并在回复中一句话说明 |
| 时间戳 | 以本机系统时间为准；跨天批次按动作**实际发生时间**归日 |

> `_巡检状态.json` 是**巡检机制自身的元数据**，其自身变化**不构成工程推进动作，不得记录**。

## 五、边界与纪律

### 5.1 不记录的内容

| 类别 | 例 |
| --- | --- |
| 瞬时信息 | 临时文件路径、工具报错堆栈、检索/搜索过程、token 消耗、中间草稿 |
| 纯读取行为 | 打开/查看/查询某个文件（未产生变更） |
| 非工程动作 | 聊天、提问、澄清、讨论未形成结论的设想 |
| 重复内容 | 已在 `10-评审记录` / `编制要求` / 变更记录表中留痕的内容，不重复搬抄 |

### 5.2 排除扫描的路径

`.git/`、`_受控区/`（不入版本控制；受控资产的变更**只在摘要层记「受控资产发生变更」**，不记实体词条）、`09-合规资料库/07-第三方词库源/funNLP/`、`__pycache__/`、`node_modules/`、`.venv/`、各类缓存与临时输出目录。

### 5.3 脱敏纪律（重要）

本目录**位于版本控制内**，随 `main`（对外脱敏版）一并提交。因此：

- 文档中**不得出现真实企业名与人名**，一律使用占位符 `{{PROVIDER_NAME}}` / `{{ALGO_OWNER}}` / `{{ALGO_AUTHOR}}`（口径见根 `README.md` 第〇节）；
- 记录「做了什么」而不是「谁做的」，人员一律写角色（算法负责人 / 算法作者 / 运维）；
- **受控类**（涉政、涉民族）内容**不落明文**，只记「受控资产计数变化」，与 `09-合规资料库/05-台账与制度/SEC-012_资产受控与保密说明.md` 口径一致。

### 5.4 只读扫描

巡检任务**不修改**任何被记录的正文文档、不动 `00-需求` ~ `11-过程文档` 下的既有文件（除本目录与 `11-过程文档/README.md` 的文件清单外），**只写入本目录**。

## 六、与其他目录的关系

| 目录 | 留痕对象 | 方向 |
| --- | --- | --- |
| `10-评审记录/` | 某**份**文档的评审意见 | 收（他人 → 我方） |
| `11-过程文档/编制要求/` | 某**份**文档的编制要求 | 发（我方 → 他人） |
| **`11-过程文档/开发历史/`** | **整个工程**的推进动作 | 时间轴（顺序留痕） |
| `00-需求/REQ-006_需求文档.md` §10 变更记录 | 需求条目级变更 | 结构化登记，粒度粗 |

> 四者**互补不重复**：变更记录表回答「需求改了什么」，本目录回答「哪天为了什么改了它」。
