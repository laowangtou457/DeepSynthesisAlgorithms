## 1 动作摘要

手动路径（`OPS-002` §3.3 方式 B）首轮实跑失败，**报错信息被截断成一行、无法定位**。回厂排查发现是**两个独立缺陷叠加**：Python 片段被漏传一个参数（真因），而脚本的 `$ErrorActionPreference = 'Stop'` 又把原生程序写入 stderr 的每一行升级为终止性错误（把真因藏起来）。两者**缺一不可**，只修一个仍会失败。

本次一并纠正一处**事实判断错误**：`ubuntu-24.04.5-wsl-amd64.wsl` **不是 zip 容器，而是 gzip 压缩的 rootfs tar**——原脚本按 zip 解包，在该分支上必然抛 `BadZipFile`。

⚠️ **修完首轮再跑，又被第二类问题拦下**：脚本把 `tar.exe` 的退出码当完整性门禁，而 Ubuntu 官方这个 tar 会被 bsdtar 报 `Archive entry has empty or unreadable filename` 并**返回退出码 1** —— 尽管它已列出 **49188/49190** 条、且归档本身**结构完好**。⇒ **好镜像被判「文件损坏」而拒绝导入**。故本批实际修复的是**三处缺陷**（详见 §2.1）。

### 4.5 第二轮追加：`tar.exe` 退出码**不可**作完整性门禁（实测证据）

| 检查项 | 结果 |
| --- | --- |
| `tar.exe -tf` **退出码** | **1** ← 原脚本据此判「文件损坏」并 `exit 4` |
| `tar.exe` **实际列出条目** | **49188 / 49190**（仅 2 条异常名被跳过） |
| `tar.exe` stderr | `Archive entry has empty or unreadable filename ... skipping` ＋ `Error exit delayed from previous errors` |
| tar 结构（Python 独立判读） | **49190** 成员 · 末尾 **2048 字节全零**（正确的 EOA）· 总长 **1,275,596,800 B ＝ 10240 的整数倍** |
| 异常条目成因 | 名字含**字面 `\x2d`** 的 systemd unit **2 个**（如 `usr/lib/systemd/system/system-systemd\x2dcryptsetup.slice`）＋ 含非 ASCII（`ő`）的证书软链 1 个 —— **官方打包侧遗留**，非本次解包引入 |
| **新判据 正例** | Python 全量校验：**退出码 0 / 耗时 1.8 s**，输出 `members = 49190`、`odd names = 2`、`RESULT=49190` ✅ |
| **新判据 反例** | 自造「无 `etc` / `usr` 顶层」的 tar：**退出码 1**，报 `NOT_A_ROOTFS: missing top-level etc,usr` ✅ |

> ⚠️ **通用纪律（与 `OPS-002` §3.1.1 的既有教训互为镜像）**：本工程此前记的是「**退出码 0 ≠ 成功**」（wsl 静默失败）；
> 本次是「**退出码非 0 ≠ 失败**」。外部工具的退出码**只在语义明确时**才是判据；
> 凡以退出码作门禁，**必须同时给出「为什么这个码可信」的依据**，否则应换成**能表达意图的替代判据**
> —— 此处即「**是不是 rootfs 布局**」，而非「tar 命令满不满意」。

### 7.2 暴露的缺陷：`DRY_RUN=1` **走不到打印启动参数**

干跑的目的就是「先看参数」，但脚本在 `2/5` 因缺 pip 直接 `die` ⇒ **干跑意义落空**（本轮实际发生）。
同族问题另有一处：`3/5` 在拿不到版本时会执行 `[[ "$MAJOR" -gt 0 ]]`（此时 `MAJOR=未取到`），
bash 会报 `integer expression expected` 并在 `set -e` 下中止 —— 即便只修 `2/5`，**仍到不了 `5/5`**。

| # | 缺陷 | 修正 |
| --- | --- | --- |
| ① | `DRY_RUN=1` 时缺 pip 仍 `die` | 干跑**降级为 `WARN`** ＋ 打印补 pip 的两条命令，**不阻断** |
| ② | 干跑仍会执行 `pip install` | 干跑分支**只打印将要执行的命令**，不安装 |
| ③ | `[[ "未取到" -gt 0 ]]` 非整数比较报错 | 版本比较**整体包进「已取到版本」分支** |
| ④ | venv 内仍传 `--break-system-packages` | 探测 `sys.prefix != sys.base_prefix` ⇒ **venv 自动摘掉**，并打印 `(venv)` 标记 |

> ⚠️ **本批第一类缺陷（§4.5 记的是「退出码 0 ≠ 成功」、本节记的是「退出码非 0 ≠ 失败」）之外，
> 这是第三类**：**功能缺陷可以藏在「中断点」后面** —— 干跑被前置检查拦住，
> 于是「打印参数」这个功能**从未被执行过**，缺陷也从未暴露。⇒ 凡设了「前置门禁」的脚本，
> 必须验证**门禁之后的那段**也能被走到（本批用三路分支实测补上）。

### 7.3 附带修正：venv 提示**粘成一行也能跑**

`die` 提示里原本是两行（`python3 -m venv ~/vllm-venv` / `PY_BIN=… bash $0`），
人工从终端复制时**换行丢失**（本轮实际发生，被粘成

**语义上本就是一条命令**，即使粘成一行也正确。

## 8 第四批（2026-10-15 16:39）：下载慢的真因＝**源选错**（结论订正）＋ 代理打通选项

### 8.1 现象与真因

用户反馈「vLLM 轮子下载太慢，已开代理，能否加速」。结论：**与代理无关，是 pip 源选错了** ——
而**选错的依据出自我方**：`OPS-002` V1.2 把**阿里云源列为「采用」**，依据只是一条
「`200` / `0.57 s`」的**可达性**探测。

⚠️ **那条探测测不出吞吐** —— 当时只对一个**几十 KB 的索引页**发了 HEAD。改用**真实大轮子**
（`torch-2.14.1-cp312-manylinux_2_28_x86_64.whl`）计时 12 s 取样后，阿里云只有 **0.38 MB/s**：
按 6~8 GB 计**要跑 4~5 小时**，正是「太慢」的来源。

- 旁证：`~/.config/clash-verge/clash-verge.yaml` 为 `allow-lan: false`（另一客户端，**未在运行**）。
- 宿主侧 WSL 网卡地址＝ **`172.30.224.1`**（`vEthernet (WSL (Hyper-V firewall))`），即 WSL 的默认网关。

### 9 续：pip 源「短窗 vs 持续」口径订正（2026-10-15 傍晚，`OPS-002` V1.6）

**触发**：项目方贴回 `--speedtest` 结果（`huawei` 23.05 ／ `aliyun` **21.92** ／ `pypi.org` 15.60 ／ `cn` 4.43 MB/s）
并追问 ——「**阿里云吞吐量挺高的，为什么下载速度那么慢**」。

**取证（全只读，未动任何工程文件）**：从 Windows 侧读 WSL 内 pip 的 HTTP 缓存
（`\\wsl$\Ubuntu\root\.cache\pip\http-v2`，**224 个 `.body` / 2.50 GB**），
按**相邻文件完成时间的差值**反算每个大轮子的实际下载速率：

| 轮子 | 体积 | 相邻完成间隔 | 反算速率 |
| --- | --- | --- | --- |
| `torch-2.13.0` | 502.2 MB | 1736 s | **0.289 MB/s** |
| `triton-3.8.0` | 236.5 MB | 656 s | **0.361 MB/s** |
| `nvidia_cudnn_cu13-9.20.0.48` | 349.2 MB | 1061 s | **0.329 MB/s** |
| `nvidia_cusparselt_cu13-0.8.1` | 162.3 MB | 490 s | **0.331 MB/s** |
| `nvidia_nccl_cu13-2.29.7` | 196.4 MB | 876 s | **0.224 MB/s** |
| `tokenspeed_triton` | 89.0 MB | 238 s | **0.374 MB/s** |
| `nvidia_cuda_nvcc-13.4.92` | 45.5 MB | 222 s | **0.205 MB/s** |

**结论（口径订正，本工程第二处）**：

1. 阿里云**持续速率 0.31 MB/s**（区间 0.20~0.37），仅为同源 10 s 短窗读数 **21.92** 的 **1/70**
   ⇒「测速快、下载慢」**不是矛盾，而是两种口径**：短窗单流常只吃到 CDN 的**突发额度（令牌桶）**。
2. 速率**稳定得像被按住**（而非拥塞那种忽快忽慢）⇒ 更接近**限速**，不是链路质量问题。
3. 同源同日短窗 **0.38 ↔ 21.92（57 倍）** ⇒ **任何单次短窗读数都不能作为选源结论**。
4. 缓存元数据（响应头）显示来源 `Server: Tengine` ＋ `X-Swift-*` ＋ `Ali-Swift-Global-Savetime`，
   且 `X-Cache: $HIT` ⇒ 对象**来自阿里云 CDN 且已命中缓存**，慢**不是回源**造成的。
