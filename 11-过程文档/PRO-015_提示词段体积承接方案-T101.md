## 1 测量基线：885s 到底花在哪（本方案的地基）

`T-100b` 冒烟第 2 轮（`sess_4d4ec9be2e52`，`serve8017_t100b.log`，2026-11-05 11:50）
是第一个「分镜 11 镜／5 单元」走完 `shot_prompt` 的真机样本。段级 trace 全量对账：

| 量 | 实测 |
| --- | --- |
| 调用次数 | **12**（`package_head`＋5 个 `unit:` × **2 次尝试**） |
| `prompt_tokens` 合计 | **202,584**（均值 ≈16.9K/次） |
| `completion_tokens` 合计 | **39,006**（第 1 次 ≈21.8K；第 2 次 ≈17.2K） |
| 端到端耗时 | **885s** |
| 解码速率（对拍） | storyboard 段 6,457 tokens／153s ⇒ **≈42 tok/s** |
| **合并后产物体积** | **14,455 chars（≈6K tokens）** |
| `merge_warnings` | **36**（越界重复条目被按 id 去重丢弃） |

三条推论（⭐ 本方案与 `PM-001` 原始框定的**差异**，全部来自实测）：

1. **延迟由产出体积驱动，不是输入体积**。39,006 completion tokens ÷ 42 tok/s ≈ **850s**——
   885s 里 ~96% 在解码；202K prompt 的预填只占几十秒。
   ⇒ `T-101` 原始框定「输入侧 ×5~6」对**延迟**不成立（对 token 成本与**扩展性**仍成立：
   上游随场次增长，每段输入迟早撞 32,768 窗口）。
2. **产出膨胀 ≈6 倍**：最终内容 ≈6K tokens，模型却产出 39K。结合 `merge_warnings=36`，
   形态是**每段都把输入里看得见的整包重写一遍**（越界产出别单元/别镜），合并时按
   id「保留先出现者」丢弃。段「该产什么」只靠 `{segment}` 提示语这一**弱信号**约束——
   输入（整份 `storyboard_json`）与引擎 schema（整包 schema）都不拦。
3. **重试定位失效放大 2 倍**：`R34` 报错只列 shot_id（`S02-SH002`…），
   `_retry_segments` 规则 1 只认 `U<数字>` 字面 ⇒ 定位不到 ⇒ `scope_fallback`
   **全部 6 段重跑**（第 2 次 17.2K completion 基本白烧）。

## 2 根因（一句话）

段级拆分把**调用**切开了，但**输入、引擎 schema、重试定位**三处仍是整包口径——
「段该产什么」没有一处是**程序保证**。这与 `PRO-014` §1 的立论同构：
把段级约束从模型移到程序。

## 3 方案（A/B/C 三期）

### 3.1 A 期（本批施工）：输入裁剪 ＋ 重试定位

**① `storyboard_json` 按段裁剪注入**（`shot_prompt` 段专用；`script_json` **不裁**——
角色/风格一致性依赖它，且仅 ~2K tokens）：

| 段 | 注入的 scoped 副本 |
| --- | --- |
| `package_head` | 头部键全保留＋`units[]` 全量（含 `shot_ids`，供枚举）＋`unspecified` 全量；**`shots[]` 置空**（头部段不产镜，镜明细是最大体积块） |
| `unit:<id>` | 头部键全保留＋**只该单元**＋**只该单元的镜**（按 `shots[].unit_id` 与 `units[].shot_ids` **并集**过滤）＋`unspecified` 全量 |

- 纪律：**解析失败／uid 不中 ⇒ 原样整份注入＋留痕**（不猜测、不静默）；
- `total_duration_ms`／`quality_gate` 等小键原样保留（不构成体积问题，不引入新差异面）；
- **门禁不受影响**：`R23`/`R24`/`R31` 等跨层判据喂的是 `gate_upstream`（上游**原文**，
  在裁剪之前已另行保存）——与 `T-100` 的 `scene_json` 注入同一先例；
- 预期效果：模型看得见的只有该段该产的 ⇒ 越界重写失去素材 ⇒ completion 显著回落
  （预期两轮 39K → **<15K**），`merge_warnings` 同步下降。

**② `_retry_segments` 增 shot_id 定位**（`T-086` 按段重试的补全）：

- 报错文本中的 shot_id（`S\d{2}-SH\d{3}`）**出现在某段产物文本里** ⇒ 该段重跑
  （shot 的属主段必含其 id，定位即包含关系，无需全局映射表）；
- 兜底（宁多勿漏）：`S<场>-` 前缀 → 场号 → 解析各段产物的 `units[].scene_no` 命中即重跑
  （覆盖「镜整段没生成出来、任何段文本里都找不到」的形态）；
- 现有规则 1~3 与 `scope_fallback` 语义**原样保留**。

### 3.2 B 期：A/B n=12 验收后翻默认（本批不做）

- 两臂＝`shot_prompt_segment_scope` off/on（上游固定同一份剧本，`_ab_t100b.py` 器具复用，
  但**须归档每轮产物原文**——`DEV-20261105-005` 器具缺陷 ② 的教训）；
- 主指标：两轮 completion tokens 合计 **<40% 基线**、`shot_prompt` 端到端 < **400s**；
- 不回退判据：`R7`/`R9`/`R14`/`R34` 失败率不得高于 off 臂；新失败类 0；
- 成本判据**沿用双口径纪律**（`PRO-014` §5 教训：先问分母——按**交付镜数归一**）。

### 3.3 C 期：引擎 schema 按段收窄（**已随本批提前实施**，见 §7.1 的实测改判）

`cap_pack_array_bounds`：`package_head` 段 `units`/`shots` 上限 **0**（`minItems` 同步压 0——
否则 schema 不可满足）；`unit:<id>` 段 `units` 上限 **1**、`shots` 上限＝该单元上游镜数。
超出上游的镜本就该被 `R31`/`R7` 拦——收窄只是把「事后判」升级为「事中不生成」
（与 `R14`/`R8` 回填同族：把约束从模型移到程序）。`script_json` 按场裁剪**仍未做**（体量小，可缓）。

## 4 开关与灰度

- 新配置项 `shot_prompt_segment_scope: bool = False`（env `APP_SHOT_PROMPT_SEGMENT_SCOPE`）。
- **行为改变类**（模型输入变了）⇒ 默认 `false`，A/B 后翻——与
  `storyboard_scene_orchestration` 同一纪律。
- ⚠️ 与 `T-100` 开关的**依赖方向**：`T-101` 是 `T-100` 翻默认的硬前置，反之不成立

  在 >6 镜时同样走 `package_head`＋逐单元，同样受益）。

## 7 施工追记（2026-11-05；留痕 `DEV-20261105-006`）

### 7.1 一次**批内实测改判**（本方案最重要的事件）

`A` 期按原设计先行落地（输入裁剪＋重试定位），真机第 2 轮验证给出**否证**：
