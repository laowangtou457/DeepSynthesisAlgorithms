## 0 一句话

评审 §4-B 指出 `SW-002` 有两件事**都没有"家"**：**① 每轮跑出来的漂移报告没有落盘位置**（于是「同一口径下的时间序列」这句话在物理上不成立）；**② 本层的语义判据与脚本判据打架时没有裁定载体**（于是「由人裁定」这句话没有主语、没有落笔处、没有与报告轮次的关联）。**两件事必须一起定**，因为 ② 的裁定只能挂在 ① 的落点上。本件把两件事的**现状、可选项、代价、推荐**摆开，**等裁决**。

## 1 要定的是哪两件事

### 1.1 事项 B-1 · 漂移报告现在是「一段文本」，不是「一份物证」

**事实（逐条可核）**：

| # | 事实 | 出处 |
| --- | --- | --- |
| 1 | `check_consistency_v1` 的产物是**一份 JSON 文本**（顶层恰好 5 键：`pair_role`／`focus`／`findings`／`summary`／`anchor`），模板**没有规定它落哪个文件** | `TPL-016` 输出契约段；`CFG-007` ⑧ 段判据登记 |
| 2 | 模板**自陈本层的核心价值**是「可以被反复调用：每轮修改后跑一次，得到的是**同一口径下的时间序列**，而不是每次重新定义'什么算漂移'」 | `TPL-016` L23–L25 |
| 3 | 模板**自陈本层的下游用途**包含「**供备案举证留档**」 | `TPL-016` L96 |
| 4 | `SW-002` 的**验收标准本身就是这份报告**——「以输入要点与既有产物为基准**逐项比对**…漂移 **0 处**方为合格」 | `REQ-005` §2.1 `SW-002` 行 |
| 5 | 本工程**已有同型先例的处置**：`SPEC-007` **V2.2** 为 `revise` 层的缺口台账补了归档落点（详见 §2.1） | `SPEC-007` L63／L66／L220／L222／L259／L1547 |

**这四条合起来说明什么**：

- 「时间序列」**必须落盘才能成立**（第 2 条）——否则「每轮跑一次」只产出一叠**彼此无关的一次性文本**，第 3 轮和第 1 轮放在一起看时，没有任何东西能证明它们是同一个口径、同一个对象、有先后顺序。
- 第 4 条更硬：**验收时被调阅的就是这份报告**，它不是过程日志、是**验收证据**。而**证据必须有物证形态**——"我们每轮都比对过了"这句话，在监督检查面前等价于零。
- 第 5 条说明**这不是新问题**：同一批内已经处置过一次同类缺口，**重复出现而不处置会形成"审查口径不一"**——而「审查口径不一」正是"两份主评一起评"要避免的事。

**当前缺口的具体后果**（决策时请把这一段的功能当作"不做的代价"来读）：

| 场景 | 现在能做到 | 落盘后能做到 |
| --- | --- | --- |
| 备案举证「我们对每轮修改都做了一致性校验」 | 只能说、不能出示 | 出示第 1…N 轮的报告，逐轮可比 |
| 复现「第 3 轮为什么判这处是漂移」 | 若当时那段文本没保存，无法复现 | 调取 r3 报告即复现 |
| 裁定一次真实分歧 | 裁定过程无载体（见 §4） | 裁定挂在轮次报告旁，可回溯 |
| 判据升级后回看历史结论 | 无法区分"当时没查"与"当时查了没问题" | 有历史报告可比对 |

### 1.2 事项 B-2 · 「由人裁定」这句话没有主语、没有落笔处、没有关联

**事实**：

- `TPL-016` 明写「两者结论不一致时**如实并列**，由人裁定——**不得择一掩盖**」（L48），且多处要求把拿不准的条目「入表并注明'**需人裁定**'」（L166／L171／L260／L280／L340／L364）。
- 但模板**没有**规定：**"人"是谁**、**裁定写在哪**、**与哪一份报告（哪一轮）关联**。
- 同族的缺口在 `SW-008` 那轮已被处置过一半：`TPL-015`／`TPL-016` 的分工段（`TPL-016` L35 起）只笼统写「**互补 + 交叉验证**」，**没有落到具体判据上**（评审 §4-B 结论二原话）。

**"冲突"的机器可判定义（必须先定义，才能谈载体）**：

```
冲突(C) ⇔ 存在一对同源结论，二者在本工程既有判据体系中不可能同时为真：
  C1  本层报 drift_count > 0   而  脚本侧 R23／R24／R28／R31／R36 全过
  C2  本层报 clean（drift_count = 0）  而  脚本侧至少一条 BLOCK
  C3  同一对产物上，本层判 consistent 而 --before 比对脚本（见下 §1.3）判「顺手多改」
```

⚠️ **关键**：`C1`／`C2` 是**两个既有产物的组合**，不需要任何新增字段就能判——所以"触发条件"这条**属服务层编排**（模板不实现），但它**需要一个把两份结论放在一起的地方**，那就是 B-1 的落点。

### 1.3 顺带说明：`--before` 比对脚本（决策项第 6 项）会**加深** B-2，不会消解它

项目方已对第 6 项裁「**立项**」。请注意这两件事的耦合关系：

- 评审 §4-A 第 2 层明确指出：`--before` 脚本的 `op_type=normalize` 路径**必须走"值语义等价"豁免**（否则会把被授权的结构化归一当成"多改"），而该豁免规则**必须与校验侧「数值换写法不算漂移」（`TPL-016` L270–L282）同源**；
- 评审原话：「否则**两个脚本会对同一对产物给出相反结论**，这正是待议项 B 的'仲裁缺口'在工程侧的再现」。

⇒ **`--before` 脚本落地后会新增第三个判据方（语义判据 / 交付门禁 / `--before` 脚本），三方的两两冲突都需要同一个仲裁载体**。所以 B-2 不是可以往后拖的小事，而是**第 6 项落地的前置条件**。

### 2.3 ⚠️ 为什么**不能照抄** `revise` 的成例

这是本件最需要项目方注意的一处**结构性差异**：

| 维度 | `revise` 层（`SW-008`，已处置） | `modify_v1`／`check_consistency_v1`（`SW-002`，本件） |
| --- | --- | --- |
| 是否链路阶段 | **是**（`stage_chain` 第 5 值） | **不是**——「**对话式修改…不是链路阶段**」（`CFG-007` L172 ⑧ 段）；`modify_v1` **刻意不填 `stage`** |
| 产物归属 | **交付包的伴随产物**（与交付包同批交付） | **既不是四件套、也不是伴随产物**——它是**运行期证据**，服务于任意阶段的任意轮次 |
| 适用对象 | 只有"客户自带素材"这一种入口 | `target_stage` **5 个取值**（`synopsis`／`script`／`storyboard`／`shot_prompt`／`pack`）——**只有 `pack` 那一个落在交付包目录里**，其余四个阶段**当时连交付包都还没生成** |
| 轮次 | 一次性（一包一台账） | **天然多轮**——同一 `target_stage` 上第 1…N 轮，评审强调「没有轮次号，'时间序列'这个说法就不成立」 |
| 落点结论 | 交付包目录（`manifest.json` 登记） | **必须分层**：`pack` 可随包，其余四类只能落服务层 |

⇒ **照抄成例会把四分之四的轮次漏在体系之外**。这也正是评审原话里「**非 `pack` 时**与 `<pack_id>.unspecified.json` **同级**（`SPEC-007` §1.4 目录树）**或服务层留档目录**」这一句留了"或"的原因——因为非 `pack` 场景下，交付包目录**可能还不存在**。

### 3.2 命名口径（评审的硬要求，无论选哪个落点都必须含）

> 「**文件名必须含轮次号**（如 `<pack_id>.drift.r<N>.json`）——**没有轮次号，'时间序列'这个说法就不成立**，而轮次号正是 `TPL-015` L110 已经要求 `change_context` 标注的那个东西的**另一半**（报告有轮次、变更说明也有轮次，两者才对得上）。」（评审 §4-B 结论一）

⇒ 本件建议把轮次口径**写死为**：`N` = **该 `target_stage` 上的第 N 轮修改**（从 1 起，正整数），与 `change_context`（`TPL-015`「修改是**多轮累积**的」段，L110–L111）标注的轮次**同源同值**。⚠️ **不同 `target_stage` 各自独立计数**（改 `storyboard` 的 r2 与改 `pack` 的 r2 是两回事），因为它们是不同的产物对象。

## 5 两案的耦合关系（为什么必须一起定）

```
        ┌───────────────────────────────────────────────┐
        │  B-1 归档落点（报告落到哪、叫什么名）            │
        │  └─ 定义"轮次"= 报告与裁定共用的关联键          │

                        │ 提供"落笔处"与"关联键"
                        ▼
        ┌───────────────────────────────────────────────┐
        │  B-2 仲裁载体（裁定写到哪、怎么与轮次对上）      │
        └───────────────┬───────────────────────────────┘
                        │ 触发条件与强制触发属服务层
                        ▼
        ┌───────────────────────────────────────────────┐
        │  服务层方案（MR-13 溯源落点 / 非 pack 留档 /    │

        │  ⏸ 项目方第 3 项已裁「等服务层方案再定 · 挂起」 │
        └───────────────────────────────────────────────┘
```

**三条耦合纪律**：

1. **轮次键一次定死**（§3.2）——两份文件（报告 + 裁定）"对不上"就等于没关联；
2. **两层落点共用一套命名**（`qa/` 与 服务层留档目录用同一套 `<id>.drift.r<N>.*` 形态）——否则"同一事实两处表述不一"必然复发；
3. **服务层三项（MR-13 / 非 `pack` 留档 / 冲突触发）共用一张挂起表**——它们本质是同一件事（"服务层为 `SW-002` 留什么运行期档案"）的三个切面。
