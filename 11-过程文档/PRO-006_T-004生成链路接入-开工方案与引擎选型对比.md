## 3 唯一硬前置：推理引擎路线

### 3.1 为什么它是「硬前置」

**约束①（平台）** —— 本机是**原生 Windows**，WSL 未安装；而主流高吞吐推理引擎**官方均不支持 Windows 原生**。
　· SGLang 官方文档明写：「**Linux 或 WSL2。不支持 Windows 原生**」；
　· vLLM 同族口径（本会话**未取得 vLLM 官方支持矩阵原文**，标 **⚠️ 待核验**；但两者同属 PyTorch + 自定义 CUDA kernel 路线，平台约束一致）。

**约束②（契约）** —— `TPL-009_shot_prompt_v1.yaml` 的 `sampling` 段**注释原文**：「本层输出为**受约束解码**的 JSON（服务层以 **jsonschema 为 FSM 约束采样**，`delivery/schemas/CFG-006_shot_prompt_pack.v1.schema.json`）」。
　→ 引擎**必须支持 guided decoding**（结构化输出约束）；
　→ `app/inference/base.py` 的 `TextGenerator.generate(prompt, params, **json_schema**)` **参数位已在 `T-003` 预留**，但**至今无任何后端实现它**（`mock` 忽略该参数）。

**约束③（连带口径）** —— `T-010` 已定案 **BF16 全精度、不走量化路径**；任何「必须转 GGUF／量化件」的路线都与该定案**一致性冲突**。

### 3.2 三候选逐项对比

| 维度 | **A. WSL2 + vLLM** | **B. Windows 原生 + Ollama（已装）** | **C. Windows 原生 + transformers** |
| --- | --- | --- | --- |
| 平台可行性 | ✅ 需启用 WSL2（Windows 功能 + 重启） | ✅ 已装 0.40.3，**零安装** | ✅ 包已装（但见下） |
| **FSM 受约束解码** | ✅ 支持（vLLM structured outputs／xgrammar 生态） | ❌ llama.cpp 系**不支持** jsonschema 驱动的 FSM 约束采样 | ❌ 无约束解码（`outlines`／`xgrammar` 可补，非官方路径） |
| 与 `T-010`「不走量化」一致性 | ✅ 直接加载 `E:\models\...` 的 **BF16 safetensors，零转换** | ⚠️ **冲突**：现有模型均为 **GGUF 量化件**；用 BF16 须自行转 GGUF，且 llama.cpp 于 24 GB 卡上吞吐并不优于 A | ✅ 可直接加载 BF16 |
| 单卡 10 并发（`SYS-015`／`T-013`） | ✅ PagedAttention ＋ 连续批处理，最贴近 `T-012` 的「单卡 10 并发」目标 | ❌ 无 PagedAttention，10 并发目标基本不可达 | ❌ 无 |
| `HW-002` KV Cache 可登记 | ✅ 启动日志可读 `GPU KV cache size`，直接支撑 `HW-002` | ❌ 口径与 vLLM 不同，无法按原口径登记 | ❌ 无 |
| 环境／权重落盘 | ⚠️ WSL2 默认 vhdx 落 C 盘，**须迁至 E/F** | ✅ 已在 `F:\Develop\VLM\models` | ✅ 已在 F 盘 |
| 新增安装量 | 中（WSL2 runtime ＋ Linux 侧 venv ＋ torch-cu ＋ vllm ≈ 8–12 GB） | 几乎为零 | 小（仅补 CUDA 轮子） |
| 首次可跑通耗时 | 中 | **最短** | 中（须先解决 Python 3.14 的 CUDA 轮子） |
| 主要风险 | WSL2 启用需重启、或受本机／企业策略限制；宿主 ComfyUI／Ollama 与推理进程**争用 24 GB 显存** | **把「受约束解码」从架构保证降级为后处理补偿**，与模板契约**正面冲突** | 现装 `torch` 为 **CPU 版**、且解释器为 **Python 3.14.7**（CUDA 轮子覆盖面窄），须重装甚至换解释器 |

### 3.3 倾向性建议（**待项目方裁决**）

**建议取 A（WSL2 + vLLM）为正式路线。** 理由按权重排序：

1. **唯一同时满足两条硬约束**：既支持 FSM 受约束解码（约束②），又直接吃 BF16 不走量化（约束③）；
2. **唯一能支撑下游验收**：`T-013` 的 10 并发实测与 `HW-002` 的 KV Cache 登记，都依赖 vLLM 的运行时口径（B／C 均无法提供）；
3. **绕开 Python 版本坑**：Windows 原生只有 **Python 3.14.7**（CUDA 轮子生态不成熟），WSL2 侧可用成熟的 3.11／3.12 生态，反而更省事。

**若 WSL2 启用受阻的降级路径（须显式留痕）**：短期改用 **B** 打通「端到端真实生成」，**仅用于链路与契约验证**；但必须在留痕中**显式声明**「**非受约束解码、非 BF16、并发不达标**」，且**不得**据此校准 `SYS-015`。

## 6 待裁定的范围口径（两项）

### 6.1 `revise` 是否计入 `T-004` 的「五段」

- **事实**：七阶段状态机（`schemas/dialogue.py` 的 `Stage` 枚举共 7 值）**无 `revise` 承载**；`dialogue_service._GENERATE_ON` 亦**无 revise 项**。`revise_v1` 是 `SW-008` 的**并行入口层**——设计语义为「客户自带素材时不跑前四段」。
- **选项**：(a) **计入** —— 须先定义「并行入口」如何进入七阶段主链（新增阶段？旁路会话？）；(b) **不计入** —— `T-004` 只做主链四段生成，`SW-008` 服务化**另立任务**。
- **建议：先取 (b)**，把 `SW-008` 服务化与 `T-008`（二期外围能力）一并看，**避免 `T-004` 膨胀**而稀释关键路径。

### 6.2 会话持久化归属

- **事实**：`DEV-20261014-017` 第 4 条写「持久化替换见 **`T-004` 及二期**」——**口径含糊**；`SW-001` 验收含「状态可恢复」，当前**内存实现未完全达成**（仅留了超时配置位 `APP_SESSION_TTL_SECONDS`）。
- **建议：明确归二期（`T-008`）**；`T-004` 只做「**替换后端 ＋ 真跑通**」，不加 DB／Redis。
