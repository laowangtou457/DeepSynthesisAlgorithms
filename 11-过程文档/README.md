# 过程文档

> **本目录存放「过程件」**——即围绕工程推进与文档编制产生、但**不属于交付物本身**的过程性材料。现有两个子目录，性质互补：
>
> | 子目录 | 留痕对象 | 信息流向 |
> | --- | --- | --- |
> | `编制要求/` | **某份专项文档**的编制输入 / 评审委托 | 我方 → 编制方 / 评审方（发） |
> | `开发历史/` | **整个工程**的推进动作 | 时间轴（顺序留痕） |
>
> 建立 2026-10-12（`编制要求/`）｜ 2026-10-13（`开发历史/`）

---

## 一、目录用途（为什么单独建这个目录）

本工程此前把「编制要求」放在 `01-架构设计/`，与交付物正文同处一室，导致两个问题：

| 问题 | 后果 |
| --- | --- |
| 要求与正文同目录 | 正文修订后，**要求件被当成过期的旁支**，容易被覆盖或误删 |
| 要求件性质不清 | 交接时**分不清哪份是"成果"、哪份是"任务书"**——成果可以改，任务书是历史依据 |

**因此约定**：

1. **被要求编制的对象文档**留在原归属目录（如 `01-架构设计/`），**不移动**；
2. **编制要求**一律进本目录，按类别归入子目录；
3. 文件名格式：**`<对象文档名>-<文类>.md`**，如 `REV-D-017-01_分镜提示词交付规范-编制要求书.md`；
4. 要求件**永久保留，不随对象文档的修订而删除或覆盖**——它记录了「当时为什么提这些要求」。

## 二、与 `10-评审记录` 的分工（按信息流向划分）

两者都是**围绕某份专项文档的过程件**，但**方向相反**，因此分列两个目录：

| 目录 | 信息流向 | 内容 | 产生时机 |
| --- | --- | --- | --- |
| `10-评审记录` | **他人 → 我方**（收） | 评审方对某份文档提出的问题清单与处置建议 | 文档**产出后** |
| `11-过程文档/编制要求` | **我方 → 他人**（发） | 我方要求对方编制什么、达到什么标准 | 文档**产出前** |
| `11-过程文档/开发历史` | **时间轴**（顺序） | 工程每一次推进动作做了什么、怎么验证的 | 动作**发生时/后** |

> 前两者回答「某份文档的要求与意见」，第三者回答「工程是怎么长成现在这样的」，三者互补不重复。

同一份专项文档的完整过程链如下，**两端各归其位、中间的正文留原目录**：

```
11-过程文档/（编制要求）  →  XX 文档正文（留在归属目录）  →  10-评审记录/（评审意见）  →  XX 文档修订
      我方下达                      编制方产出                      他方反馈                  我方修订
```

## 三、子目录

| 路径 | 内容 | 说明 |
| --- | --- | --- |
| `编制要求/` | **发出件**：编制要求书（`xx-编制要求书.md`）· 评审请求书（`xx-评审请求书.md`） | 我方下达的编制输入件与评审委托件；同类文件会持续增加，故单独归类 |
| `开发历史/` | **动作粒度工程留痕**（`DEV-<YYYYMMDD>-<NNN>-<动作简述>.md`） | 每发生一次工程推进动作生成一份独立文档；由每 2 小时巡检任务自动产出，也支持手工补录。规范见该目录 `README.md` |

> 后续如出现性质相近的其他发出件（如「修订任务书」「专家答复要点」「版本变更说明」），按同样方式在此新增同级子目录，不新开顶层编号。

> **顶层另有规程件**：`PRO-001_评审接力协作规程.md`（`PROC-RELAY-001`）——本工程**对外评审的强制协作规程**。规定：对外评审**一律走路径 B（文件接力，真实独立会话）**，路径 A 降级为设计期预评审；并规定四个落点命名、意见编号前缀分配（`D-` / `R-` / `RV-` / 后续专用）、六件必备、我方七项核验与五条禁区、接力队列。**每次委托评审前先读它。**

### 3.1 `编制要求/` 发出件约定（两个文类通用）

本子目录现有**两类发出件**：

| 文类 | 命名 | 性质 | 流向 |
| --- | --- | --- | --- |
| **编制要求书** | `<对象文档名>-编制要求书.md` | 我方要求对方**编制**某份文档 | 我方 → 编制方（发） |
| **评审请求书** | `<对象文档名>-<评审视角>评审请求书.md` | 我方**委托**对方对某份文档出具评审意见 | 我方 → 评审方（发） |

四条约定：

1. **被要求编制 / 被评审的对象文档**留在原归属目录（如 `01-架构设计/`、`03-工程代码/`），**不移动**；
2. **发出件**一律进本目录，按类别归入子目录；
3. 文件名格式：**`<对象文档名>-<文类>.md`**，如 `REV-D-017-01_分镜提示词交付规范-编制要求书.md`、`REV-SW-004-01_synopsis_v1-故事梗概生成模板-导演视角评审请求书.md`；
4. 发出件**永久保留，不随对象文档的修订而删除或覆盖**——它记录了「当时为什么提这些要求」。

> **评审请求书的下游是 `10-评审记录/`**：请求书（我方委托，留本目录）→ 评审意见（他方产出，落 `10-评审记录/`）。**两端各归其位，被评审正文不动。**
>
> **与「本会话内实例评审」的区别**：评审请求书委托的是**真实独立会话**，其意见在**举证效力**上强于本会话内加载同一份专家定义所出的意见；两类意见都保留、互不覆盖。
>
> ⚠️ **这两类的取舍已于 2026-10-13 定案**：**今后一律走「评审请求书 + 真实独立会话」（路径 B）**；「本会话内起实例」（路径 A）**仅作设计期自查**，其产物须命名为「预评审」并注明性质。完整规程见顶层 **`PRO-001_评审接力协作规程.md`**（`PROC-RELAY-001`）。

### 3.2 `开发历史/` 核心约定（完整规范见其 `README.md`）

| 项 | 约定 |
| --- | --- |
| 粒度 | **一份文档只记一个动作**；互不相关的对象拆多份 |
| 判定依据 | 双源：`git log`/`git status` + 工作区文件 `mtime`（覆盖未纳版的 `_受控区/`） |
| 幂等 | 同一动作只记一次；同批次同文件的多次修改合并为一条 |
| 无新增时 | **不产出文档**，不写占位文件 |
| 无证据不闭环 | 无验证证据的动作不得标「已完成」，须标「未验证」 |
| 脱敏纪律 | **不出现真实企业名与人名**，一律用 `{{PROVIDER_NAME}}` / `{{ALGO_OWNER}}` / `{{ALGO_AUTHOR}}`；人员写角色 |
| 只读扫描 | 不修改被记录的正文文档，只写入本目录 |

## 四、归档要求（`编制要求/` 适用）

| 项 | 要求 |
| --- | --- |
| 文件编号 | 必须给（如 `REQ-NORM-DELIVERY-001b`），并与对象文档编号建立对应 |
| 版本与日期 | 必须给；同一对象的多次要求按 `a`/`b`/… 或版本号区分，不覆盖 |
| 上位文件 | 必须写明被要求的对象文档（路径 + 编号），**且该对象文档不随本件移动** |
| 要求正文 | 必须分层、可核查；涉及数值须给出**来源**（实测 / 官方文档 / 内部规则实现） |
| 验收口径 | 必须写明「达到什么状态算完成」，否则要求件无法闭环 |
| 保留原则 | 永久保留，不随对象文档的修订而删除或覆盖 |

> `开发历史/` 的归档要求见其 `README.md` 第三节「记录要素」（五节必备结构 + 六项头部字段）。
